1. **P2 — USB/SAFE still erases DP state after a failed restart.**  
   [phy-qcom-qmp-combo.c:4626](<scratchpad>/fix/dp4/k/b2/drivers/phy/qualcomm/phy-qcom-qmp-combo.c:4626)

   The early ignore condition additionally requires `qmp->com_on`. Scenario: DP is initialized, a C↔D request is pending, then a forced orientation restart fails and leaves `com_on=false`. A late USB/SAFE bypasses the ignore condition, overwrites `req_mode`, changes `qmpphy_mode` to USB-only, and can successfully restart with DP held in reset. Subsequent DP power-on is refused until another DP request restores routing.

   **Remove `qmp->com_on` from this early USB-only ignore condition.** Keep it on the later powered-DP deferral condition, where it permits DP requests to recover an off common block.

2. **P1 — inherited native-HPD retraining/shutdown race remains; not introduced by these guards.**  
   [dp_display.c:1601](<scratchpad>/fix/dp4/k/b2/drivers/gpu/drm/msm/dp/dp_display.c:1601), [dp_ctrl.c:2333](<scratchpad>/fix/dp4/k/b2/drivers/gpu/drm/msm/dp/dp_ctrl.c:2333)

   IRQ_HPD now holds `plugged_lock`, but atomic disable/post-disable do not. A native HPD request can pass the `link_clks_on` check; concurrent post-disable then gates the link clocks; link maintenance subsequently writes `PUSH_IDLE` or training registers. That is the unclocked-MMIO hard-hang scenario these patches already describe.

   Serialize teardown with IRQ handling, placing guards after synchronous snoop cancellation and, for post-disable, after the eDP unplug handler; release before the final runtime-PM put.

   **ROG5 qualification:** PMIC GLINK transports `hpd_irq` to the mux, but its DRM notification carries only connected/disconnected status. MSM selects IRQ handling from its hardware HPD status register. Thus GLINK’s `hpd_irq` bit alone does not trigger this race; it requires native MSM pulse handling to be active. I found no demonstrated ROG5 boot-hang regression here.
