Their user-visible effects remain hypotheses until tested.

**SYS_UBWC_CONFIG must use the stock gen1 layout.** Lahaina’s LPDDR5 configuration sets channel/MAL/HBB override bits, with **8 channels, MAL 32, HBB 16**. Swizzle and spreading values are zero, but their override bits are clear: that does **not** explicitly disable those firmware settings. Stock changes HBB separately for LPDDR4/4X. (`S/msm_vidc_platform.c:2180–2182`; `S/vidc_hfi_helper.h:925–942`; `S/msm_vidc_platform.c:2452–2465`.)

The stock packet builder declares **60 bytes**, rather than a compact property plus five values:

| Word | Content |
|---:|---|
| 0 | Outer size: `0x3c` |
| 1 | `HFI_CMD_SYS_SET_PROPERTY`: `0x10005` |
| 2 | Property count: `1` |
| 3 | `HFI_PROPERTY_SYS_UBWC_CONFIG`: `8` |
| 4–5 | Embedded `size`, `packet_type` |
| 6 | Override bits: `7` |
| 7–9 | Channels `8`, MAL `32`, HBB `16` |
| 10–11 | Swizzle `0`, spreading `0` |
| 12–13 | Reserved |
| 14 | Extra word included in stock’s declared packet size |

This follows stock’s size calculation and embedded structure. **Stock leaves the embedded size/type words unwritten; zeroing them is a proposed deterministic implementation, not an established firmware requirement.** (`S/hfi_packetization.c:250–288`; `S/vidc_hfi_helper.h:189–206,925–942`; `K/iris_hfi_gen1_defines.h:24`.)

Thus the zero-initialized proposal’s complete 15-word packet is:

```text
0000003c 00010005 00000001 00000008
00000000 00000000 00000007 00000008
00000020 00000010 00000000 00000000
00000000 00000000 00000000
```

Patch 0163 already implements this layout. (`W/patches/linux-7.2.7/0163-media-iris-ROG5-SM8350-OEM-firmware-platform-data-secure-session-EOS-power-off-gating.patch:158–194`.)

Stock queues UBWC during fresh core initialization, after SYS_INIT, image-version/debug and subcache commands, before subsequent session setup. It does **not** first wait for SYS_INIT_DONE in that sequence. k115’s core initialization calls SYS_INIT, image version and interframe collapse without this property. (`S/hfi_common.c:1746–1767`; `K/iris_hfi_common.c:77–90`.)

**Hypothesis:** matching the LPDDR5 bank configuration could improve memory behavior at high throughput. Existing bit-exact decoding shows that its omission is not sufficient to explain a universal decode failure. Test it independently; neither the packet’s acceptance nor a performance gain is established by A–D. (`W/test-results/2026-10-02-video-iris-k115-ram-trials.md:14`; stock configuration references above.)

**The OUTPUT/OUTPUT2 count mismatch is concrete.** For NV12 split decoding, both drivers use firmware OUTPUT for internal UBWC DPBs and OUTPUT2 for the client’s decoded pictures. Iris’s format and size properties already follow that arrangement. (`K/iris_hfi_gen1_command.c:923–935,1067–1076`; `S/msm_vdec.c:1095–1114`.)

| Resource | Correct count relationship from stock | k115 advertisement |
|---|---|---|
| Compressed INPUT | Actual allocated input count, distinct from minimum | Minimum and actual both 32 |
| Firmware OUTPUT / internal DPBs | Minimum DPB count for both minimum and actual | Both 32 |
| Firmware OUTPUT2 / V4L2 CAPTURE | Required minimum plus actual client allocation | Both internal DPB count |

The stock split-mode rule is explicit at the requested `msm_vdec.c:1095–1114`; the Iris discrepancy is in [iris_hfi_gen1_command.c:979](/home/deck/.local/state/rog5-kernel-7.2.7-build-r115/source/drivers/media/platform/qcom/iris/iris_hfi_gen1_command.c:979). The wire fields are separate `count_actual` and `count_min_host` values. (`K/iris_hfi_gen1_defines.h:420–424`.)

Iris actually allocates DPBs from `fw_min_count`, falling back to the output minimum before that is known. Source-change parsing updates the capture minimum, control and VB2 allocation minimum. Consequently, advertising 32 internal DPBs is not evidence that 32 DPBs were allocated. (`K/iris_vpu_buffer.c:2213–2223`; `K/iris_buffer.c:586–592`; `K/iris_hfi_gen1_response.c:159–167`.)

**Hypothesis:** incorrect minimum/actual counts could impair firmware scheduling, capture-buffer headroom, or resource accounting. A–D do not prove that this caused a stall. The correction must use actual VB2 allocation counts, including CREATE_BUFS, rather than merely swapping the two current constants. Stock separately adds capture extras for DCVS/batching; minimum and actual are deliberately different concepts. (`K/iris_vb2.c:98–151`; `S/msm_vidc_buffer_calculations.c:703–762,835–878`.)

**Internal memory is substantially overprovisioned relative to stock’s count-dependent calculation.** Gen1 Iris places COMV, non-COMV and line storage inside SCRATCH1, and its COMV helper hardcodes 32 pictures. Stock computes SCRATCH1 using `max(output_minimum, vpp_delay + 1)`. (`K/iris_hfi_gen1.c:399–406`; `K/iris_vpu_buffer.c:727–737,836–840`; `S/msm_vidc_buffer_calculations.c:443–453`.)

| Coded dimensions | Codec | Iris count 32, bytes | Same formula at count 8, bytes |
|---|---|---:|---:|
| 1920×1080 | H.264 | 34,488,832 | 8,622,592 |
| 1920×1080 | HEVC | 66,847,232 | 16,712,192 |
| 3840×2160 | H.264 | 137,888,256 | 34,472,448 |
| 3840×2160 | HEVC | 265,421,312 | 66,355,712 |

These numbers include the helpers’ final 512 bytes. Iris and stock use matching COMV arithmetic; the decisive difference is the count supplied. (`K/iris_vpu_buffer.c:114–146,727–737`; `K/iris_vpu_buffer.h:28`; `S/msm_vidc_buffer_calculations.c:1133–1160,1287–1297`.)

Other internal sizes need a more selective comparison:

- **BIN:** Iris’s H.264/HEVC formulas correspond to stock’s low-delay case. For four pipes, the calculated sizes are 12,533,760 bytes at 1080p and 49,766,400 at 3840×2160. Stock increases BIN sizing when its delay multiplier increases; copying a delay property without that sizing relationship would be unsafe. (`K/iris_vpu_buffer.c:28–111,708–718`; `S/msm_vidc_buffer_calculations.c:1217–1254,1339–1372`.)
- **H.264 command storage:** Iris uses a height-derived multiplier of 48 where stock uses 12, before their slice caps. This is another oversizing difference, not evidence of undersizing. (`K/iris_vpu_buffer.c:169–174,215–222`; `S/msm_vidc_buffer_calculations.c:1163–1182`.)
- **PERSIST:** calculated H.264 sizes are 498,176 bytes in Iris versus 278,528 in stock; HEVC is 397,568 versus 250,112. Iris adds display-information arrays absent from these stock formulas. Those smaller differences do not justify making PERSIST reduction the first memory change. (`K/iris_vpu_buffer.c:188–195,225–230`; `K/iris_vpu_buffer.h:32–44`; `S/msm_vidc_buffer_calculations.c:1907–1924`.)

The likely memory benefit is strongest for 4K and concurrent sessions. **Shrinking COMV before fixing the advertised DPB count would make the host’s resource promises internally inconsistent.** That dependency follows directly from the count and sizing implementations above.

**Clock and bandwidth selection currently disagree about the workload.** Iris initializes decoder `frame_rate` to 480. Its QBUF estimator later counts submissions across wall time, does not divide by the elapsed interval, and clamps to 30–480. This measures submission behavior rather than media cadence. Bandwidth independently always uses 30 fps. (`K/iris_vdec.c:57,448–461`; `K/iris_platform_common.h:24–25`; [iris_power.c:64](/home/deck/.local/state/rog5-kernel-7.2.7-build-r115/source/drivers/media/platform/qcom/iris/iris_power.c:64).)

There is also a threshold inconsistency: workload MBs round each dimension up to 16, but the 1080p table thresholds use `1920*1080/256`. Thus 1080p30 evaluates to 244,800 MB/s, above the table’s 243,000 threshold, selecting its 60 fps row. (`K/iris_power.c:23–35`; `K/iris_platform_sm8250.h:9–14`.)

These are **predicted per-session votes from the source**:

| Workload | k115 bandwidth, kB/s | Consistent fps and rounded thresholds, kB/s |
|---|---:|---:|
| 1920×1080p30 | 812,000 | 416,000 |
| 1920×1080p60 | 812,000 | 812,000 |
| 3840×2160p30 | 1,224,000 | 1,224,000 |
| 3840×2160p60 | 1,224,000 | 2,403,000 |
| 4096×2160p60 | 1,224,000 | 2,403,000 |

The right column preserves the existing bandwidth values while correcting rate selection and threshold arithmetic. It is **not** a stock bandwidth result. (`K/iris_power.c:16–39,64–75`; `K/iris_platform_sm8250.h:9–14`.)

For clocks, Iris uses approximately:

```text
VPP = rounded_MB_per_frame × fps × 200 × 1.05
VSP = rounded_MB_per_frame × fps × 25
      + fps × maximum_queued_input_bytes × 8 × 10/7
frequency = max(VPP, VSP)
```

It does not divide VPP work by the four-pipe route. (`K/iris_vpu2.c:15–38`; `K/iris_platform_vpu2.c:37–47,119`; `K/iris_ctrls.c:531–541`.)

The candidate OPPs are 240/338/366/444 MHz; stock lists effectively the same frequencies. The candidate also assigns MX/MMCX required OPPs, so lowering the selected clock can change the associated power-domain requirements. (`W/dts/qcom/sm8350-asus-rog-phone5-video.dtso:103–124`; `T/../` is not needed here; stock DT: `/home/deck/Projects/rog-phone-linux-migration/kernel-src/msm-5.4/arch/arm64/boot/dts/vendor/qcom/lahaina-vidc.dtsi:29–30`.)

Assuming nominal fps and **VPP dominates**, the predictions are:

| Workload | Iris VPP request, MHz | Selected candidate OPP |
|---|---:|---:|
| 1080p30 | 51.408 | 240 MHz |
| 1080p60 | 102.816 | 240 MHz |
| 3840×2160p30 | 204.120 | 240 MHz |
| 3840×2160p60 | 408.240 | 444 MHz |
| 4096×2160p60 | 435.456 | 444 MHz |

At Iris’s initial 480 fps estimate, even 1080p’s VPP request exceeds 444 MHz. The OPP helper chooses a ceiling, falling back to a floor when the request exceeds the table, so these oversized startup requests select the maximum available OPP. These are calculations, not observed device clocks. (`K/iris_vpu2.c:26–38`; `K/iris_resources.c:62–70`; `T/drivers/devfreq/devfreq.c:2089–2095`; candidate DT references above.)

Stock’s Iris2 decoder model is materially richer:

- Divide VPP cycles by the configured work route; add the greater of 5% overhead or firmware VPP cycles, then 5.9% multipipe overhead.
- Include separate firmware cycles.
- Calculate VSP with codec, entropy, B-frame and work-mode factors.
- Treat high-bitrate VP9 specially.
  
Lahaina supplies four pipes, firmware constants 326389/44156, H.264/HEVC VSP coefficient 25 and VP9 coefficient 60. (`S/msm_vidc_clocks.c:701–702,768–812`; `S/msm_vidc_platform.c:57–64,1240–1245,2225–2226`.)

For example, stock’s **VPP component alone**, with four pipes, is approximately 108.082 MHz for 3840×2160p60 versus Iris’s 408.240 MHz. **This does not prove stock would run that stream at 240 MHz:** VSP, compressed packet peaks, B frames and DCVS can select a higher OPP. (`S/msm_vidc_clocks.c:770–812`; `K/iris_vpu2.c:29–38`.)

Stock bandwidth also accounts for DPB/OPB formats, bitrate, compression, complexity, pipes and system cache, with separate DDR and LLCC results. Stock DT has separate DDR/LLCC paths and a video cache slice; the candidate exposes one video-memory path. Therefore a cache-enabled stock bandwidth number cannot safely be copied into this candidate’s single vote. (`S/msm_vidc_clocks.c:346–465`; `S/msm_vidc_bus_iris2.c:58–99,264–265`; stock `lahaina-vidc.dtsi:12–13,39–50`; `W/dts/qcom/sm8350-asus-rog-phone5-video.dtso:85–90`.)

Two error paths deserve correction alongside voting: decoder QBUF ignores `iris_scale_power()` failure, and the interconnect helper updates its cached “applied” vote before knowing whether `icc_bulk_set_bw()` succeeded. (`K/iris_vdec.c:464–466`; `K/iris_resources.c:38–45`.)

**DCVS should follow count and rate fixes.** Stock uses firmware-owned capture-buffer counts, minimum/nominal/maximum thresholds and hysteresis; its maximum threshold is capped by actual allocation, with four extra decoder buffers. It boosts during the initial 16-buffer window and raises the shared clock if any active session requests an increase, lowering only when all request a decrease. Iris’s current power path instead computes and sums static session votes. (`S/msm_vidc_clocks.c:470–537,888–915,961–965,1037–1075`; `S/msm_vidc_internal.h:47`; `S/msm_vidc_buffer_calculations.h:10`; `K/iris_power.c:42–119`.)

**Hypothesis:** bounded startup boost plus stock-style hysteresis could reduce power while preserving decode headroom. Using the current fictional actual counts would invalidate that feedback policy; implementing DCVS first would make failures harder to interpret.

**Resolution changes are implemented, but several details need hardening.** Iris handles both SUFFICIENT and INSUFFICIENT sequence-change notifications through the same DRC path, including a subsequent output flush and source-change event. Stock continues without client reconfiguration when a SUFFICIENT notification leaves the relevant output parameters unchanged. (`K/iris_hfi_gen1_response.c:176–215`; `S/msm_vidc_common.c:1626–1694`.)

**Hypothesis:** repeated SPS notifications with unchanged output parameters could cause avoidable interruption. This requires a same-session repeated-SPS test; ordinary successful decoding does not settle it.

The gen1 changed-parameter parser also lacks per-property extent checks. An unknown property does not advance the pointer, so later declared properties can be ignored. The outer response check only establishes the fixed packet minimum. Missing properties start as zero and are then committed to instance state. (`K/iris_hfi_gen1_response.c:21–105,107–113,159–173,625–629`.)

DRC reallocates input internal buffers and creates output DPBs. It retains DPBs that firmware has not returned, while creation starts new indices at zero; FBD matching uses index and offset. **A collision is a conditional risk if old and new DPBs coexist**, not a demonstrated leak. Scratch release itself waits for RELEASE_BUFFERS and destroys the buffer after acknowledgement. (`K/iris_common.c:113–123`; `K/iris_vdec.c:401–415`; `K/iris_buffer.c:586–592,724–735`; `K/iris_hfi_gen1_response.c:458–463`; `K/iris_hfi_gen1_command.c:516–524`.)

**Seek/drain restart has a more specific stock parity gap.** Stock requeues driver-owned DPBs after an ordinary output flush, excluding active reconfiguration, and clears their payload/offset/flags. Iris marks returned DPBs dequeued/done; its completion helper returns immediately for internal DPBs, and its deferred queue helper only requeues buffers marked DEFERRED. DECODER_CMD_START clears drain state without an equivalent DPB recycling call. (`S/msm_vidc_common.c:2021–2038,2070–2083`; `K/iris_hfi_gen1_response.c:526–538`; `K/iris_buffer.c:613–630,943–951`; `K/iris_vdec.c:497–529`.)

Additionally, FLUSH_DONE merely decrements a shared pending counter; it does not match the returned flush type, despite that field existing in the gen1 response structure. **Unexpected replies can therefore corrupt the counter’s meaning.** (`K/iris_hfi_gen1_response.c:693–695`; `K/iris_hfi_gen1_defines.h:321–323`.)

**Concurrent sessions are supported in the design, but accounting has gaps.** Iris sums session frequency and bandwidth demands. Its admission path checks MB/frame and dimensions, but decoder admission does not call the existing MB/s helper. Session insertion silently declines an instance beyond the platform limit while open continues; removal does not itself recompute power votes. (`K/iris_power.c:49–57,85–94`; `K/iris_vb2.c:52–81`; `K/iris_utils.c:175–191`; `K/iris_vidc.c:42–74,209,382`.)

The inherited SM8250 core limits also differ from Lahaina’s documented stock limits: Iris uses 138240 MB/frame and 7,776,000 MB/s, while Lahaina lists 173056 and 7,833,600. These are **driver admission limits, not measured concurrency guarantees**. (`K/iris_platform_vpu2.c:121–122`; `S/msm_vidc_platform.c:1184–1197`.)

**Compliance needs a fresh run, not additional speculative buffer fixes.** C logged an invalid `plat:` prefix, zero colorspace, `have_source_change`, and allocation/export failures after firmware had become unresponsive. Iris reports that prefix and can return DEFAULT colorspace both initially and after sequence parsing. (`C/compl-dec.txt:22,65,74–82,94–103`; `W/test-results/2026-10-02-video-iris-k115-ram-trials.md:13,18–20`; `K/iris_vidc.c:546–564`; `K/iris_vdec.c:29–54`; `K/iris_hfi_gen1_response.c:122–145`.)

The SOURCE_CHANGE failure is consistent with a compliance classification cascade: QUERYCAP validation returns before setting the M2M classification, and the later event test rejects source-change support for a non-M2M output node. That mechanism is visible in [v4l2-compliance.cpp:619–641](https://github.com/gjasny/v4l-utils/blob/v4l-utils-1.32.0/utils/v4l2-compliance/v4l2-compliance.cpp#L619-L641) and [v4l2-test-controls.cpp:1149–1150](https://github.com/gjasny/v4l-utils/blob/v4l-utils-1.32.0/utils/v4l2-compliance/v4l2-test-controls.cpp#L1149-L1150). Fixing QUERYCAP and rerunning the installed binary is the confirming test.

Patch 0164 already provides the prefix and colorspace fallback changes. Its resolution-based colorspace is a fallback policy; valid caller or decoded VUI values should remain authoritative. (`W/patches/linux-7.2.7/0164-media-iris-ROG5-v4l2-compliance-bus_info-prefix-and-colorspace.patch:38–64,85–105,149–169`.)

Browser compatibility still has separate codec boundaries: VP9 currently fails with firmware messages about unknown CP mode and rejected internal buffers, while gen1 sequence parsing explicitly rejects nonzero bit depth. Thus “smooth 4K60” qualification should initially mean **progressive 8-bit H.264/HEVC**, not Main10 or general browser video acceleration. (`D/journal-trial-boot.txt:2418–2424`; `K/iris_hfi_gen1_response.c:169–173`; `K/iris_hfi_gen1_command.c:925–935`.)

The following changes are ordered by expected user-visible benefit, with risk stated separately. **All tests below are prospective.** The same-file-descriptor ioctl tests require a small test harness; a player that closes and reopens the decoder can mask the lifecycle defects.

1. **Correct gen1 minimum/actual buffer counts — high benefit for 4K and concurrency; medium risk.**  
   In `iris_hfi_gen1_set_num_bufs()`, replace the hardcoded count assignments with:

   ```diff
   INPUT:
   - min = actual = VIDEO_MAX_FRAME
   + min = buffers[BUF_INPUT].min_count
   + actual = input_vb2_queue->num_buffers

   split OUTPUT:
   - min = actual = VIDEO_MAX_FRAME
   + min = actual = iris_vpu_buf_count(inst, BUF_DPB)

   split OUTPUT2:
   - min = actual = iris_vpu_buf_count(inst, BUF_DPB)
   + min = buffers[BUF_OUTPUT].min_count
   + actual = capture_vb2_queue->num_buffers
   ```

   Gate each property on its queue being allocated; validate `actual >= min`. Refresh counts after initial source change and DRC, before resuming with the new resources. Preserve the nonsplit OUTPUT rule using capture minimum/actual. (`K/iris_hfi_gen1_command.c:979–1024`; `S/msm_vdec.c:1095–1114`.)  
   **Confirm on device:** on one decoder fd, obtain the firmware minimum, allocate CAPTURE at minimum, minimum+4, and minimum+8 in separate runs; repeat using CREATE_BUFS to add four. Decode 600-frame H.264 and HEVC 4K60 clips with B frames. Trace every count property and DPB allocation. Pass only if advertised actual counts equal allocated counts, all 600 frames match software hashes, and every queued client buffer completes once.

2. **Use one effective decode rate for clocks/BW; fix rounded thresholds and vote errors — highest direct 4K60 lead; low-to-medium risk.**  
   Add a nominal/effective decode-rate field distinct from startup boost. Replace the submission-count estimator with a bounded timestamp-cadence estimator that handles reordered timestamps and resets on seek/DRC; use an explicit conservative unknown-rate fallback. Change `vote_data->fps = DEFAULT_FPS` to that effective rate, and express table thresholds as `DIV_ROUND_UP(w,16) * DIV_ROUND_UP(h,16) * fps`. Propagate `iris_scale_power()` errors from decoder QBUF/start/deferred paths. Commit cached ICC bandwidth only after a successful interconnect call. (`K/iris_vdec.c:448–466`; `K/iris_power.c:23,71`; `K/iris_platform_sm8250.h:9–14`; `K/iris_vb2.c:173`; `K/iris_buffer.c:868`; `K/iris_resources.c:38–45`.)  
   **Confirm on device:** run H.264/HEVC at 1080p30/60, 3840×2160p30/60 and 4096×2160p60. Record effective fps, requested/selected OPP and applied ICC vote. Run each fixture both unpaced and paced; pause for two seconds and resume. Rates must remain media rates rather than burst rates, and bandwidth must match the corrected table above. For sustained 4K60, run a 600-second fixture:

   ```sh
   timeout 660 gst-launch-1.0 -m -e \
     filesrc location=/var/tmp/t4k60.mp4 ! qtdemux ! h264parse ! \
     video/x-h264,stream-format=byte-stream,alignment=au ! \
     v4l2h264dec ! video/x-raw,format=NV12 ! \
     fakesink sync=true qos=true max-lateness=20000000
   ```

   Require 36,000 completed pictures, no firmware errors, and no sustained lateness after startup. A decode-to-null speed result alone does not pass this test.

3. **Repair flush/drain/DRC ownership and restart — high benefit for mpv seeks and adaptive playback; medium risk.**  
   Add a gen1 helper that requeues only returned, driver-owned DPBs, clearing payload, offset and flags; invoke it after ordinary flush/restart, with an explicit exclusion for DRC’s old pool. Match FLUSH_DONE by type, reject unsolicited replies without decrementing zero, and serialize indistinguishable outstanding flushes. Reset timestamp/rate/drain bookkeeping on restart. Parse sequence properties into a temporary structure with presence bits and bounds checks before committing state; unknown un-sized properties must not leave the parser repeating the same address. Handle unchanged SUFFICIENT notifications without unnecessary capture reconfiguration, while preserving the initial source-change event. (`K/iris_hfi_gen1_response.c:40–105,176–215,693–695`; `K/iris_vdec.c:469–529`; `S/msm_vidc_common.c:1671–1689,2021–2038,2077–2083`.)  
   **Confirm on device:** use one fd for 20 repetitions of each protocol:  
   **Drain:** decode 60 frames → DECODER_CMD_STOP → dequeue through LAST/EOS → confirm FLUSH_DONE in trace → DECODER_CMD_START → submit a fresh IDR and decode 300 frames, without STREAMOFF.  
   **Seek:** OUTPUT STREAMOFF while CAPTURE remains allocated → await FLUSH_ALL completion → restart OUTPUT at an IDR; alternate forward/backward GOPs.  
   **DRC:** feed independently decodable 1080p→4K→720p segments; at each event drain old CAPTURE through LAST, STREAMOFF CAPTURE, REQBUFS(0), query format/selection/minimum, allocate and restart CAPTURE while OUTPUT stays on.  
   Require correct hashes and timestamps, no duplicate completion, no unexplained DPB loss, and no duplicate live DPB tags.

4. **Land and verify the existing compliance changes — immediate compatibility benefit; low risk.**  
   Use `snprintf(..., "platform:%s", dev_name(...))`; resolve unspecified `colorspace` in initialization, TRY_FMT/S_FMT and post-VUI sequence handling.
