# GPT-6.1-Sol review: install guide (2026-09-30)

Answer to [the brief](2026-09-30-install-guide-brief.md) (codex exec, gpt-6.1-sol, reasoning high, read-only sandbox). It reviewed the first draft of [install-guide.md](../install-guide.md); line numbers refer to that draft. Absolute links were shortened to repository paths.

## Answer

**The guide is not ready to serve as an installation recipe.** Its opening warning is useful, but the first-install sequence still has bootstrap failures and insufficient protection against booting slot A. I reviewed the current working tree and relevant archived sources without modifying files or contacting any device.

Findings below are ordered by severity. **P1** means potential data loss or a fundamental installation blocker; **P2** means a broken command, unmet prerequisite, or material overstatement.

1. **P1 — RAM validation comes after the flash/reboot commands.**  
   **Guide:** Stage 10, lines 521–524; Recovery, lines 642–646.  
   The sequence flashes `boot_b`, selects B and reboots before saying “Try the wrapper in RAM first.” Recovery also promises that plain `fastboot reboot` boots B without checking the active slot. The bootloader assessment explicitly says ABL may switch to A after a wrapper failure.

   **Fix:** Put the RAM test and its acceptance checks before flashing. Immediately before every flash and recovery reboot, verify the intended serial, product, unlocked state, active slot and available slot flags. Check the flash result before advancing. Replace the unconditional recovery reboot advice with a procedure that verifies B and stops on unexpected slot state. Explain that a bundle named `safe` has not become a proven fallback merely by being built.

2. **P1 — The guide lacks the initial phone-side environment needed to reach partitioning.**  
   **Guide:** Stages 6–8, especially lines 368–412.  
   Inventory collection, firmware extraction and partitioning require Linux running on the phone, privileged partition access and—in the shown commands—SSH. The first Linux boot and USB networking instructions appear in Stage 10. “Any Linux running on the phone” leaves the central bootstrap prerequisite unresolved.

   **Fix:** Document a separately qualified RAM recovery/capture environment before Stage 7: how to build it with the owner’s key, start it, authenticate access, collect stock RAM/storage information and extract the required firmware. Until that exists, place a hard stop before unlocking or formatting, with an explicit list of unavailable prerequisites.

3. **P1 — Freshly formatted userdata lacks a directory required by the first selector boot.**  
   **Guide:** Stage 7, lines 382–392; Stage 10, lines 503–524.  
   `mkfs.ext4` does not create `/rog5`. The trial-state helper opens that directory and requires root ownership and mode `0700`; it creates only the `boot` child. See [`rog5-persistent-trial-state.c:209`](../../tools/persistent_trial_state/rog5-persistent-trial-state.c). The state stager independently requires the same directory.

   **Fix:** Add verified creation of the userdata directory structure during the qualified provisioning stage, before attempting a v2 selector boot. Include ownership, mode and filesystem-root checks.

4. **P1 — Disabling the overlay does not produce the bootstrap environment Stage 10 assumes.**  
   **Guide:** Stage 9, lines 475–477; Stage 10, lines 535–540.  
   `PERSISTENT_ROOT_OVERLAY=0` still installs `rog5-persistent-state.service`, which attempts to mount an already-existing state image. SSH identity readiness depends on that service. See [`persistent-root-init:2766`](../../initramfs/persistent-root-init) and [`persistent-service-state:350`](../../initramfs/persistent-service-state). Without `/persist`, normal readiness and trial commitment cannot complete; the next boot can select the fallback before provisioning is finished.

   **Fix:** Define and rehearse a dedicated bootstrap mode with suitable temporary SSH identity and service dependencies, or provision `/persist` from the earlier RAM environment. Specify the expected selector state throughout this transition.

5. **P1 — A generated device profile does not cover all fresh-root boot requirements.**  
   **Guide:** Stage 5, lines 309–327; Stage 8, lines 440–441.  
   The init still pins the reference `/etc/ld.so.cache` to exactly 20,207 bytes and a fixed hash outside the profile. See [`persistent-root-init:2335`](../../initramfs/persistent-root-init). It also requires a specific root-shadow shape and absent lower `/etc/.updated` and `/var/.updated` files. The builder locks root but does not explicitly normalize or validate these requirements.

   **Fix:** Make the remaining root-dependent identities part of the generated contract, normalize required account/marker state before sealing, and validate the complete fresh root against the actual init/attestor predicates before permitting a flash.

6. **P1 — Adding bundles after sealing invalidates the recorded tree seal.**  
   **Guide:** Stage 10, lines 506–515.  
   `--steps boot,image` changes `/boot/rog5-linux` after the seal was generated. The sealing tool excludes only `.rog5-persistent-seal`, so the boot files and their directory metadata are covered by the tree hash. See [`persistent-root-tool.py:194`](../../scripts/host/persistent-root-tool.py) and [`rog5-build-rootfs:373`](../../scripts/host/rog5-build-rootfs). Keeping the UUID and seal-file bytes unchanged does not keep the seal truthful. Boot currently does not recompute the complete tree, which can hide this mismatch.

   **Fix:** Define an explicit seal boundary excluding mutable signed boot storage, then verify that boundary after inserting bundles. Simply resealing everything creates a circular dependency: the signed bundle contains the profile that pins the seal.

7. **P1 — The destructive partitioning summary omits essential safeguards and backs up too late.**  
   **Guide:** Stage 7, lines 379–397.  
   The displayed order formats userdata before capturing GPT backups. The archived executor captures and obtains host acknowledgement of backups before mutation. The guide also presents `/dev/sda23` directly despite historical evidence that UFS names can change.

   **Fix:** Put verified, durable backups and exact LUN/GPT identity checks before the first destructive operation. Describe preservation of p1–p22, p23 start/GUID/type/attributes and both GPT copies. Move the bare commands into a clearly historical reference until a per-device executor is qualified. Retain the existing “Do not run them as they are” warning.

8. **P2 — The “four missing pieces” and rehearsal claims are incomplete.**  
   **Guide:** Opening, lines 11–31; Step inventory, lines 684–695.  
   Other missing inputs include the display-firmware kit, V9 base DTB, ASUS wrapper-kernel builder, allocated-RAW sparse converter and retained trial-state executable plus `SHA256SUMS`. Those helper artifacts are not tracked in Git. The recovery builder itself needs additional pinned bases, packages and native tools; the bundle ramdisk base supplies more than ADSP firmware. Also, `docs/fresh-install-rehearsal.md` is absent in the reviewed tree.

   **Fix:** Replace the four-item summary with a complete dependency inventory, including acquisition/build instructions and qualification status. Until the report exists, remove the completed-rehearsal claim. Replace “Stages 0–6 work today” with stage-specific limits: unlocking is unresolved, and Stage 6 partly depends on later phone access.

9. **P2 — Stage 8 describes a p24 prerequisite the current tool intentionally avoids.**  
   **Guide:** Lines 420–422.  
   The guide says `make` requires p24 to contain the matching root filesystem. The tool explicitly accepts an empty p24, taking its expected root UUID from `root-identity.env`; see [`rog5-device-profile:385`](../../scripts/host/rog5-device-profile).

   **Fix:** State the actual sequence: build the root identity, partition, recollect storage inventory with p24 empty, generate the profile, build bundles, insert them into the image, then flash. Preserve a separate **pre-install bootloader RAM capture** for Stage 9; a later mainline inventory reports the bundle’s map.

10. **P2 — The state-staging command is unarmed, and its power prerequisite is understated.**  
    **Guide:** Stage 10, lines 535–540.  
    `stage-persistent-service-state.sh stage` requires `ALLOW_ROG5_SERVICE_STATE_STAGE=1`; see [`stage-persistent-service-state.sh:198`](../../scripts/device/stage-persistent-service-state.sh). Its voltage floor is **8.4 V**, alongside external power and thermal checks, so the general “above 50%” warning is insufficient. The overlay stager requires boot ID and bundle identity even for `preflight`.

    **Fix:** Give complete separate preflight/stage commands with their required environments and expected PASS records. Document the actual power gates and how to satisfy them without bypassing checks.

11. **P2 — The prescribed Git workflow prevents the final install.**  
    **Guide:** Stage 9, lines 465–472; Stage 10, lines 545–550.  
    Users edit tracked inputs, register a DTB and build bundles, which modify tracked registries/docs. `--stage` then refuses any dirty repository; see [`install-default-kernel.py:227`](../../scripts/host/install-default-kernel.py). Bundle construction uses `git archive HEAD`, excluding uncommitted source changes. Moreover, rerunning “the same command with `--stage`” fails if it reuses the preflight evidence directory.

    **Fix:** Document commits before source-dependent builds and before staging, while keeping keys, credentials and private profiles outside Git. Support local input/registry copies explicitly. Use distinct evidence directories for preflight and staging, and include the existing prohibition on retrying a failed or ambiguous stage operation.

12. **P2 — The DTB output cannot be registered as shown.**  
    **Guide:** Stage 9, lines 449–466.  
    The composer does not create `~/rog5-dtb`. The memory-adjusted output is called `board-mine.dtb`, while `add-dtb` requires exactly `<registry-root>/<directory>/board.dtb`; see [`rog5-bundle-registry.py:342`](../../scripts/host/rog5-bundle-registry.py).

    **Fix:** Create the output directories, compose to an intermediate file, write the adjusted result as `board.dtb` under the registry root, show the complete `add-dtb --features …` invocation, and use the ID it prints instead of assuming `d10`. Quote the hexadecimal `memory_reg` value instead of presenting it as shell angle-bracket syntax.

13. **P2 — USB networking and strict SSH tooling are not fully configured.**  
    **Guide:** Stage 10, lines 527–533; kernel-update advice, lines 636–638.  
    The package lists omit host NetworkManager and SSH-client prerequisites. The created connection is named `rog5-usb`, whereas the RAM-trial tool expects named profiles `rog5-standalone-shared` and `rog5-fallback-usb-ssh`. It also defaults to reference-host USB topology, interface and credential paths; see [`production-ram-trial.py:47`](../../scripts/host/production-ram-trial.py). The default installer shares its strict SSH implementation.

    **Fix:** Explain interface discovery and connection activation, configure the documented tool profiles/environment overrides, supply the matching SSH private key, and establish trusted `known_hosts` entries using the tool’s host alias. Cover transient bootstrap host keys versus the persistent identity. Do not suggest disabling host-key checks.

14. **P2 — Variant handling is useful tooling, but broader compatibility is overstated.**  
    **Guide:** Variants, lines 76–112.  
    The overlay formulas match `overlay_limits()`, including their MiB rounding. However, installation, health commitment and updates still assume `sda`/`sda23`/`sda24`; see [`install-default-kernel-on-target.sh:213`](../../scripts/device/install-default-kernel-on-target.sh), `production-trial-commit:72` and `rog5-update:605`. The storage profile does not remove those assumptions.

    The statement that `rog5-sea-retire` retires “any page” is also too strong: it handles particular user-mode instruction-fetch aborts, attempts bounded block retirement, leaves unmovable pages, and acts after the process receives SIGBUS.

    **Fix:** Describe 8/16/18 GB and 128/512 GB units as unqualified bring-up targets. Resolve UFS devices consistently across all consumers, or explicitly enforce the supported enumeration. Require a genuine bootloader RAM capture and per-variant validation of reservations and board differences. Present page retirement as a bounded mitigation.

15. **P2 — Firmware provenance and hash-check claims do not match every recipe.**  
    **Guide:** What you need, lines 59–61; Stage 6, lines 335–352.  
    The sensor installer verifies its source archive and vendor filesystem label, but does not hash every extracted sensor/DSP file against WW33. CDSP fetching additionally requires the exact reference display-kit manifest, so an owner-generated kit is not automatically accepted; see [`fetch-vendor-cdsp-firmware.py:56`](../../scripts/host/fetch-vendor-cdsp-firmware.py).

    The guide explicitly obtains GMU and Bluetooth firmware from `linux-firmware`, conflicting with the brief’s strict **own-phone-only firmware** constraint.

    **Fix:** State the actual checks per installer and validate the relevant partition metadata/extent. Generalize the CDSP base-kit input safely or label the script reference-kit-only. Under the stated constraint, provide own-phone acquisition for those firmware files or identify them as unresolved dependencies.

16. **P2 — Host and target prerequisites are incomplete.**  
    **Guide:** Stage 0; Stage 11 custom packages; Stage 12.  
    Arch’s host list lacks explicit `kmod` and schema-build prerequisites such as SWIG. Debian’s list lacks explicit `zlib1g-dev`, needed by the verifier’s `-lz` build, and the OpenSSL executable. Namespace setup checks only `/etc/subuid`, omitting subordinate GIDs and an actual capability check. On the phone, the FEX installer requires `xxhsum`; see [`steam-fex-rootfs-install:51`](../../scripts/device/steam-fex-rootfs-install). Deferred package instructions assume `sudo` access that the builder never configures.

    **Fix:** Publish complete host prerequisites and a namespace/emulation preflight. Explicitly install `xxhash` before FEX setup. Build custom packages as `phone`, then install them through the already-established root SSH session, with dependency installation documented.

17. **P2 — Recovery and verification claims need narrower guarantees.**  
    **Guide:** Warnings, lines 134–137; Updates/recovery, lines 627–650.  
    “You can brick nothing that is signed” is unnecessarily reassuring. The stock-A warning is correctly prominent, but calling A a charging/rescue route needs a direct reminder that normally booting it destroys Linux userdata. Automatic update rollback remains subject to validation/refusal conditions; current status says a real rollback is still untested.

    **Fix:** State that the prescribed workflow preserves signed early firmware while boot failure and data loss remain possible. Keep stock restoration separate, explicitly destructive and untested. Add acceptance checks after each stage: filesystem/GPT identity, flashed-image verification, bundle identity, readiness, storage write scope, persistent SSH identity, primary commitment and a demonstrated fallback boot. Qualify rollback claims against the current evidence.

The signing-key location and the warning against running archived partitioning tools are sound. Keep those protections, and explicitly mark inventories, `getvar all` output, GPT backups and personalized root images as private artifacts requiring redaction before publication.
## Disposition

The guide was rewritten; the code changes are in the same branch.

1. **Fixed (guide).** Stage 10 tries the wrapper in RAM before any flash,
   checks product, unlock state and the active slot before each fastboot
   step and before `fastboot reboot`, and says a `safe` bundle is only a
   candidate until it has booted. The recovery section stops on slot `a`.
2. **Fixed (guide).** A "pre-install environment" is listed as missing; the
   opening says not to unlock or erase a phone for this project until the
   missing pieces exist; Stages 6-10 are marked as the reference record.
3. **Fixed (guide).** Stage 7 creates `/rog5` (root, 0700) after formatting.
4. **Documented as missing.** No bootstrap boot exists; `/persist` is created
   in the pre-install environment (Stage 7 step 5).
5. **Fixed (code).** The lower `ld.so.cache` pin moved into the device
   profile (`rog5_root_ld_cache_bytes/sha256`, `root-identity.env`).
   `rog5-build-rootfs` now runs `ldconfig`, removes `/etc/.updated` and
   `/var/.updated`, and checks the root shadow line, `/sbin/init`, the sshd
   drop-in hash, `authorized_keys`, host keys, the keyring and machine-id
   before sealing.
6. **Fixed (code).** The seal leaves out `boot/rog5-linux` (signed boot
   storage that `install-default-kernel.py` rewrites and that the bundles,
   which pin the seal, live in); `persistent-root-tool.py` documents the
   boundary. Adding bundles no longer changes the sealed tree.
7. **Fixed (guide).** Backups and identity checks come first; the commands
   are a historical record, with the warning kept.
8. **Fixed (guide).** The opening lists eleven missing pieces, including the
   display kit, the V9 DTB, the ASUS kernel builder, the sparse converter and
   the trial-state helper. The rehearsal report is committed with the guide.
9. **Fixed (guide).** Stage 8 states the order (root identity, partition,
   inventory with p24 empty, profile, bundles, image, flash) and the need for
   a bootloader RAM capture.
10. **Fixed (guide).** Both stagers are shown with `preflight` and their
    arming variables; the 8.4 V, charging and temperature gates are stated.
11. **Fixed (guide).** Commit on your own branch before bundle builds; keys
    and profiles outside Git; separate evidence directories; no retry of a
    failed `--stage`.
12. **Fixed (guide).** The DTB commands create their directories, write the
    final `board.dtb` under the registry root, show `add-dtb --features` and
    use the printed id; the hex is quoted.
13. **Fixed (guide + code).** The NetworkManager profiles the RAM-trial tool
    expects are given with their addresses; `production-ram-trial.py` takes
    the interface, SSH key and `known_hosts` from the environment or
    `~/.config/rog5/`; host-key handling is described.
14. **Fixed (guide), open (code).** Variants are "unqualified bring-up
    targets"; the remaining `sda` assumptions are listed; `rog5-sea-retire`
    is described as a bounded mitigation.
15. **Fixed (guide).** Per-installer checks are stated; the CDSP script is
    marked reference-only; redistributable firmware (A660 GMU, Bluetooth,
    regulatory database) comes from Arch's packages, the rest from the phone,
    never from this project.
16. **Fixed.** Host lists gained kmod, SWIG, zlib, OpenSSL, OpenSSH,
    NetworkManager and firewalld; the user-namespace check covers
    `/etc/subgid` and a real `unshare`; `xxhash` is in the package list;
    deferred package builds use the root SSH session instead of `sudo`.
17. **Fixed (guide).** The warnings name what is and is not protected; the
    slot-A warning says booting it formats the Linux data; the rollback claim
    says the restore has passed fault injection but has not been needed for
    real.
