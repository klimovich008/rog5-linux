## 1. Clock requirement and hypothesis ranking

**The code supports a mixer clock requirement of approximately `pclk / num_lm`; it does not establish a full-pixel-rate bottleneck after MERGE_3D. No single hypothesis explains every supplied observation.**

## 2. Correct bound and 0099 vote

**Keep 0114 only as a temporary conservative policy while retaining the current full-rate 0099 vote. Do not describe it as the established SM8350 hardware limit.**

For the specified uncompressed DP path, use one shared mode-floor formula:

```text
M = mixers actually selected for this path
mode_floor = ceil(pclk_Hz × 105 / (100 × M))
core_vote  = max(mode_floor, adjusted per-SSPP requirements)
```

`mode_valid` checks the same `mode_floor` against maximum core clock. Atomic checking must additionally validate the actual SSPP/scaling requirements and reject an excessive vote instead of silently clamping it.

For r98’s single-interface uncompressed topology, the shared mixer-selection helper must reproduce its `hdisplay > 1080` rule; `has_3d_merge` alone is insufficient. [dpu_crtc.c:1402](/home/deck/.local/state/rog5-kernel-7.2.7-build-r98/source/drivers/gpu/drm/msm/disp/dpu1/dpu_crtc.c:1402)

| Pixel clock | Two-LM mode floor |
|---:|---:|
| 148.5 MHz | 77.9625 MHz |
| 266.5 MHz | 139.9125 MHz |
| 453 MHz | 237.825 MHz |
| 469 MHz | 246.225 MHz |

Those are **mode floors, not promised final votes**. For an unsplit 1080p SSPP, r98’s active-pixel estimate can still produce approximately 136 MHz. For the supplied 3840×1080@100 EDID timing, the full-width SSPP estimate is approximately 456.8 MHz after adjustment. Thus replacing 0099’s floor with `pclk/2` need not substantially lower every actual vote.

Also divide the existing mode-derived active-pixel term by `M`; otherwise it can defeat the corrected floor. Preserve the separate per-SSPP maximum.

Before relying on this formula, correct the state/timing issue below. The current performance check validates bandwidth, whereas rate application clamps the clock. ## 3. “Latched”, recovery and r180

**The IRQ-idle mechanism is confirmed. Its occurrence in a particular captured failure remains an inference until matched to a trace.**

The complete chain is:

1. FRAME_DONE schedules idle work.
2. Video-mode ENTER_IDLE disables encoder IRQs without releasing the scanout resources.
3. Physical video IRQ disable unregisters UNDERRUN and drops its VSYNC reference.
4. Unregistering disables the hardware IRQ; the debugfs IRQ count increments only when a registered callback executes.

Consequently, both counters can freeze while INTF continues scanning blue. An additional VSYNC reference can keep VSYNC observable even after UNDERRUN is disabled. A subsequent ordinary kickoff re-enables the video IRQs without needing a modeset. [dpu_encoder.c:986](/home/deck/.local/state/rog5-kernel-7.2.7-build-r98/source/drivers/gpu/drm/msm/disp/dpu1/dpu_encoder.c:986), [dpu_encoder.c:1078](/home/deck/.local/state/rog5-kernel-7.2.7-build-r98/source/drivers/gpu/drm/msm/disp/dpu1/dpu_encoder.c:1078), [dpu_encoder_phys_vid.c:689](/home/deck/.local/state/rog5-kernel-7.2.7-build-r98/source/drivers/gpu/drm/msm/disp/dpu1/dpu_encoder_phys_vid.c:689), [dpu_hw_interrupts.c:317](/home/deck/.local/state/rog5-kernel-7.2.7-build-r98/source/drivers/gpu/drm/msm/disp/dpu1/dpu_hw_interrupts.c:317), [dpu_hw_interrupts.c:713](/home/deck/.local/state/rog5-kernel-7.2.7-build-r98/source/drivers/gpu/drm/msm/disp/dpu1/dpu_hw_interrupts.c:713), [dpu_encoder.c:948](/home/deck/.local/state/rog5-kernel-7.2.7-build-r98/source/drivers/gpu/drm/msm/disp/dpu1/dpu_encoder.c:948)

- Stops timing and waits for disable to latch.
- Resets CTL, mixer routing, PP binding/dither and MERGE_3D configuration.

## 4. Minimal opt-in watchdog proposal

Count **bad VSYNC intervals**, rather than raw underrun IRQs. After N consecutive bad intervals, request maximum core clock and maximum catalog bandwidth. Start a new N-frame observation after that vote succeeds; continued underruns produce BAD plus hotplug.

The proposal below uses the existing virtual callbacks, so neither `dpu_encoder_phys_vid.c` nor `dp_display.c` needs modification. A small perf hook is necessary to preserve the boost across subsequent commits and avoid changing the user’s global `perf_mode`.

It keeps IRQ observation active until disable, clears the boost on disable, and limits hotplug notifications across recovery modesets. Default is off; set `msm.dpu_dp_underrun_frames=8` before the next enable.

**Validation:** generated entirely in memory; `git apply --check` passed against r98. Not compiled or tested on hardware. If a commit fails to complete, the worker logs and stops that recovery attempt. Loss of VSYNC itself needs a separate timeout watchdog.

BAD/hotplug is the DRM recovery notification contract, but DRM explicitly warns that userspace support cannot be assumed. The inspected wlroots source forces rediscovery/modesetting on BAD; the installed wlroots version was not verified. **Mutter 50’s BAD recovery behaviour remains unverified.** [DRM contract:2806](/home/deck/.local/state/rog5-kernel-7.2.7-build-r98/source/drivers/gpu/drm/drm_connector.c:2806), [wlroots handling](https://github.com/swaywm/wlroots/blob/master/backend/drm/drm.c#L1175)

## 5. Two experiments using existing knobs

**Do not read any `dri/*/DP-*` debugfs files.** Use kernel traces, core_perf/clock/ICC observations and the visible picture. Keep desktop animation running when comparing IRQ rates.

**Experiment A — isolate bit depth at a known-working timing.**

Use native DP at 3840×1080@60, fixed 460 MHz and 15.5 GB/s. Set `msm.dp_max_bpc` to **6 → 8 → 6**, with an actual `gdctl` away-and-back modeset after each change. Confirm the selected bpp in kernel logging.

| Hypothesis | Prediction |
|---|---|
| H1 | All depths work: pixel clock and core margin are unchanged. |
| H2, generally broken RGB6 | Both six-bit trials fail; eight-bit trial works. |
| H2, high-fill TU-specific | Low-fill RGB6 can work; that does not exonerate RGB6 near saturation. Optionally compare the existing 285-MHz timing at RGB10, approximately 99% fill. |
| H3 | Similar behaviour across depths when framebuffer format and fetch votes remain constant. A failure following enable history rather than depth favours startup state. |

**Experiment B — boost a failing stream without re-enabling its DP encoder.**

Reproduce the r180-like 1080p failure at 200 MHz/4 GB/s. First raise bandwidth alone to 15.5 GB/s; then raise clock to 460 MHz. Observe whether either step clears blue. Finally perform the known DP away-and-back modeset at those same maximum votes.

**Knob writes alone do not guarantee application:** `perf_mode` only changes a field, and perf updates are conditional. Force application by enabling the DSI CRTC through `gdctl` while retaining the DP configuration; accept the comparison only if traces confirm the new votes took effect **without a DP disable/enable**. If the compositor also modesets DP, this arm cannot answer the latch question. [perf_mode write:491](/home/deck/.local/state/rog5-kernel-7.2.7-build-r98/source/drivers/gpu/drm/msm/disp/dpu1/dpu_core_perf.c:491), [conditional updates:425](/home/deck/.local/state/rog5-kernel-7.2.7-build-r98/source/drivers/gpu/drm/msm/disp/dpu1/dpu_core_perf.c:425)

| Observation | Interpretation |
|---|---|
| Bandwidth increase clears blue | Supports continuous H3 starvation. |
| Only clock increase clears blue | Supports a continuous rate/latency limit; does not uniquely prove H1. |
| Maximum votes fail, subsequent DP modeset clears | Supports startup/programmed state or a real stuck pipeline over a solely steady-state rate limit. |
| Animation resumes underrun counting without clearing blue | Supports IRQ-idle masking of a continuing failure. |
| RGB8 1080p still fails | General RGB6 failure cannot explain this case. |

These experiments cannot establish post-merge throughput from a clock sweep alone while an unsplit SSPP term remains a competing limit.
