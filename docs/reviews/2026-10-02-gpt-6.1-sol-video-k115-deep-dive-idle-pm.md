**The stock contract: two different kinds of collapse**

The stock Lahaina configuration enables software power collapse with a **1,500 ms delay**, while separately requesting firmware codec-plane power control. Firmware residence and host power collapse are independent: Lahaina also sets `never-unload-fw=1`. (`S/msm_vidc_platform.c:1162–1173,1215–1217`; `S/hfi_common.c:1912–1919`.)

Its sequence is:

```text
command / response activity
    → restart host idle timer
    → firmware may collapse the codec plane between frames
    → after inactivity: host PC_PREP
    → PC_READY + WFI
    → SCM video SUSPEND
    → controller/fabric shutdown
    → release clocks, regulators and bus votes
```

Commands restart the delayed work at `S/hfi_common.c:1257–1265`; response processing does likewise at `:2875–2882`. The worker serializes collapse with the HFI device lock, retries failed preparation, and eventually reports fatal failure after repeated skips. (`S/hfi_common.c:2516–2567`; `S/hfi_common.h:46`.)

**PC_PREP is permission for host shutdown, not the command that enables interframe collapse.** Stock first tests controller `PC_READY`; otherwise it requires idle and WFI, sends PC_PREP, and waits for WFI plus PC_READY. Only then does common code perform SCM suspend and power-off. (`S/hfi_iris2.c:255–306`; `S/hfi_common.c:2497–2513,2571–2603,3847–3874`.)

The GDSC warning has a precise meaning:

> The host’s software enable/reference does not force the codec plane on after ownership transfers to hardware.

Stock explicitly warns that NORMAL→FAST can turn the GDSC off without a hardware vote. The downstream regulator implements FAST by setting `HW_CONTROL`; NORMAL clears it and waits for power-on before software uses the domain. Mainline’s GDSC implementation expresses the same contract. ([stock warning:3991](/home/deck/Projects/rog-phone-linux-migration/kernel-src/msm-5.4/techpack/video/msm/vidc/hfi_common.c:3991); downstream `drivers/clk/qcom/gdsc-regulator.c:584–632`; `K/drivers/clk/qcom/gdsc.c:392–416`.)

There is also an essential **controller/codec distinction**. Stock supplies `iris-ctl` from MVS0C and `vcodec` from MVS0; only MVS0 advertises hardware triggering. Mainline similarly gives MVS0C ordinary software control and MVS0 `HW_CTRL_TRIGGER`. Consequently, “the codec GDSC collapsed, therefore ordinary controller IRQ/HFI access necessarily hangs” is not supported by this design. (Downstream `arch/arm64/boot/dts/vendor/qcom/lahaina-vidc.dtsi:15–24`; `lahaina.dtsi:2735–2757`; [mainline domains:432](/home/deck/.local/state/rog5-kernel-7.2.7-build-r115/source/drivers/clk/qcom/videocc-sm8350.c:432).)

**B: revised mechanism assessment**

**Established:** `power/control=on` disables host runtime suspension; it does not change the HFI codec-plane property. Generic sysfs calls `pm_runtime_forbid()`, which clears `runtime_auto`, adds a usage reference and resumes the device. Iris’s firmware-collapse property is sent independently. (`K/drivers/base/power/sysfs.c:107–118`; `K/drivers/base/power/runtime.c:1664–1675`; `I/iris_hfi_gen1_command.c:107–130`.)

**Inference:** pinning runtime PM leaves Iris outside the normal stock inactivity sequence because its host PC_PREP/SCM shutdown is reached through the runtime-suspend callback. However, stock deliberately supports hardware-controlled codec collapse while its controller remains powered. Therefore pinning is a materially different experiment, **not proof of an intrinsically invalid hardware state**. (`I/iris_probe.c:336–352`; `I/iris_hfi_common.c:125–142`; `S/hfi_common.c:1257–1265,3991–3997`; `S/hfi_iris2.c:255–306`.)

**Most likely classification of the actual B failure:** an encoder-triggered bring-up failure, potentially involving firmware execution, DMA/fabric access or a startup power transition. B and D both end at encoder activation despite different runtime-PM policies. The evidence cannot select a particular bus transaction, vote loss or deadlock. (`B/kmsg.log:395–397`; `D/kmsg.log:417–421`.)

If a separate decoder-only pinned-idle failure exists, its likely power-related mechanism would be **an uncoordinated resource transition or access during firmware-owned collapse**. Neither the supplied B endpoint nor its clock counts proves that event happened. An IRQ alone is insufficient evidence: Iris’s interrupt status and acknowledgment accesses correspond to the controller-side accesses used by stock. (`I/iris_vpu_common.c:110–123`; `S/hfi_iris2.c:360–380`; `B/phone-logs/k115-B-dec1.log:20–21`.)

**C: strongest hypothesis and its limits**

C’s packet layout is consistent with stock: SYS_SET_PROPERTY, one property, `HFI_PROPERTY_SYS_CODEC_POWER_PLANE_CTRL`, scalar enable value zero. A malformed property identifier/layout is therefore a weak explanation. (`I/iris_hfi_gen1_command.c:107–130`; `I/iris_hfi_gen1_defines.h:84`; `S/hfi_packetization.c:308–325`.)

The concrete mismatch is that Iris:

```text
powers domains and clocks
    → loads/authenticates firmware
    → boots firmware
    → unconditionally hands codec GDSC to hardware
    → sends firmware codec-plane control = 0
```

It repeats the hardware handoff and property transmission on runtime resume. (`I/iris_core.c:324–340`; `I/iris_hfi_common.c:155–173`; `I/iris_vpu_common.c:328–335`.)

**Most likely mechanism — inference, not established fact:** disabling firmware codec-plane management removes or fails to establish the hardware request needed to keep/reawaken MVS0, while Linux still leaves MVS0 under hardware control. Codec execution then waits indefinitely on an unavailable plane; the controller and host can remain alive, matching C’s heartbeats and silent HFI failure. This follows the documented vote hazard, but C has no surviving physical-domain snapshot or last-consumed-command trace proving it. (`S/hfi_common.c:3991–3997`; `K/drivers/clk/qcom/gdsc.c:408–416`; `C/phone-logs/dmesg.txt:1126–1158`.)

**Alternative:** this OEM firmware’s zero-property handling itself stalls even with the plane physically powered. A fresh boot with **software-owned MVS0 plus firmware property zero** distinguishes that alternative: success supports the ownership hypothesis; continued failure with verified MVS0-on state moves suspicion toward firmware policy handling. The current firmware-only switch cannot make that distinction. (`I/iris_hfi_gen1_command.c:125`; `I/iris_core.c:336`; `K/drivers/clk/qcom/gdsc.c:408–414`.)

**Required host invariants for safe idle**

These are proposed design requirements, grounded in the stock sequence—not a claim that five minutes proves arbitrary OEM firmware hang-free.

| State | Host requirements |
|---|---|
| Firmware owns interframe collapse | Retain controller domain, controller/interface clocks, required OPP/supply and configuration/memory-path votes. Do not interpret software clock counts or PM references as physical codec-plane power. |
| Controller HFI/IRQ access | Serialize against host shutdown and retain a controller-access reference through the access. Permit only accesses whose domain remains powered. |
| Codec/datapath MMIO | Do not access while hardware may collapse MVS0. If access is necessary, acquire software ownership and wait for physical power-on before touching it. |
| Host idle shutdown | PC_PREP/PC_READY → SCM suspend → fabric/controller quiescence → checked ownership/resource release. Never pull resources merely because queues appear empty. |
| Failed transition | Retain memory and necessary resources, record an uncertain/error state, and refuse further submissions. Free firmware-visible memory only after acknowledged release or accepted firmware shutdown. |

Basis: `S/hfi_common.c:369–400,2571–2603,3847–3874`; `S/hfi_iris2.c:176–306`; `K/drivers/clk/qcom/gdsc.c:408–414`; `I/iris_core.c:100–120`; `I/iris_vidc.c:263–285`.

**Optional always-on mode:** keep MVS0 software-owned and powered, send firmware property zero, retain controller/codec clocks and votes, and disable host idle shutdown for that mode. Select it **before firmware boot**, keep it immutable for the binding, and apply the same policy on every resume. Changing only the property—or changing it asynchronously after hardware handoff—is insufficient. (`I/iris_core.c:324–340`; `I/iris_hfi_common.c:155–173`; `I/iris_hfi_gen1_command.c:125`; `K/drivers/clk/qcom/gdsc.c:392–416`.)

**Making `power/control=on` harmless:** the smallest defensible interim implementation is to reject the write **before** generic PM adds its reference in normal hardware-collapse mode, and allow it in the coordinated software-owned mode. This is a conservative qualification restriction; B no longer proves it necessary. The existing 0163 open-time guard misses writes made after firmware initialization, including while idle. (`K/drivers/base/power/sysfs.c:107–118`; `K/drivers/base/power/runtime.c:1664–1675`; `W/patches/linux-7.2.7/0163-media-iris-ROG5-SM8350-OEM-firmware-platform-data-secure-session-EOS-power-off-gating.patch:589–600`.)

3. **Make SM8350 shutdown transactional and match stock Iris2 quiescence.**

   Split shutdown into **quiesce** and **gate** operations. Add an SM8350 controller-quiesce implementation:

   ```c
   write(X2RPMh, 3);
   write(AON_MVP_NOC_LPI_CONTROL, 1);
   poll(AON_MVP_NOC_LPI_STATUS & BIT(0));
   write(DEBUG_BRIDGE_LPI_CONTROL, 7);
   poll((DEBUG_BRIDGE_LPI_STATUS & 7) == 7);
   write(DEBUG_BRIDGE_LPI_CONTROL, 0);
   poll(DEBUG_BRIDGE_LPI_STATUS == 0);
   ```

   Remove the generic CPU-NOC `wrapper+0x5c/+0x60` handshake for this platform. Complete quiescence while controller access and votes remain available; then reacquire/check codec software ownership as required and release clocks/domains/votes.
