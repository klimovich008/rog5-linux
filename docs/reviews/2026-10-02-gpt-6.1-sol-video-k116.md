## Round 1 answer

**Two blocking encoder findings and one incomplete error-propagation fix, all in 0165.**

1. **[P1] OUTPUT-first encoder startup fails after firmware START.**  
   [iris_hfi_gen1_command.c:392](drivers/media/platform/qcom/iris/iris_hfi_gen1_command.c:392)  
   Starting raw OUTPUT first defers LOAD/START and moves the instance to `IRIS_INST_INPUT_STREAMING`. CAPTURE’s callback subsequently sends LOAD_RESOURCES and START, then sets `IRIS_INST_SUB_LOAD_RESOURCES`. However, `iris_state.c:118` forbids that substate in INPUT_STREAMING, returning `-EINVAL`. CAPTURE STREAMON therefore fails even when firmware startup succeeds; deferred client buffers never reach firmware. The state transition needs to accommodate startup from either queue order. Compiler evaluation of the actual validator confirmed OUTPUT-first returns `-22`, while CAPTURE-first returns zero.

2. **[P1] Deferring START leaves STOP/STREAMOFF paths issuing commands before START.**  
   [iris_hfi_gen1_command.c:350](drivers/media/platform/qcom/iris/iris_hfi_gen1_command.c:350)  
   After OUTPUT-only STREAMON, firmware has received neither LOAD nor START, but:
   - OUTPUT STREAMOFF enters the firmware STOP/RELEASE sequence at `iris_hfi_gen1_command.c:461`.
   - `V4L2_ENC_CMD_STOP` remains allowed and sends the EOS ETB through `iris_venc.c:619`, bypassing the new qbuf guard.

   Thus the promised “no buffer before START” protection has a drain bypass, and aborting deferred startup can provoke invalid-state errors or timeouts. `enc_start_deferred` also remains set across STREAMOFF; if firmware accepts the premature STOP, a subsequent CAPTURE-only STREAMON can start the session without OUTPUT active. Guard these paths using firmware startup state and clear deferred-start bookkeeping on cancellation.

3. **[P2] Real property transport failures still become successful STREAMON.**  
   [iris_ctrls.c:1503](drivers/media/platform/qcom/iris/iris_ctrls.c:1503)  
   The three-error allowlist misses `-ENODATA`, returned by command submission when the HFI queue is full, and runtime-resume failures such as `-EBUSY`. These propagate through the property setter but are logged and discarded here, allowing startup with missing properties. Preserve intentional “not applicable” results while propagating transport failures. This retained failure path can affect decoding under queue pressure too.

**I found no deterministic regression in the default H.264/HEVC trial-D path.** The encoder findings require `experimental_encoder=1`. The remaining requested checks were consistent:

- SM8350 selects its new platform data; SECURE_SESSION emits the expected six words after successful SESSION_INIT and before session buffers.
- Decoder and encoder drains use real EOS allocations; encoder registration defaults off. `video_unregister_device(NULL)` safely covers remove and error paths. VP9 enumeration and validation respect `dec_fmts_size`.
- Controller register offsets and poll conditions match stock Iris2. Timeouts continue through shutdown; the returned error reaches the logging wrapper, while runtime suspend still reports success.
- UBWC layout matches stock, including its trailing word. **Both packets are 60 bytes**, despite the comment and commit message saying 64; that is a documentation error, not a packet-size mismatch.
- DMA checks preserve the base-address-plus-allocation convention with `data_offset` separate, use sufficient integer width, and accept valid boundary-ending ranges. I found no legitimate-buffer false rejection or inherent normal-decode failure from propagating `iris_scale_power()`.
- Bus-info and colorspace changes introduce no identified decode/compliance blocker. Markers add no evident Iris lock recursion. The runtime-auto guard retains its documented limitation around later sysfs writes.

All three patch payloads match the supplied HEAD against k115. No files changed and no hardware tests ran; trial-D equivalence remains unverified on-device.
