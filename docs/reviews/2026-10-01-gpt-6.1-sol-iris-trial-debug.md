Also retain a bounded trace of transmitted commands and received responses: firmware generation, session ID, packet type, instance/substate, buffer address/tag, stream ID, flags and lengths. That distinguishes failure after EOS ETB, STOP, RELEASE_RESOURCES, END, or idle power collapse. The current log cannot distinguish those boundaries.

The normal decoder stop flow is broadly reasonable:

1. With both queues streaming, OUTPUT streamoff sends `FLUSH_ALL`; CAPTURE streamoff sends `FLUSH_OUTPUT`.
2. After one queue stops, the second streamoff sends STOP, then RELEASE_RESOURCES.
3. Close sends SESSION_END.

See [iris_hfi_gen1_command.c:188](/home/deck/.local/state/rog5-kernel-7.2.7-build-r114/source/drivers/media/platform/qcom/iris/iris_hfi_gen1_command.c:188). **Do not replace CAPTURE-only streamoff with unconditional STOP:** CAPTURE reconfiguration is part of resolution-change handling.

The defective parts are failure handling and lifetime:

- STOP failure is overwritten by the following RELEASE_RESOURCES operation (`:217–227`, encoder equivalent `:241–251`).
- A completed wait returns success even when the response handler has set `IRIS_INST_ERROR`: `K/iris_utils.c:70–85`.
- RELEASE_BUFFERS waits without first reinitializing its shared completion: `K/iris_hfi_gen1_command.c:439–445`.
- The response handler completes the same `inst->completion` for several different response types: `K/iris_hfi_gen1_response.c:654–665`.
- Streamoff failure sends an unawaited END through `iris_kill_session()`, and ordinary close can send END again: `K/iris_common.c:190`, `iris_vidc.c:225`.

**Exact changes:** stop at the first failed transaction; record its response error; reinitialize before each request; match completion to the expected response type; make END idempotent. After timeout, do not let a late response satisfy the next transaction—abort/quarantine that session.

Stock uses a state machine with response-specific waits through STOP, RELEASE_RESOURCES and END, and rejects operations on invalid instances: `S/msm_vidc_common.c:3595`, `:3627`, `:4202–4218`.

**B. `1004`, and why “command 0”**

`0x1004` is **`HFI_ERR_SESSION_INVALID_SESSION_ID`**, not bad pointer (`0x1003`) or incorrect state (`0x1006`). The exact definitions are at [vidc_hfi_helper.h:42](/home/deck/Projects/rog-phone-linux-migration/kernel-src/msm-5.4/techpack/video/msm/vidc/vidc_hfi_helper.h:42).

The message’s “event id” label is misleading: it prints `event_data1`, the session error code. “command” prints `event_data2` (`K/iris_hfi_gen1_response.c:253–259`). Zero means the firmware supplied no usable offending-command identifier. It is **not evidence of HFI opcode zero or V4L2 command zero**.

The recovery sequence explains these errors:

- System error marks existing instances ERROR.
- The work item immediately deinitializes and initializes firmware again.
- Existing instances remain in `core->instances`.
- Stop/close/release paths can then transmit their old IDs to the fresh firmware.

The reload is explicit at [iris_probe.c:213](/home/deck/.local/state/rog5-kernel-7.2.7-build-r114/source/drivers/media/platform/qcom/iris/iris_probe.c:213). The log shows fatal → authentication → `1004` at [dmesg-trial-boot.txt:1119](/home/deck/.local/state/rog5-production-boot-20260923/ram-trial-main-k114-d15-261001a-2/phone-logs/dmesg-trial-boot.txt:1119).

Add a monotonically increasing firmware generation, copy it into each successfully opened HFI session, and reject **every session command** if generations differ. That check belongs under the core serialization immediately before queue submission.

Also fix event dispatch: `K/iris_hfi_gen1_response.c:627–635` chooses system-versus-session handling by instance lookup. Dispatch `HFI_EVENT_SYS_ERROR` by **event type first**. A stale session error with no matching instance must not become another system-error recovery.

`pkt:20007` is SESSION_END_DONE (`K/iris_hfi_gen1_defines.h:105`), consistent with an END acknowledgment arriving after removal; it is not itself proof of another firmware crash.

**C. Drain, LAST, and the H.264 hang**

There are two distinct problems.

**The post-crash hang has a direct explanation.** The system-error handler changes instance states but does not call `iris_vb2_queue_error()` or complete their pending waits: [iris_hfi_gen1_response.c:228](/home/deck/.local/state/rog5-kernel-7.2.7-build-r114/source/drivers/media/platform/qcom/iris/iris_hfi_gen1_response.c:228). The existing helper errors both queues at `K/iris_buffer.c:893`. Calling it wakes queue waiters; changing the private instance state alone does not.

On fatal error, notify each live instance under safe lifetime/locking:

```c
iris_inst_change_state(inst, IRIS_INST_ERROR);
iris_vb2_queue_error(inst);
complete_all(&inst->completion);
complete_all(&inst->flush_completion);
```

Then make the waiter return `-EIO` after waking if the instance is erroneous. Do not acquire `inst->lock` while holding `core->lock` without redesigning lifetime management: existing command paths acquire them in the opposite order.

**Normal gen1 drain works as follows:**

1. `V4L2_DEC_CMD_STOP` calls `session_drain()`, then sets `IRIS_INST_SUB_DRAIN` (`K/iris_vdec.c:532`).
2. It sends a zero-length compressed ETB with EOS and address `0xdeadb000` (`K/iris_hfi_gen1_command.c:453`).
3. EBD for that address is ignored (`K/iris_hfi_gen1_response.c:350`).
4. Empty EOS FBD triggers `FLUSH_OUTPUT` and sets DRAIN_LAST (`:426–436`).
5. Empty stream-1 CAPTURE buffers receive LAST (`:480–490`).
6. Buffer completion queues V4L2 EOS and marks the context stopped (`K/iris_buffer.c:978`).

Thus **STOP does not immediately generate LAST**; firmware output drives completion.

The OEM difference is substantial: stock allocates a real 4 KiB EOS buffer and supplies its DMA address and allocation length: [msm_vidc_common.c:4339](/home/deck/Projects/rog-phone-linux-migration/kernel-src/msm-5.4/techpack/video/msm/vidc/msm_vidc_common.c:4339), `:4262–4270`.

Test this exact alternative:

```c
ip_pkt.packet_buffer = lower_32_bits(inst->eos_daddr);
ip_pkt.alloc_len = SZ_4K;
ip_pkt.filled_len = 0;
ip_pkt.flags = HFI_BUFFERFLAG_EOS;
```

Allocate/map `eos_daddr` through the Iris device, track its EBD separately, and retain the allocation until firmware ownership is demonstrably released. Replace the hardcoded EBD exclusion with the tracked EOS address.

This is an **OEM compatibility experiment**, not a proven upstream bug: Qualcomm explicitly introduced the dummy address for all codecs because supported firmware accepts it. [Upstream patch](https://lkml.iu.edu/2508.3/00725.html).

Two other trace-dependent corrections:

- If this firmware returns **nonempty EOS on stream 1**, current code misses LAST because both drain completion and LAST handling require zero payload. Handle EOS on the client-output stream regardless of payload, preserving the final frame.
- If EOS arrives on internal stream 0, record drain completion but issue exactly one LAST on a client CAPTURE buffer. Never expose an internal DPB as a vb2 buffer.

The historical “missing LAST” fix is already substantially present—the old early return is absent. Blindly reapplying it will not resolve this. [Upstream fix](https://www.spinics.net/lists/linux-media/msg280551.html).

The GStreamer H.264 hangs cannot yet be assigned to drain: no captured progress establishes that they reached EOF. Test explicit framing:

```text
h264parse ! video/x-h264,stream-format=byte-stream,alignment=au !
v4l2h264dec ! video/x-raw,format=NV12 ! fakesink sync=false
```

Capture SOURCE_CHANGE, first FBD, STOP, EOS and LAST. HEVC working once establishes a working HEVC path, not a general H.264-specific hardware failure—especially after several firmware reloads.

**D. The exact vb2 violation**

The warning means **the buffer being completed was not `VB2_BUF_STATE_ACTIVE`**. It does not complain about the requested ERROR completion state. See [videobuf2-core.c:1181](/home/deck/.local/state/rog5-kernel-7.2.7-build-r114/source/drivers/media/common/videobuf2/videobuf2-core.c:1181).

There is a concrete stale-list bug:

```text
iris_vb2_buf_queue()
  adds vbuf to the m2m ready list
  iris_vdec_qbuf()/iris_venc_qbuf() fails
  calls buf_done(ERROR) without removing vbuf from that list
```

See [iris_vb2.c:332](/home/deck/.local/state/rog5-kernel-7.2.7-build-r114/source/drivers/media/platform/qcom/iris/iris_vb2.c:332). Later `iris_helper_buffers_done()` removes that stale entry and completes it again (`K/iris_utils.c:61–66`). After cancellation/dequeue, it may be ERROR, DONE or DEQUEUED. The log does not identify which.

**Fixes:**

1. Track whether `vbuf` was added to the m2m list. On qbuf failure, remove that exact entry before completing it.
2. Update Iris ownership attributes when returning buffers: clear QUEUED/DEFERRED and set BUFFER_DONE.
3. Remove gen1 stop’s blanket completion of **both** queues (`K/iris_hfi_gen1_command.c:231`, `:256`). Let the queue-specific stop callback return its remaining buffers.
4. As defensive cleanup, remove stale entries but call `buf_done()` only for ACTIVE buffers. Log the unexpected state; do not merely hide the WARN.

There is also a close-lifetime defect: [iris_vidc.c:288](/home/deck/.local/state/rog5-kernel-7.2.7-build-r114/source/drivers/media/platform/qcom/iris/iris_vidc.c:288) frees the m2m context **before SESSION_END**, while session errors and buffer responses can still use it. `v4l2_m2m_ctx_release()` actually frees that object at `drivers/media/v4l2-core/v4l2-mem2mem.c:1288`.

Reorder close to: mark closing → stop queues while context is alive → finish END or establish crash quiescence → detach response lookup and synchronize existing response users → free m2m/context/buffers. `iris_get_instance()` currently returns an unreferenced pointer after dropping the core lock (`K/iris_utils.c:88`); safe detachment needs reference/lifetime protection.

**E. What can cause a hard hang, and the containment guard**

The last authentication line proves PAS authentication completed; it does not identify where execution subsequently stopped. The four-minute reset could reflect a stalled kernel, a fabric/DMA fault, or watchdog policy. The log cannot choose among them.

The strongest source-level hazards are:

- **IRQ versus power-off:** `K/iris_vpu_common.c:232–240` removes power/clocks before `disable_irq()`. The IRQ thread unconditionally accesses VPU registers at `K/iris_hfi_common.c:107–109`.
- **Runtime-suspend deadlock:** `iris_pm_suspend()` holds `core->lock` (`K/iris_probe.c:324`) through that `disable_irq()`. An IRQ thread waiting for the same lock cannot finish. Patch 0154 addresses this in core teardown, but the runtime-suspend path still exists.
- **Failed shutdown still frees DMA:** [iris_core.c:18](/home/deck/.local/state/rog5-kernel-7.2.7-build-r114/source/drivers/media/platform/qcom/iris/iris_core.c:18) logs PAS shutdown failure, then powers off and frees HFI queues anyway.
- **LPI timeout still gates power:** controller shutdown jumps to `disable_power` after handshake failure and returns success (`K/iris_vpu_common.c:185–220`).

GDSC hardware control is present: `videocc-sm8350.c:450–455` uses `HW_CTRL_TRIGGER`; Iris enables it at `K/iris_vpu_common.c:312` and requests software mode on shutdown at `:225`. The latter return value is ignored. Fix error propagation before assuming a missing HW-control implementation.

**Proposed first-trial containment:**

- Latch `core->fatal` permanently for that boot; reject new opens/session submissions with `-EIO`.
- Remove unconditional reload from `iris_sys_error_handler()`.
- Wake/error existing queues and waits.
- Quiesce and synchronize IRQ handling **outside `core->lock`, before clocks are removed**; explicitly track IRQ ownership and actual controller power state.
- Gate all ISR/PM/MMIO entry paths on that power state.
- Preserve clocks, interconnect votes and DMA allocations if PAS shutdown or required isolation fails. Do not declare DEINIT or reuse those addresses.
- Handle the gen1 firmware-watchdog interrupt through the same fatal path even if no HFI error packet exists.

A software guard cannot guarantee “never hang the SoC”: a blocked `readl()` is not made safe by `readl_poll_timeout()`, and DMA may already have faulted before notification. These changes prevent the driver from **compounding** a crash through stale commands, freed DMA or powered-down MMIO.

Keep the low-IOVA exclusion. The overlay reserves `[0, 0x25800000)` at [video.dtso:145](/home/deck/.local/state/rog5-video-wt/dts/qcom/sm8350-asus-rog-phone5-video.dtso:145). Verify the actual IOMMU reserved regions and all traced DMA addresses, rather than relying solely on the overlay text.
