# GPT-6.1-Sol review: 0145 DP link policy and rog5-dp-power-measure (2026-09-30)

Brief: the questions in [2026-09-30-dp-link-efficiency.md](2026-09-30-dp-link-efficiency.md) (patch 0145 v1, script v1). Read-only; Sol's file links point at the scratch copy of the patched dp_ctrl.c.

1. **P2 — Retry exhaustion can report successful training.** In [dp_ctrl.c:2494](/tmp/claude-1000/-home-deck-Projects-rog-phone-linux-migration/2cc1c994-1a4f-4a0b-aca7-41804577680f/scratchpad/dp0145/b/drivers/gpu/drm/msm/dp/dp_ctrl.c:2494), a failed training attempt is followed by downshift/reinitialization, which overwrites `rc` with zero. After the fourth attempt, the helper can return zero for a freshly reinitialized, **untrained** link. This defect is inherited from the moved loop, but the new fallback relies on its result. **Smallest fix:** return zero directly when `setup_main_link()` succeeds; return an error on retry exhaustion.

2. **P2 — The maximum-link fallback can finish below the mode’s required bandwidth.** [dp_ctrl.c:2635](/tmp/claude-1000/-home-deck-Projects-rog-phone-linux-migration/2cc1c994-1a4f-4a0b-aca7-41804577680f/scratchpad/dp0145/b/drivers/gpu/drm/msm/dp/dp_ctrl.c:2635) invokes the same downshift helper again without checking its final capacity. For example, the fallback can successfully train 2 × HBR, whose 4.32 Gbit/s payload cannot carry the requested 7.995 Gbit/s. **Smallest fix:** repeat the capacity check after fallback training and enter failure cleanup if it fails. Separately, the first check at line 2621 uses 100%, so downshifts can bypass the configured 95% margin; use the configured margin when deciding whether to retain a reduced link.

3. **P2 — Compliance link-training requests change software parameters without changing the physical link.** [dp_link.c:763](/home/deck/.local/state/rog5-kernel-7.2.7-build-r108/source/drivers/gpu/drm/msm/dp/dp_link.c:763) replaces `link_params` with the requested rate/lanes, but [dp_ctrl.c:2354](/tmp/claude-1000/-home-deck-Projects-rog-phone-linux-migration/2cc1c994-1a4f-4a0b-aca7-41804577680f/scratchpad/dp0145/b/drivers/gpu/drm/msm/dp/dp_ctrl.c:2354) only runs link maintenance. It never reinitializes the PHY/clocks. A maximum-rate CTS request against the newly selected HBR link therefore programs HBR2 into DPCD while transmitting HBR. This is an existing defect exposed by routinely using reduced links. **Smallest fix:** reinitialize the mainlink before training changed CTS parameters; refresh rate-dependent stream programming before resuming video.

4. **P2 — A policy-restore error prevents charger restoration.** At [rog5-dp-power-measure:447](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-dp-power-measure:447), the policy write can raise before either restoring `charge_behaviour` or restarting the charge service. A battery run can remain in `force-discharge` because an unrelated DP restore failed. In-memory fault injection reproduced this. **Smallest fix:** attempt each restoration independently, collect errors, and retain the recovery record for unsuccessful steps.

5. **P2 — Charge-service failures are ignored, and recovery evidence is discarded.** [rog5-dp-power-measure:396](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-dp-power-measure:396) ignores a failed service stop, allowing the running policy to overwrite `force-discharge` during measurement. Lines 456–458 likewise report a failed restart as “started” and delete `saved.json`. Fault injection reproduced the latter. **Smallest fix:** check both return codes; abort measurement on failed stop, and retain pending restoration state on failed restart.

6. **P2 — Standalone restore does not restore the active link or recover interrupted DPMS.** [rog5-dp-power-measure:304](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-dp-power-measure:304) has no local `finally` around off/on. SIGKILL between those calls leaves the display off; `restore` only writes the parameter, so it also leaves an already active experimental link unchanged. The normal final modeset occurs *after* `saved.json` is deleted at line 458, and another SIGTERM during that modeset escapes the `except Exception` at line 548. **Smallest fix:** persist pending display restoration, ensure ordinary cancellation attempts power-on, and let `restore` apply the saved policy through a verified modeset before removing recovery state. SIGKILL still requires explicit recovery.

7. **P2 — Concurrent sessions can overwrite each other’s recovery state.** [rog5-dp-power-measure:377](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-dp-power-measure:377) treats any existing record as an abandoned run, even if its owner is active. A second invocation can restore the first session mid-measurement, replace its snapshot, and later have that snapshot deleted by the first session. **Smallest fix:** hold an exclusive lock across measurement and cleanup; require the same lock for standalone restore.

8. **P2 — Cleanup can leave the measurement workload running.** [rog5-dp-power-measure:413](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-dp-power-measure:413) skips group cleanup when the shell leader has exited, and silently forgets the process after a SIGTERM timeout. Background descendants or a TERM-resistant workload can remain active and contaminate subsequent measurements. **Smallest fix:** manage the owned process group through completion, escalate after the grace period, and reap the leader before forgetting it.

9. **P2 — The summary can average different physical links as one configuration.** [rog5-dp-power-measure:527](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-dp-power-measure:527) records whichever link appeared without distinguishing fallback, while [line 348](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-dp-power-measure:348) displays only the last round’s link beside averages from every round. Intermittent fallback can therefore produce an “efficient” power result containing both HBR and HBR2 windows. The stub always returns its expected successful link, so it misses this. **Smallest fix:** require consistent mode/bpp/rate/lanes within each comparison, or summarize distinct trained configurations separately and explicitly mark fallback.

10. **P3 — `/dev/kmsg` retries every read error indefinitely.** [rog5-dp-power-measure:231](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-dp-power-measure:231) treats every `OSError` as overwritten-record `EPIPE`. A persistent different error spins instead of failing. **Smallest fix:** continue only for `errno.EPIPE`; propagate other errors, and bound log draining.

**Verdict:** Fix the P2 findings before relying on this for production or power conclusions. I found no new P1 clock/PHY imbalance or unclocked-register path: the guards cover failed enables, clearing training patterns uses AUX, and QMP bus width describes routed capacity rather than selected lanes. TU, MSA, audio and ordinary link maintenance consume actual `link_params`; wide bus correctly halves the interface clock rather than link demand. RBR’s 810 MHz pixel parent and the 16-bit fractional RCG have matching source support, although that is not hardware validation. I would retain 95% and the two-lane selection floor: 92.535% leaves reasonable headroom, and the kernel’s [bandwidth helper:4815](/home/deck/.local/state/rog5-kernel-7.2.7-build-r108/source/drivers/gpu/drm/display/drm_dp_helper.c:4815) confirms the 0.6% SSC/reference margin. Lowest-rate-first is a plausible SM8350 power hypothesis because it lowers the MMCX vote; additional lane bias and stock’s separate MX TURBO vote prevent claiming it is measured cheapest. Keep policy 0 as the production default until 4 × HBR picture, underrun, replug and resume behavior is verified. Mutter’s native backend does [disable CRTCs](https://github.com/GNOME/mutter/blob/main/src/backends/native/meta-kms-impl-device-atomic.c#L1214) and [queue modesets on power-on](https://github.com/GNOME/mutter/blob/gnome-49/src/backends/native/meta-renderer-native.c#L2109), supporting the DPMS approach. Paired per-round deltas are correct; their SD is descriptive variability, not a confidence interval. Review and fault checks were read-only and in memory; no phone was contacted.
