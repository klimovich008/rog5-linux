1. **P2 — REMOVE can decrement the wrong speed bucket.**  
   [0148:220](/home/deck/.local/state/rog5-prod-boot-20260923/patches/linux-7.2.7/0148-usb-dwc3-qcom-legacy-ROG5-usb-ddr-vote-follows-the-attached-devices.patch:220)

   `udev->speed` is not immutable between ADD and REMOVE. In r110, `hub_port_wait_reset()` assigns the newly negotiated speed; `hub_port_init()` subsequently rejects an unexpected speed change **without restoring the old value**. An HS→FS reset followed by disconnect therefore leaves the fast count elevated and decrements the slow count, potentially belonging to another device. This can permanently retain the full vote or undervote remaining slow devices.

   **Smallest fix:** track each counted `udev` and its ADD-time bucket; REMOVE must decrement that recorded bucket.

2. **P2 — USB notifications are not reliably paired for every device.**  
   [0148:225](/home/deck/.local/state/rog5-prod-boot-20260923/patches/linux-7.2.7/0148-usb-dwc3-qcom-legacy-ROG5-usb-ddr-vote-follows-the-attached-devices.patch:225)

   A `generic_subclass` driver sends ADD through `usb_generic_driver_probe()` **before its own probe**. If that later probe fails, `usb_probe_device()` returns the error without calling generic disconnect. There is no balancing REMOVE; another probe can add another count. This is reachable through drivers such as `apple-mfi-fastcharge`. Non-generic device drivers such as usbip-host can instead generate neither notification while performing transfers.

   **Smallest fix for failed-probe accounting:** unwind generic probe on subsequent probe failure and deduplicate ADD by device identity. To satisfy the stated *every attached device* goal, attachment accounting needs a device-lifetime notification independent of driver binding; documenting the usbip exception does not meet that goal. ADD also arrives after configuration/interface probing, so it cannot guarantee full bandwidth before interface-driver traffic begins.

3. **P2 — Leaving DEVICE lowers bandwidth before the gadget stops.**  
   [0148:275](/home/deck/.local/state/rog5-prod-boot-20260923/patches/linux-7.2.7/0148-usb-dwc3-qcom-legacy-ROG5-usb-ddr-vote-follows-the-attached-devices.patch:275)

   The pre-role hook immediately clears `bw_device_role` for HOST/NONE. DEVICE→HOST teardown happens later in queued `drd_work`; DEVICE→NONE drops the pull-up later through `usb_udc_vbus_handler()`. With no counted host devices, the running NCM gadget temporarily receives the 1/1 vote while transfers or teardown DMA can still be active.

   **Smallest fix:** raise bandwidth in the pre-hook, but defer lowering until gadget teardown or pull-up removal has completed. Steady DEVICE operation correctly requests full bandwidth.

4. **P2 — Probe can miss a concurrent parameter update.**  
   [0148:345](/home/deck/.local/state/rog5-prod-boot-20260923/patches/linux-7.2.7/0148-usb-dwc3-qcom-legacy-ROG5-usb-ddr-vote-follows-the-attached-devices.patch:345)

   Probe applies the initial policy before joining the global list. A setter between those operations changes the parameter and updates existing entries, missing this controller. Probe then registers it with the previous vote, potentially indefinitely on an empty port. This also compromises A/B observations during startup.

   **Smallest fix:** hold `dwc3_qcom_bw_list_lock` across initial application and list insertion, acquiring `bw_lock` underneath it to match the setter’s ordering.

5. **P2 — The voltage range does send a voltage request.**  
   [antenna overlay:42](/home/deck/.local/state/rog5-prod-boot-20260923/dts/qcom/sm8350-asus-rog-phone5-antenna-rail-off.dtso:42), [voltage test:62](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/test-idle-power-votes.py:62)

   r110’s `of_regulator.c:110` sets `apply_uV` whenever both bounds are nonzero, including unequal bounds. The unknown cached voltage causes `machine_constraints_voltage()` to select **2.848 V**. RPMh initially caches that selector, then sends the voltage request before the boot-on enable request.

   Thus the overlay changes the wrapper’s voltage vote, contrary to its premise. Failure of that extra request can fail the entire `regulators-1` probe and unwind already registered sibling rails. The structural test does not verify the claimed absence of a voltage request.

   **Smallest fix:** omit both voltage properties for this enable/disable-only declaration; update the composition checks and test accordingly. No initial mode request is generated by the current declaration.

6. **P2 — Failed DDR reads can become plausible-looking measurements.**  
   [sample:68](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-idle-power-sample:68)

   `rd()` converts a read error into `None`, and `ddr_residency()` converts that into `{}`. A failed final read therefore subtracts every previous counter from zero. For example, a previous ten-second 451 MHz duration produces `−10 s`; normalization can still report **451 MHz 100%**. A failed initial read instead attributes accumulated boot history to the window. Counter resets likewise produce negative deltas without invalidating the result.

   **Smallest fix:** distinguish read/parse failure from valid empty statistics and reject the window; reject unexplained counter decreases. Add failure/reset fixtures.

7. **P2 — A second termination signal can interrupt restoration.**  
   [sample:218](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-idle-power-sample:218), [A/B test:166](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/test-idle-power-votes.py:166)

   One SIGINT/SIGTERM/SIGHUP enters cleanup correctly. Their handlers remain active during the restoring write, however, so another signal can raise `KeyboardInterrupt` inside `finally` and leave the parameter changed. An in-memory fault injection reproduced this: original `Y`, interrupted trial at `N`, interrupted restoration leaves `N`. Existing tests cover normal completion only.

   **Smallest fix:** block SIGINT/SIGTERM/SIGHUP during restoration, then verify readback. Add signal-interruption coverage.

8. **P3 — The requested measurement duration is shortened.**  
   [sample:152](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-idle-power-sample:152)

   There are `n` samples but only `n−1` sleeps. A requested four-second window at two-second intervals waits two seconds; a one-second window with that interval performs no wait. Defaults wait 298 seconds plus read overhead instead of 300.

   **Smallest fix:** sample against a monotonic deadline and record actual elapsed time. Add a fake-clock duration assertion.

The remaining requested checks:

- **Ordinary notification behavior:** successful generic device-driver bindings pair ADD/REMOVE, including device-driver rebinding. `authorized=0` still gets initial ADD; authorization changes, configuration changes and interface-driver rebinding do not themselves change these counts. Ordinary hub removal recursively removes children, and xHCI removal disconnects both root-hub trees. The failed-probe and speed-change exceptions above remain.
- **Controller filtering:** `bus->controller->parent->parent == glue` is correct for both xHCI root hubs here. `controller` is the xHCI platform device, distinct from its DMA `sysdev`.
- **Locks and lifetime:** I found no significant new deadlock or notifier lifetime bug. `bw_lock` is released before `session_lock`/runtime PM; bandwidth application does not acquire role or USB-device locks. Unregistration waits for callbacks. The built-in boot parameter callback encounters an empty, statically initialized list; its uncontended mutex does not establish a boot deadlock.
- **Disabled ICC paths and s2idle:** `icc_set_bw()` updates stored requests while disabled, but aggregation uses zero until `icc_enable()`. The added serialization therefore preserves the requested resume vote without re-enabling either suspend-disabled path.
- **The 1/1 floor:** BCM arithmetic preserves small nonzero votes, and enable-mask BCMs remain enabled. That supports connectivity, but does **not prove sufficient DMA latency** for a running xHCI controller. Stock’s suspended-controller zero vote is not equivalent evidence. Hardware qualification remains necessary.
- **LDO11 cleanup:** after successful early registration, boot-on leaves `use_count` zero and establishes known enabled state; late cleanup disables it. This assumes registration before the one-shot cleanup and no `regulator_ignore_unused`. Exact 2.850 V constraints really are unsupported on this PLDO grid.
- **Measurement format:** DDR regex matches r110 output, and the charger µV×µA conversion is correct. Both Python scripts parse successfully. I ran read-only, in-memory checks; I did not run the tempfile-based suite or hardware tests.
