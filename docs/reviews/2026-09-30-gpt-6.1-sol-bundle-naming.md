# GPT-6.1-Sol review: bundle names, kernel labels and rog5-make-bundle (2026-09-30)

Read-only review (`codex exec -m gpt-6.1-sol`, reasoning high) of the uncommitted change before its first commit. Brief: the kNNN/dN/bundle naming, the per-build `uname -r`, the bundle tool and registries; asked to break the claim that a k111 default next to a k69 fallback and an install from k110 keep working.

## Review

No P0/P1 found, and no fixed-release dependency that breaks k111 main + legacy k69 fallback or installation from k110.

- **P2 — External-module fixes can be silently omitted.** [rog5-make-bundle.py:191](scripts/host/rog5-make-bundle.py:191): reuse checks the kernel identity and package hash, but never checks external-module sources against HEAD. Commit a fix under `tools/`, then rebuild a bundle with the same kernel: it ships the old `.ko` without warning. Even after `--fresh-modules`, subsequent ordinary runs select the original cache. Pin external sources and invalidate reuse when they change.

- **P2 — A registered kernel ID can acquire different bytes.** [rog5-make-bundle.py:331](scripts/host/rog5-make-bundle.py:331): existing kernel entries are retained without comparing their Image pin to the selected build. Replace/recreate a build directory with different bytes but the same label/release, then package it: the new bundle succeeds while the registry still identifies the old Image. Check the existing entry before building.

- **P2 — Wrapper construction inherits an unpinned helper override.** [rog5-make-bundle.py:301](scripts/host/rog5-make-bundle.py:301): the package step inherits the caller’s environment. `ROG5_TRIAL_HELPER`, consumed by `build-persistent-slotb-recovery-initramfs.sh:17`, can select an older helper or abort packaging despite unchanged HEAD and pinned inputs. Sanitize the wrapper step too.

Test gaps: the bundle tests fake all three builders; the labelled-release composition test uses no production module package ([test-standalone-rescue-composition.py:35](scripts/device/test-standalone-rescue-composition.py:35)). Neither exercises real labelled module composition/publication or the mixed-release installer path, and the findings above lack regressions.

Three read-only tests passed; all registered DTB pins/features and kernel registry/result Image pins matched. Full suites were not run because they require temporary writes.
## Follow-up

- P2 external-module sources: a package the tool makes records a digest of the packager, the module selection and every external module source tree (`make-bundle-sources.json`); it is reused only while the digest matches the snapshot, otherwise a new `modules-kNNN-<time>` is packaged. A legacy package without a digest is used only when the build objects are gone (k69), and the bundle notes say so. Tests: `test_changed_external_module_sources_give_a_new_module_package`, `test_legacy_module_package_is_reused_only_for_a_pruned_build`.
- P2 kernel pin: an existing `kernels` entry must name the same build, release and Image hash (checked in the plan and again under the registry lock). Test: `test_a_registered_kernel_must_keep_its_bytes`.
- P2 inherited overrides: every build step (modules, ramdisk, package) runs without inherited `PRODUCTION_*`, `EXPECTED_*`, `ROG5_*` (e.g. `ROG5_TRIAL_HELPER`) and `PYTHON*` variables. Test: `test_build_steps_get_no_inherited_overrides`.
- Test gap: `test-standalone-production-tree.py` `LabelledRelease` relabels the private r110 module package to 7.2.7-rog5-k111 and builds the real production ramdisk (one tree, `expected_kernel_release=7.2.7-rog5-k111`, a k112 build refused). The installer never compares releases, so a mixed-release install has no release-specific path to test.
- Also added before the commit: the registry is reloaded and saved under a lock when a build finishes, so a status change made during a build is kept (`test_a_status_change_during_a_build_is_kept`).
