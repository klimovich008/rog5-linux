**1. Encoder: ranked changes and possible SoC-hang mechanisms**

The surviving journal ends at the userspace encode marker. It contains **no encoder HFI transaction identifying the failing boundary**. Therefore SESSION_INIT, property submission, SET_BUFFERS, LOAD_RESOURCES, START and first ETB remain distinguishable hypotheses—not established locations. See [journal-trial-boot.txt:2434](/home/deck/.local/state/rog5-production-boot-20260923/ram-trial-main-k115-d15-261002d-D/phone-logs/journal-trial-boot.txt:2434) and [k115-D.log:35](/home/deck/.local/state/rog5-production-boot-20260923/ram-trial-main-k115-d15-261002d-D/phone-logs/k115-D.log:35).

A firmware assertion alone normally leaves the host able to process a watchdog/system-error interrupt. A host-wide freeze additionally suggests stalled fabric access, DMA/security faults, a kernel deadlock, or another shared-resource failure. **The logs do not select one.**

Ranked by usefulness and likelihood of correcting OEM encoder bring-up:

| Rank | Concrete change | Evidence and uncertainty |
|---|---|---|
| 1 | Send **`HFI_PROPERTY_PARAM_SECURE_SESSION = 0`** before any firmware-visible session buffer | Stock explicitly does this for encoding. Iris omits it. VP9 proves this firmware can reject buffers while CP mode remains unknown. Strong compatibility candidate; **not proof of the encoder’s hard-hang cause**. |
| 2 | Complete encoder configuration before LOAD_RESOURCES/START; explicitly send **WORK_ROUTE=4** for this ordinary VBR case | Stock waits for both queues and chooses work mode/route before installing buffers. | 3 | Send stock **SYS_UBWC_CONFIG** for SM8350/LPDDR5 | Real omitted initialization. NV12 input still needs UBWC reconstructed references. Decode success weakens a universally broken UBWC-default explanation, but does not establish correct encoder reference writes. |

| 5 | Validate every DMA range and instrument controller/core power transitions | Low protected IOVA and powered-down MMIO can cause much wider failure than a session error. **No encoder address or power snapshot survives to demonstrate either.** |

Before another encoder attempt:

**2. VP9: likely rejection and exact proposed fix**

This is considerably clearer than a generic bad-format hypothesis.

The firmware reports:

- `CP mode is UNKNOWN`;
- `CP breached - buffer type 5`, then 6 and 7;
- required internal buffers missing at LOAD_RESOURCES.

See [journal-trial-boot.txt:2418](/home/deck/.local/state/rog5-production-boot-20260923/ram-trial-main-k115-d15-261002d-D/phone-logs/journal-trial-boot.txt:2418).

Those types are PERSIST1, SCRATCH and SCRATCH1 (`K/iris_hfi_gen1_defines.h:78`). The trace supplies addresses `ce000000`, `cd000000`, `ccf80000`, all above the protected low-IOVA interval, before LOAD (`D/journal-trial-boot.txt:2394`). SESSION_INIT itself succeeded (`:2378`).

**Highest-confidence hypothesis: omitted `SECURE_SESSION=0`, leaving VP9’s CP mode uninitialized.** Stock sends that property even for nonsecure decode: [msm_vdec.c:1205](/home/deck/Projects/rog-phone-linux-migration/kernel-src/msm-5.4/techpack/video/msm/vidc/msm_vdec.c:1205), called at `:1508`.

Implement:

```c
#define HFI_PROPERTY_PARAM_SECURE_SESSION 0x1011
```

Add a gen1 packetization case carrying one `u32`, and send zero after successful SESSION_INIT, before any SET_BUFFERS/ETB/FTB. Expected packet:

```text
00000018 00011001 <session_id> 00000001 00001011 00000000
```

Apply it to OEM nonsecure decoder and encoder sessions. Do not confuse this with the global SCM protected-memory configuration.

`0x1001` means **SESSION_FATAL**, not “unsupported VP9 property” (`S/vidc_hfi_helper.h:42`). The SFR remains its initial text because this is a session failure. The missing-property diagnosis is strongly supported, but still requires a corrected trial to prove.

**3. `interframe_pc=0`: correct property, inconsistent host mode**

The switch sends:

```text
HFI_CMD_SYS_SET_PROPERTY
num_properties = 1
HFI_PROPERTY_SYS_CODEC_POWER_PLANE_CTRL = 0x5
enable = 0
```

See [iris_hfi_gen1_command.c:107](/home/deck/.local/state/rog5-kernel-7.2.7-build-r115/source/drivers/media/platform/qcom/iris/iris_hfi_gen1_command.c:107). Stock uses the same property and scalar layout: `S/hfi_packetization.c:308`. **The property is not demonstrably wrong for gen1/VPU2.**

The more important mismatch: Iris unconditionally switches the hardware domain into hardware-controlled mode **before** sending this property (`K/iris_core.c:336`; `K/iris_vpu_common.c:328`). Setting the module parameter false changes only firmware policy.

Stock explicitly warns that handing the GDSC to hardware can turn it off unless the hardware vote exists: [hfi_common.c:3991](/home/deck/Projects/rog-phone-linux-migration/kernel-src/msm-5.4/techpack/video/msm/vidc/hfi_common.c:3991).

**Likely mechanism, still a guess:** firmware stops maintaining a vote after receiving zero while the host still relies on hardware-controlled power. Boot C does not provide the final acknowledged HFI packet or hardware-state snapshot to prove this.

A meaningful “disable interframe collapse” experiment must coordinate **both** sides:

- Keep the hardware domain under software control and powered on during init/resume.
- Send firmware `enable=0`.
- Keep matching behavior across every resume.

For the next normal build, force `interframe_pc=1` for this OEM configuration and reject unsupported attempts to change it. Its present writable switch is not a complete power-management experiment.

**4. Boot B: pinned runtime PM**

`power/control=on` adds a runtime-PM usage reference and prevents host runtime suspension. It **does not disable firmware hardware collapse**: [power/sysfs.c:107](/home/deck/.local/state/rog5-kernel-7.2.7-build-r115/source/drivers/base/power/sysfs.c:107), `drivers/base/power/runtime.c:1664`.

Consequently B keeps the authenticated firmware/controller around during idle, whereas D executes PC_PREP → SCM suspend → host shutdown (`K/iris_hfi_common.c:125`).

**What is established:** B failed in prolonged idle; D completed five minutes of idle with the core off. **What is not established:** a particular collapsed-core MMIO access, interrupt race or firmware idle bug caused B. Stock supports hardware collapse while powered, so the combination is not inherently invalid.

D supports retaining autosuspend as the current default. It does **not** prove all autosuspend/resume races safe.

For a temporary refusal:

- Reject opens/submissions when the OEM configuration has `runtime_auto == false`.
- Recognize that this alone does **not** protect an already-idle core from a later sysfs write.
- A complete rejection of the write needs a per-device PM-policy check in generic `control_store()` before `pm_runtime_forbid()`. There is no Iris callback invoked by this write, and `pm_runtime_forbid()` has no failure return. Avoid pretending an open-time guard solves that transition.

For eventual support, first reproduce idle with persistent PM/IRQ diagnostics and repair the responsible transition. Any software-controlled “always on” mode must coordinate GDSC ownership and firmware policy as described above.

**5. CPU-NOC LPI timeout: concrete wrong-sequence candidate**

Iris VPU2 selects the generic controller-off implementation (`K/iris_vpu2.c:44`). It requests CPU-NOC LPI at wrapper offsets **`+0x5c/+0x60`**, times out, and jumps directly to gating clocks/domains: [iris_vpu_common.c:178](/home/deck/.local/state/rog5-kernel-7.2.7-build-r115/source/drivers/media/platform/qcom/iris/iris_vpu_common.c:178).

Stock Iris2 shutdown instead does:

1. `CPU_CS_X2RPMh = 3`.
2. AON MVP-NOC request/acknowledgment.
3. **DEBUG_BRIDGE_LPI_CONTROL = 7**, wait for `(status & 7) == 7`.
4. DEBUG_BRIDGE_LPI_CONTROL = 0, wait for zero.
5. Disable clocks, regulators and bus votes.

See [hfi_iris2.c:176](/home/deck/Projects/rog-phone-linux-migration/kernel-src/msm-5.4/techpack/video/msm/vidc/hfi_iris2.c:176).

Stock has **no CPU-NOC `+0x5c/+0x60` handshake in this sequence**. Iris omits the debug-bridge request of 7; its timeout also bypasses the later debug-bridge release and TZ FIFO operations.

**Recommendation:** add a VPU2-specific `power_off_controller` matching stock Iris2, rather than adjusting unrelated register bases or setting `no_aon=true`.

The repeatable zero—including before firmware starts—strongly supports an unsupported/wrong handshake sequence. It is **not proof of outstanding DMA**, nor proof that the skipped sequence is harmless. Successful shutdown/restart in D establishes limited operational tolerance.

Also stop returning unconditional success after handshake failure (`K/iris_vpu_common.c:226`). Propagate failures with corresponding PM/state restoration; merely returning an error after already gating everything would also misrepresent the hardware state.
