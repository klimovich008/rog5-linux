**Secure-session theory: verified against stock**

Stock’s secure control defaults to disabled. `msm_vdec_set_secure_mode()` restricts the allowed codecs only when the control is nonzero, but **unconditionally sends the property afterward**, including zero. The initial decoder property sequence calls it before resource loading; initial-only properties are skipped during port reconfiguration. [S/msm_vdec.c:128–134,1218–1234,1491–1508][svdec]

Stock packetization is generic: it writes one property ID and copies the supplied payload. For secure mode the payload is exactly one `u32`; there is no extra enable structure, protected-address list or VP9-specific wrapper. Its property ID is `0x1011`. [S/hfi_packetization.c:624–642][spacket]; [S/vidc_hfi_helper.h:238–239][shelper]

The expected six-word command is therefore:

```text
00000018 00011001 <session_id> 00000001 00001011 00000000
```

That follows stock’s header/property/payload construction and Iris’s existing property framing. [S/hfi_packetization.c:632–639][spacket]; [K/iris_hfi_gen1_command.c:576–587,845–865][kcmd]

The global SCM call is a different operation: it configures protected address ranges, not an individual session’s secure/nonsecure state. k115 performs that call during firmware boot. [K/iris_firmware.c:97–102][kfirmware]

The three rejected allocations lie entirely above the configured protected interval `[0,0x25800000)`: their ranges are `ce000000..ce8d6f00`, `cd000000..cdbf4000` and `ccf80000..ccfe3500`. This arithmetic provides no evidence that the allocations themselves were placed inside the protected range. [K/iris_platform_vpu2.c:58–64][kplatform]; [D/journal-trial-boot.txt:2394–2397][djournal]

**Highest-confidence inference:** VP9’s buffer validator encounters an uninitialized session CP mode because the host omitted the explicit nonsecure property. The sources and logs support that explanation; they do not reveal the firmware implementation or prove that this is the only startup requirement. Moving buffers, changing the SCM range or disabling protection would not directly address the reported unknown session mode. [S/msm_vdec.c:1218–1234][svdec]; [D/journal-trial-boot.txt:2418–2424][djournal]

**H.264 and HEVC: the omission is shared; the internal CP state is unproven**

The session-open path is shared by H.264, HEVC and VP9, and none receives secure initialization in k115. Stock explicitly initializes all three. Thus H.264/HEVC success depends on firmware behavior that Iris has not explicitly selected. [K/iris_hfi_gen1_command.c:165–194][kcmd]; [S/msm_vdec.c:1220–1234,1508][svdec]

Boot D nevertheless establishes successful decoding: H.264 and HEVC each returned 300 frames matching software; H.264 also decoded after the failed VP9 session. It does **not** establish that their CP mode was unknown or that they silently suffered the same validation failure. Possible explanations include codec-specific defaults or different validation paths; those remain guesses. [D/k115-D.log:1–4,15–31][dlog]

Absence of printed CP messages cannot settle their internal state: firmware logging is rate-limited, and this boot explicitly reports 616 suppressed callbacks. [K/iris_core.c:29–39][kcore]; [D/journal-trial-boot.txt:2417][djournal]

The defensible fix is explicit zero for every OEM **nonsecure decoder session**, including the already-working codecs.

**Probability, persist, scratch and line buffers**

**The probability storage is already present.** Stock’s single VP9 PERSIST1 allocation contains 36 probability tables of 3,840 bytes, fixed COMV storage, a 34-byte superframe-header area, a 384-byte uncompressed-header area and 32 CCE tile-offset areas. Iris includes all those components, then adds frame-info storage and HDR histogram space. [S/msm_vidc_buffer_calculations.c:233–251,1936–1947][sbuf]; [K/iris_vpu_buffer.h:47–64][kvpubh]; [K/iris_vpu_buffer.c:199–212][kvpub]

There is no demonstrated requirement to add a separate probability buffer, seed probability tables in host code, or add a standalone VP9 COMV buffer. Stock selects PERSIST1/SCRATCH/SCRATCH1 calculators and allocates the internal storage through its generic path; Iris intentionally returns zero for standalone VP9 COMV/non-COMV because the relevant storage is embedded elsewhere. [S/msm_vidc_buffer_calculations.c:352–355][sbuf]; [S/msm_vidc_common.c:4049–4076][scommon]; [K/iris_vpu_buffer.c:727–739,796–808][kvpub]

For the **1920×1088, four-pipe, split-output configuration actually sent in D**, formula evaluation gives:

| HFI allocation | Stock bytes | Iris bytes | Result |
|---|---:|---:|---|
| PERSIST1 | 9,068,288 — `0x8a5f00` | 9,268,992 — `0x8d6f00` | Iris adds 200,704 bytes. |
| SCRATCH | 12,533,760 — `0xbf4000` | 12,533,760 — `0xbf4000` | Matches stock. |
| SCRATCH1 | 341,504 — `0x53600` | 406,784 — `0x63500` | Iris adds 65,280 bytes of QP storage at this geometry. |

These are **derived calculations**, using the stock and Iris formulas; the Iris results match all three logged registrations. [S/msm_vidc_buffer_calculations.c:1379–1411,1556–1583,1936–1947][sbuf]; [K/iris_vpu_buffer.c:93–103,204–212,479–507,836–840][kvpub]; [D/journal-trial-boot.txt:2388–2389,2394–2397][djournal]

Therefore, missing or undersized probability/persist/line storage is not supported as the explanation for the **tested startup**.

There is, however, a real geometry mismatch: stock rounds VP9 reconstruction metadata and VPSS height terms to **16**, whereas Iris rounds them to **8**. Extra QP storage does not guarantee that Iris is always larger. At 128×136, four pipes and split output, evaluation gives stock SCRATCH1 **52,480 bytes** versus Iris **52,224 bytes**. This is a calculated discrepancy, not an observed hardware overrun; allocation padding could mask it. [S/msm_vidc_buffer_calculations.c:217–218,1099–1130,1556–1583][sbuf]; [K/iris_vpu_buffer.c:288–310,442–445,479–507][kvpub]

It matters after header discovery or resolution change because Iris stores the reported dimensions and recalculates input internal buffers on initial source change and DRC. [K/iris_hfi_gen1_response.c:107–113][kresponse]; [K/iris_common.c:113–123][kcommon]

A separate, unequivocal sizing omission is the **decoder input buffer’s 10/8 allowance**. Stock adds 25% for VP9 and HEVC on Iris2 regardless of the eventual stream bit depth; Iris does not. For the normal 4K-based VP9 calculation, stock returns **17,694,720 bytes**, Iris **14,155,776 bytes**. This can matter for large compressed packets, but cannot cause the observed pre-ETB CP rejection. [S/msm_vidc_buffer_calculations.c:880–943][sbuf]; [K/iris_buffer.c:393–415][kbuffer]; [D/journal-trial-boot.txt:2377–2398][djournal]

**VP9 profile 2 / 10-bit is currently unsupported, despite format names**

Stock supports VP9 profiles 0 and 2, maps them to HFI profile values `1` and `4`, and selects TP10 UBWC reference surfaces when the parsed stream is 10-bit. Linear NV12/P010 uses secondary output. [S/msm_vdec.c:267–277,546–573][svdec]; [S/msm_vidc_common.c:394–401][scommon]; [S/vidc_hfi_helper.h:117–118][shelper]

k115 has several independent blockers:

- The gen1 event parser copies the HFI bit-depth word and rejects **any nonzero value**. HFI represents 8-bit as enum zero and 10-bit as enum two, independently for luma/chroma halves. [K/iris_hfi_gen1_response.c:57–61,169–172][kresponse]; [S/vidc_hfi_helper.h:174–176][shelper]; [S/hfi_response_handler.c:178–206][sresponse]
- P010/QC10C appear in the format array, but validation requires `fw_caps[BIT_DEPTH] == BIT_DEPTH_10`; the gen1 decoder capability table does not provide or update that capability. [K/iris_vdec.c:65–105][kvdec]; [K/iris_hfi_gen1.c:16–33][kgen]
- Gen1 raw-format setup always selects NV12 UBWC references and chooses only NV12/NV12 UBWC for output. Stock has distinct P010 and TP10 UBWC HFI formats. [K/iris_hfi_gen1_command.c:923–943][kcmd]; [S/vidc_hfi_helper.h:688–697][shelper]
- Source-change handling always calculates NV12-style stride, even though the ordinary format-setting path already calculates P010 as `ALIGN(width * 2, 256)`. [K/iris_hfi_gen1_response.c:110–113][kresponse]; [K/iris_vdec.c:277–287][kvdec]

Simply removing `if (event.bit_depth)` would expose incorrect formats and sizes. HFI enum words must first be translated into Iris’s different internal representation, `BIT_DEPTH_8 = 0x00080008` / `BIT_DEPTH_10 = 0x000a000a`. [K/iris_platform_common.h:18–20][kpcommon]; [S/hfi_response_handler.c:190–206][sresponse]

**Extradata and header parsing**

Stock enables these defaults for VP9: output crop, interlace information, VPX colorspace, HDR10 histogram and concealed-macroblock count. Advanced user data, timestamps, frame packing, frame rate, panscan, recovery point, aspect ratio and QP metadata are controlled separately. [S/msm_vdec.c:1430–1482][svdec]

The direct extradata properties use an **eight-byte `{enable, index_extra_data_id}` payload**, not a scalar enable. Iris currently sends zero extradata addresses/sizes in FTB/SET_BUFFERS. Enabling the properties without backing storage would be an incomplete implementation. [S/vidc_hfi.h:89–92][shfi]; [S/msm_vidc_common.c:7496–7510][scommon]; [K/iris_hfi_gen1_command.c:393–406,433][kcmd]

Iris already handles sequence-event colorspace and crop; the missing facility is the stock per-buffer metadata path, not all color/crop reporting. Stock also supplies extradata storage when queueing internal DPBs. [K/iris_hfi_gen1_response.c:69–74,86–94,115–156][kresponse]; [S/msm_vidc_common.c:2019–2035][scommon]

**No host VP9 superframe parser is established as a stock requirement.** Stock’s decoder “Superframe” control is fixed at zero. The similarly named common routine groups fixed-size raw input frames, using a color-format conversion and `VENUS_BUFFER_SIZE`; it is not a VP9 compressed-superframe splitter. [S/msm_vdec.c:433–439][svdec]; [S/msm_vidc_common.c:4576–4613][scommon]

Stock’s decoder ETB packetizer passes compressed address, offset, lengths, timestamp and flags without VP9 header parsing. Together with the superframe/uncompressed-header areas in PERSIST1, this supports the **inference** that firmware owns VP9 parsing. It does not justify importing the raw-frame batching routine or requiring a special VP9 codec-config packet. [S/hfi_packetization.c:470–503][spacket]; [S/msm_vidc_buffer_calculations.c:249–250,1940–1946][sbuf]

There is a different parser weakness in Iris: its **HFI sequence-property parser** lacks per-property remaining-length checks, does not advance on unknown property IDs, and applies zero-initialized fields even when absent. Stock bounds-checks property IDs and payloads. This should be fixed before broadening profile/metadata support, although it is downstream of the present registration failure. [K/iris_hfi_gen1_response.c:16–105,107–172][kresponse]; [S/hfi_response_handler.c:137–150,178–181][sresponse]

**Output constraints, counts and reference lifetime**

Stock sends NV12 luma-buffer alignment **512**, chroma alignment **256**. Iris sends 256 for both. Furthermore, Iris’s packetizer reconstructs hardcoded constraints instead of serializing the caller’s structure, so fixing only `set_format_constraints()` would not change the wire packet. [S/msm_vdec.c:501–517][svdec]; [K/iris_hfi_gen1_command.c:614–630,956–976][kcmd]

The two HFI image planes are compatible with Iris’s single V4L2 memory plane; this difference does not itself require a vendor-style second V4L2 plane. [K/iris_hfi_gen1_command.c:617–627][kcmd]; [K/iris_vdec.c:275][kvdec]

VP9’s reference count is **already accounted for**: stock normally requires nine outputs, and Iris starts with nine and uses firmware minimum count for internal DPBs after discovery. Iris’s reduced client-output minimum in split mode does not mean it allocates only four VP9 references. [S/msm_vidc_buffer_calculations.c:703–758][sbuf]; [K/iris_vpu_buffer.c:2053–2072,2213–2221][kvpub]

Its **wire count assignment differs**, however. Stock split mode sends DPB minimum/actual to OUTPUT and client minimum/actual to OUTPUT2. Iris sends OUTPUT `32/32` and OUTPUT2 the DPB count, `9/9` in D. That merits correction independently of CP initialization. [S/msm_vdec.c:1092–1114][svdec]; [K/iris_hfi_gen1_command.c:979–1007][kcmd]; [D/journal-trial-boot.txt:2383–2385][djournal]

The most consequential later VP9 difference is **DPB lifetime during resolution change**:

- Stock specifically avoids force-releasing VP9 firmware-owned DPBs, marks old buffers for removal, excludes them from future queueing and matches returned buffers by DMA address. It also exempts VP9 reconfiguration flush from an all-DPB-returned validation. [S/msm_vidc_common.c:2005–2038,2070–2075,2540–2553,5098–5143,5436–5439][scommon]
- Iris already preserves queued internal buffers during non-forced destruction. That protection exists. [K/iris_buffer.c:695–734][kbuffer]
- Iris has no retired-generation attribute; new allocations restart their indexes at zero, while gen1 DPB FBD matching uses index plus offset rather than the returned `packet_buffer` address. The address is available in the HFI message. [K/iris_buffer.h:59–65][kbufferh]; [K/iris_buffer.c:586–589][kbuffer]; [K/iris_hfi_gen1_response.c:451–465][kresponse]; [K/iris_hfi_gen1_defines.h:558–581][kdef]
- Returned old DPBs have QUEUED cleared, while generic queueing excludes only queued/pending-release buffers. Consequently, an old-resolution buffer can become eligible for requeue, and retained/new buffers can share tags. **Those are code-path risks; D does not demonstrate either occurring.** [K/iris_hfi_gen1_response.c:526–538][kresponse]; [K/iris_buffer.c:665–674][kbuffer]

Stock also retains mappings for READONLY primary outputs until RELEASE_BUFFER_REFERENCE. Iris gen1 does not handle that event. Current Iris output formats all select split mode, and stock forbids READONLY on OUTPUT2, so this is principally a requirement if adding a primary reference-output path—not evidence that ordinary NV12 OPBs caused the startup failure. [S/msm_vidc_common.c:2625–2628,7109–7122][scommon]; [K/iris_hfi_gen1_response.c:281–290][kresponse]; [K/iris_utils.c:35–40][kutils]

**VP9 power policy and shared UBWC configuration**

Stock Lahaina assigns VP9 **60 VSP cycles/MB**, versus 25 for H.264/HEVC. It applies bitrate factors `170/100 × 21/20`, and forces maximum frequency for VP9 work mode 2, four routes and estimated bitrate above 90 Mbit/s. Iris uses shared 25 cycles/MB and `10/7`; conversely, its VPP calculation omits stock’s division by work route. Therefore “Iris necessarily underclocks VP9” would overstate the comparison—the complete policies differ. [S/msm_vidc_platform.c:57–63][splatform]; [S/msm_vidc_clocks.c:768–805][sclocks]; [K/iris_platform_vpu2.c:43–44][kplatform]; [K/iris_vpu2.c:15–38][kvpu2]

Lahaina also supplies a global LPDDR5 UBWC configuration. That is shared platform setup, not a VP9-only property; k116’s proposed switch is already documented. Since linear output still uses UBWC DPBs, it remains a useful separate experiment after CP initialization. [S/msm_vidc_platform.c:2180–2182,2227][splatform]; [K/iris_hfi_gen1_command.c:925–935][kcmd]; [W/docs/hardware/video.md:448–449,493–494][wvideo]

Use explicit software/hardware decoders and compare actual frame hashes:

```bash
decode_check() {
    local codec=$1 input=$2 pixels=$3 expected=$4
    local base=/var/tmp/iris-check

    timeout 60s ffmpeg -nostdin -v error -threads 1 \
      -c:v "$codec" -i "$input" -an -fps_mode passthrough \
      -pix_fmt "$pixels" -f framemd5 -y "$base.sw" || return

    timeout 60s ffmpeg -nostdin -v error \
      -c:v "${codec}_v4l2m2m" -i "$input" -an -fps_mode passthrough \
      -pix_fmt "$pixels" -f framemd5 -y "$base.hw" || return

    awk -F, '!/^#/ && NF>=6 {
      gsub(/[[:space:]]/, "", $6); print $6
    }' "$base.sw" > "$base.sw.hashes"
    awk -F, '!/^#/ && NF>=6 {
      gsub(/[[:space:]]/, "", $6); print $6
    }' "$base.hw" > "$base.hw.hashes"

    test "$(wc -l < "$base.sw.hashes")" -eq "$expected" &&
    test "$(wc -l < "$base.hw.hashes")" -eq "$expected" &&
    cmp "$base.sw.hashes" "$base.hw.hashes"
}
```
