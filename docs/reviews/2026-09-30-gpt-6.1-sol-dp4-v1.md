**Ranked correctness findings**

**1. P1 — Failed PHY re-enable reaches an unclocked link-register access.**

In [dp_ctrl.c:2066](<scratchpad>/fix/dp4/k/b/drivers/gpu/drm/msm/dp/dp_ctrl.c:2066), reinitialization disables link clocks and powers off the PHY. A subsequent configure or power-on failure returns with those clocks off.

`msm_dp_ctrl_on_link()` then reaches `msm_dp_ctrl_deinitialize_mainlink()` at lines 2470–2494. Deinitialization calls `msm_dp_ctrl_mainlink_disable()` at line 2087; that function unconditionally reads and writes `REG_DP_MAINLINK_CTRL` at lines 341–343.

This is the same register-access hazard documented by the existing [dp_display.c:1553](<scratchpad>/fix/dp4/k/b/drivers/gpu/drm/msm/dp/dp_display.c:1553) guard: an unclocked link-block access can stall the bus.

The new `link_clk_disable()` guard balances clock counts; it does **not** protect hardware accesses before that call.

**2. P1 — A failed forced common-PHY restart can poison `qmp->init_count`.**

[phy-qcom-qmp-combo.c:4482](<scratchpad>/fix/dp4/k/b/drivers/phy/qualcomm/phy-qcom-qmp-combo.c:4482) calls `com_exit(true)` followed by `com_init(true)` and ignores the latter’s return value.

`com_init()` increments `init_count` only for a non-forced initialization, at line 3675, but decrements it **unconditionally on failure**, at line 3772.

A concrete sequence is:

1. DP initialized: common count 1, DP count 1, generic PHY initialization count 1.
2. Deferred switch invokes the forced restart.
3. Restart fails: resources are unwound and common count becomes 0.
4. The caller continues into AUX initialization/PHY programming.
5. Later DP exit decrements the common count to −1.
6. The next non-forced initialization increments −1 and takes the “already initialized” return, without enabling resources.

That is a credible persistent failure until the driver is reprobed or the phone reboots. This defect existed in the mux/orientation restart code; 0136 adds another way to reach it.

Changing the decrement to `if (!force)` is necessary but insufficient. After a forced failure, logical consumers still exist while common resources are disabled. Track resource availability separately, propagate the restart error, and prevent further MMIO until recovery succeeds.

**3. P1 — Deferring until `power_on()` does not make the common reset safe for AUX.**

[phy-qcom-qmp-combo.c:3845](<scratchpad>/fix/dp4/k/b/drivers/phy/qualcomm/phy-qcom-qmp-combo.c:3845) applies the deferred mode by resetting the common block, disabling its clocks/regulators, and initializing AUX again.

An AUX transaction holds `aux->mutex` while writing the command and waiting up to 250 ms. See [dp_aux.c:376](/home/deck/.local/state/rog5-kernel-7.2.7-build-r104/source/drivers/gpu/drm/msm/dp/dp_aux.c:376) and lines 189–204. It does not hold `qmp->phy_mutex` throughout that transaction.

Consequently, a concurrent DPCD/EDID/AUX-device transaction can lose its PHY or completion interrupt during the forced restart. The generic PHY mutex does not serialize that transaction either.

Orientation changes have the same inherited problem: `typec_switch_set()` forces a common restart at combo lines 4524–4533, even while DP is powered. It leaves the software power flags/counts intact after disrupting the hardware.

**Better minimal boundary:** apply pending routing during a controlled PHY **exit/init** cycle, before the next capability read, while MSM has drained and blocked AUX transactions. On this USB2-only side port, the common count normally reaches zero at DP exit, making that boundary much simpler than forcibly restarting an initialized common block.

Moving the reset to `power_off()` alone is insufficient: AUX may remain active after the main link is off. Likewise, `enable_xfers = false` alone does not drain an already executing transfer; use the AUX mutex/deinitialization mechanism.

Keep ordinary link-rate retries as power cycles when routing has not changed. A routing change requires the coordinated reinitialization boundary.

**4. P2 — SAFE/USB requests incorrectly turn the retained four-lane routing into a two-lane limit.**

Combo lines 4570–4582 map a notification without a DP altmode to `USB3_ONLY`, store it in `req_mode`, and publish bus width 2. The physical switch is then deferred while DP is powered.

Thus the stated monitor-sleep notification produces:

```text
applied mode: DP_ONLY, four lanes
requested mode: USB3_ONLY
published limit: two lanes
```

The next four-lane voltage configuration or power-on is rejected, although 0136 deliberately retains the applied DP mode for a pending USB-only request.

For a real C→D request, publishing a two-lane restriction is appropriate. For deferred USB/SAFE, the retained DP routing must remain the effective DP limit, or MSM must explicitly tear the link down before accepting that request.

UCSI makes this more than a sleep-only concern. It calls `typec_set_mode(USB/SAFE)` at [ucsi.c:1318](/home/deck/.local/state/rog5-kernel-7.2.7-build-r104/source/drivers/usb/typec/ucsi/ucsi.c:1318) and line 1362. `typec_set_mode()` supplies an empty-altmode mux state; no common arbitration serializes that producer with the GLINK altmode producer.

Also, GPIO SBU mux lines 75–82 disable AUX for USB/SAFE independently of the QMP deferral. Fixing QMP’s lane limit alone cannot guarantee AUX survives competing UCSI writes.

**5. P2 — 0138’s next-plug-in behavior is broken by stale link capabilities.**

[dp_panel.c:201](<scratchpad>/fix/dp4/k/b/drivers/gpu/drm/msm/dp/dp_panel.c:201) calculates the fallback link rate and applies 0138 only inside:

```c
if (!link_info->rate)
```

Nothing clears that structure before the next capability read. `msm_dp_panel_unplugged()` at lines 434–440 clears the EDID only.

Therefore:

- HBR2 cached → enable `dp_hbr3` → replug: it can remain HBR2.
- HBR3 cached → disable `dp_hbr3` → replug: it can remain HBR3.
- PCON at HBR → native monitor: the native monitor can inherit HBR.
- Rate-table state and capability bits can also survive a receiver change.

This is an inherited cache defect that directly breaks the new parameter’s documented behavior.

The cap also applies to eDP fallback capability handling, despite being described as external-DP-only. Add the same external-DP distinction used elsewhere in this file.

**6. P2 — Error propagation and failed-enable cleanup remain incomplete.**

`msm_dp_ctrl_set_vx_px()` still ignores `phy_configure()` at [dp_ctrl.c:1370](<scratchpad>/fix/dp4/k/b/drivers/gpu/drm/msm/dp/dp_ctrl.c:1370). Its caller already checks the returned error at lines 1390–1394, so this is a straightforward omission.

At the display boundary:

- Link-enable failure returns at `dp_display.c:1503–1507`.
- Stream-enable failure is logged at lines 1510–1512, then execution continues into post-enable processing.
- `msm_dp_display_disable()` returns immediately when `dp->power_on` is false, at lines 730–731.

A failed stream enable can therefore leave the successfully powered PHY/link clocks—and possibly the pixel clock—owned while teardown skips them. A subsequent enable can see `phy_powered == true` and skip the provider’s power-on callback.

Add explicit failure cleanup independent of `dp->power_on`, and return before post-enable processing when stream enable fails. That cleanup must observe finding 1 and the AUX lifetime requirements above.

**7. P2 — The new USB-consumer test reads the wrong ownership state.**

Combo line 4498 reads `qmp->usb_phy->init_count` under `qmp->phy_mutex`, but the generic PHY core updates that count under `usb_phy->mutex`, **after** the provider initialization callback returns.

A mux operation can therefore run between the provider callback and the core count update. It can shut USB down, observe core count zero, and decline to restore it.

The opposite exit window can incorrectly restore a consumer that has just exited.

Do not solve this by taking the generic PHY mutex while holding `qmp->phy_mutex`: provider callbacks already acquire these in the opposite order. Track consumer initialization under the provider mutex, separately from whether USB hardware is currently enabled.

The retained `usb_init_count--` on entry into DP-only also causes underflow if that consumer exits before returning to a USB mode. This is inherited and dormant on the stated side-port topology, where no USB3 consumer initializes.

**8. P2 — Locking the writer does not synchronize the advertised bus-width reader.**

`phy_set_bus_width()` and `phy_get_bus_width()` are plain stores/loads in [phy.h:270](/home/deck/.local/state/rog5-kernel-7.2.7-build-r104/source/include/linux/phy/phy.h:270). MSM’s read at `dp_panel.c:232` does not acquire the provider mutex.

Use `READ_ONCE`/`WRITE_ONCE` for this dynamic attribute. That removes the unannotated data race, but does not solve the logical race between capability discovery and a later pin change. The configure/power-on guards are still needed, together with a defined retraining/reprobe path after the assignment changes.

**PHY caller and count audit**

I checked every `phy_power_on/off` caller in `drivers/gpu/drm/msm/dp`. In the patched tree, they all go through the two new wrappers.

| Path | Assessment |
|---|---|
| Initial main-link enable | Configure/power errors return; failed power-on does not acquire a generic PHY power reference. |
| Link-clock enable failure | New wrapper releases the acquired PHY reference. OPP vote still needs rollback. |
| Main-link reinitialization | Power reference balances; later failure cleanup has the unclocked-access defect above. |
| Main-link deinitialization | Guarded power-off avoids negative power count. PHY exit/init results remain ignored. |
| `off()` | Guarded power-off and clock disable balance successful acquisitions. Link-register accesses need guards. |
| `off_link_stream()` | Same power-count benefit; PHY exit/init results remain ignored. |
| Stream-enable failure | Display-level cleanup can skip still-owned resources. |

The negative **power-count** explanation in 0137 is correct: `phy_power_off()` decrements even when the count is zero, while a later `phy_power_on()` invokes the provider only when the count is zero. The new wrappers address that failure.

They do not address initialization failures. `msm_dp_ctrl_phy_init()` ignores `phy_init()`, yet `dp_display.c:328` records initialization success. Later exit can drive the generic initialization count negative. The internal exit/init pairs have the same unchecked-error problem. These are inherited defects; propagate initialization results and update ownership flags only on success.

The successful runtime-PM power-on/off pair remains balanced. Forced common restarts manage clock/regulator resources independently; their failure is the count corruption described above.

There are also inherited display runtime-PM leaks: repeated connected notifications acquire another reference in `msm_dp_hpd_plug_handle()` while unplug releases only one, and repeated successful detects retain additional references. These should be fixed with explicit persistent-reference ownership, without skipping capability refresh.

**0139 and 5120×1440@60**

For this non-DSC DP path, the admission condition matches resource selection:

- `MAX_HDISPLAY_SPLIT` is **1080**, not the mixer’s 2560-pixel width.
- `dpu_crtc_get_topology()` selects two mixers above that threshold when 3D merge is available and DSC is absent, at `dpu_crtc.c:1445–1447`.
- The SM8350 catalog has 3D merge and a 2560-pixel mixer width. A 5120-wide output exactly fills two mixers.
- Widebus reduces the DP interface/pixel-clock request from approximately 469 MHz to 234.5 MHz.
- The halved admission value is approximately **246.225 MHz**, including the 1.05 factor.
- `dpu_plane_split()` splits a 5120-wide plane because it exceeds the 4096-pixel SSPP rectangle limit. Two 2560-wide rectangles fit.
- The plane clock check uses each rectangle’s destination width, vertical total and refresh rate; the split rectangles do not inherently exceed 460 MHz.
- For ordinary unscaled linear RGB, the parallel multirect path can serve this split. Scaling, YUV, rotation or UBWC can require different resources or fail the plane checks.
- Bandwidth admission uses a 15.5 GB/s threshold. A simple framebuffer is not inherently over that threshold; actual prefill demand and concurrent planes still matter.

0099 still requests approximately 492.45 MHz and clamps the vote to 460 MHz in `dpu_core_perf.c:476`. That does not cause a clock-admission rejection in the performance check; it creates an over-conservative requested vote compared with the split path’s requirement. Stock mixer selection also divides the adjusted clock by mixer count, at [sde_kms.c:3583](/home/deck/Projects/rog-phone-linux-migration/kernel-src/msm-5.4/techpack/display/msm/sde/sde_kms.c:3583).

Therefore the **460 MHz OPP ceiling is not, by itself, a blocker**. Keep it; qualify underruns and fetch behavior before changing the vote calculation or removing the default quarantine.

The condition is appropriate for this experiment, not a universal topology rule: other DSC configurations may select mixers differently. Also correct the description “every atomic check”: DRM invokes mode validation for mode/connector changes, not every plane-only commit (`drm_atomic_helper.c:568–569`).
