**Ranked differences**

| Priority | Difference | Interpretation |
|---|---|---|
| 1 | AMD signals asynchronous clocking and automatically measures MVID; MSM signals synchronous clocking with software MVID/NVID. | Concrete stream difference that a native DP sink could tolerate while the PCON’s clock recovery does not. Best small experiment. Neither mode is inherently invalid. |
| 2 | AMD completes training into video-idle, checks subsequent link stability, and resets/primes its stream FIFO before video. MSM retrains after enabling the pixel clock, discards that result, then enables video. | A transition defect could explain the initial error burst and dark output despite successful earlier training. |
| 3 | AMD normally powers the receiver down/up across full link disable/enable. MSM’s attached modeset path omits that cycle. | Strong explanation for failed recovery after an HBR2 attempt; still possible as an initiating contributor. |
| 4 | Different TU scheduling, including moderation at 1080p60 RGB8. | Worth checking on hardware, but the calculator gives consistent ratios. Failing unmoderated RGB10 weakens a moderation-only explanation. |
| 5 | Polarity and stale MISC/VSC state. | Concrete correctness issues, but no evidence they explain all these failures. The captured wide mode uses positive H/V sync. |

Native-DP HBR2 success reduces suspicion of a universal HBR2 PLL/divider fault. It does **not** exclude electrical margin specific to this hub: equal DPCD swing/pre-emphasis codes do not imply equal AMD and Qualcomm waveforms.

**Clocking, MVID/NVID and MISC**

The Deck-class DCN3.01 resource code constructs a DCN30 stream encoder, whose function table selects the DCN20 unblank and attribute functions: [resource construction:1040](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/resource/dcn301/dcn301_resource.c:1040), [function table:835](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/dio/dcn30/dcn30_dio_stream_encoder.c:835).

AMD builds MISC0 from depth/colorimetry with synchronous-clock bit 0 clear. It seeds `NVID=0x8000`, calculates initial MVID, then enables automatic measurement: [MISC0 construction:365](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/dio/dcn10/dcn10_stream_encoder.c:365), [M/N programming:475](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/dio/dcn20/dcn20_stream_encoder.c:475).

MSM explicitly selects synchronous clocking and static MVID, and sets MISC0 bit 0: [controller configuration:420](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_ctrl.c:420), [MISC programming:497](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_ctrl.c:497).

For full-range RGB using legacy MSA colorimetry:

| Stream | AMD MISC0 | MSM MISC0 | MISC1 |
|---|---:|---:|---|
| RGB8 | `20` | `21` | Normally `00` |
| RGB10 | `40` | `41` | Normally `00` |

Limited-range RGB adds `08`. MISC1 bit 6 selects VSC colorimetry; it does not select HDR by itself.

MSM’s [MSA calculation:2439](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_ctrl.c:2439) gives:

| HBR2 timing | MSM software MVID/NVID | AMD initial MVID/NVID |
|---|---:|---:|
| 148.5 MHz | `17985 / 65400` | `9011 / 32768` |
| 285 MHz | `34580 / 65520` | `17294 / 32768` |

MSM’s ratios are exactly `148500/540000` and `285000/540000`. AMD’s initial values have integer rounding and subsequently use measurement. **MSM’s HBR2 NVID multiplier is correct in this calculation.** Removing it would double the reconstructed pixel rate.

Widebus halves the interface clock to 74.25 or 142.5 MHz, while MSM deliberately passes the original pixel clock to MSA calculation: [on_stream:2520](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_ctrl.c:2520), [MSA call:2572](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_ctrl.c:2572). Consequently, no additional widebus MVID doubling belongs here. Stock’s doubling compensates for reading the already-halved interface-clock M/N registers.

These calculations establish intended values, not the actual transmitted MSA or clock accuracy.

**Timing, HSP/VSP and VSC**

Both stacks derive MSA totals, active start, sync widths and active dimensions equivalently for these progressive, borderless modes: [AMD timing:419](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/dio/dcn10/dcn10_stream_encoder.c:419), [MSM timing:731](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_panel.c:731).

The captured wide mode has flags `0x9`: **+HSync, +VSync**. Expected MSM registers are:

```text
TOTAL:        04a40fa0   # 1188 × 4000
START:        00690070   # VSTART=105, HSTART=112
WIDTH/POL:    000a0020   # VSW=10, HSW=32, positive polarity
ACTIVE:       04380f00   # 1080 × 3840
```

MSM computes negative-polarity flags correctly in [bridge_mode_set:1585](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_display.c:1585), but copies them to the panel only with `dp_polarity=1`: [set_mode:664](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_display.c:664). Default-off therefore forces positive polarity initially and can retain stale values after toggling. This should eventually become unconditional assignment, but fixing it cannot change this positive-sync mode. The PHY TX-polarity knobs in 0097 are separate from HSP/VSP.

AMD enables VSC colorimetry when DPCD revision/capability and quirks permit it, including RGB, and sends HDR metadata separately: [capability selection:7792](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/amdgpu_dm/amdgpu_dm.c:7792), [VSC/HDR transmission:429](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/dio/dcn30/dcn30_dio_stream_encoder.c:429).

MSM’s shown colorimetry VSC path is YUV420-only: [dp_panel.c:776](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_panel.c:776). Its RGB stream normally relies on legacy MISC. That is a legitimate SDR path; absent HDR/VSC cannot by itself explain dark RGB8 SDR. Capture `0x2210` and AMD’s actual MISC/VSC before attributing the difference to VSC.

MSM also only clears depth bits when rebuilding MISC, leaving other fields susceptible to stale state. Confirm MISC1 bit 6 is clear during the RGB8 test.

**Training, stream enable and D3→D0**

AMD’s relevant sequence is:

1. Connect/configure the stream encoder before training, allowing SST idle afterward.
2. Enable link PHY and request receiver D0.
3. Train, disable receiver training, select source video-idle.
4. Normally wait 5 ms and check for link loss.
5. Program stream attributes/M/N, disable video, reset DIG/steer FIFO, prime for 100 μs, then enable video at a frame boundary.

Evidence: [pre-training setup:1646](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/link/protocols/link_dp_training.c:1646), [training exit:1601](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/link/protocols/link_dp_training.c:1601), [idle/check:1510](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/link/protocols/link_dp_training.c:1510), [FIFO/reset/unblank:514](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/dio/dcn20/dcn20_stream_encoder.c:514).

MSM leaves successful initial training active until `on_stream()`, enables the pixel clock, forces another training pass on fresh enable, discards its result, clears training, programs MSA/TU and writes SEND_VIDEO: [training deferral:2412](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_ctrl.c:2412), [stream sequence:2541](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_ctrl.c:2541).

Training-disable success is also discarded; mainlink-ready failure does not change the return value, and atomic enable ignores stream-enable failure. Therefore the current success log is weaker evidence than it appears.

A simple added delay is not yet justified: MSM already waits the receiver’s EQ interval after training-disable. With captured `0x0e=84`, the normal helper gives **16 ms**, although effective extended receiver caps must also be checked.

**Yes, AMD normally does D3→D0 on a full modeset that disables/re-enables this link.** Disable writes D3 before shutting the link output down; enable writes D0 after enabling it: [link_dp_phy.c:58](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/link/protocols/link_dp_phy.c:58). There are seamless/synchronized-training and receiver-power quirks; this is not a guarantee for every atomic update. The shown keep-powered dongle quirks are for VGA converters: [capability code:316](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/amd/display/dc/link/protocols/link_dp_capability.c:316).

MSM’s attached shutdown selects `msm_dp_ctrl_off()`, which omits D3, and fresh enable omits D0: [shutdown selection:732](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_display.c:732), [ctrl_off:2625](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_ctrl.c:2625), [enable:1473](/home/deck/.local/state/rog5-kernel-7.2.7-build-r94/source/drivers/gpu/drm/msm/dp/dp_display.c:1473). Keep power recovery as a separate experiment.

The requested patches do not close these differences: 0093/0094 affect depth/converter controls; 0095/0096 expose diagnostics; 0097/0109 affect selected PHY overrides; 0098 repairs bandwidth validation; 0099–0101 affect DPU votes. **0110 must be disabled for this test**: it caps converter `link_info.rate` when capabilities are read, so changing the parameter afterward alone may leave the cached HBR cap.

**DPCD `0x3047=01`**

I cannot assign a defensible standard meaning to this byte. Neither r94’s DP definitions nor the [current upstream DPCD header](https://raw.githubusercontent.com/torvalds/linux/master/include/drm/display/drm_dp.h) defines `0x3047`; I found no corresponding AMD display programming.

The capture proves that it **reads as `01` during working output**. It could be undocumented converter state/status or an implementation-specific register, but calling it an HDMI-enable, scrambling or lock bit would be speculation. Read it across disconnected, trained-idle, working SDR/HDR and failed states; do not copy it as a write based on this snapshot.

Also, the working Deck reads `303B=00`. That reinforces that this hub’s advertised PCON-status area is not presently a reliable picture-success gate.

**Pass/fail test plan**

1. **Establish comparable SDR controls.** Use explicit 1080p60 RGB8, HDR off, fixed orientation, `dp_polarity=1`, unchanged SSC/drive settings. Set `dp_pcon_max_rate=0` before capability discovery; ensure no other rate cap prevents HBR2. Verify HBR picture first. Record exact timing, effective depth, clocks, MSA/MISC/TU and both training passes.  
   **Pass:** visible HBR baseline. **Invalid experiment:** fallback rate, wrong depth, stale converter cap or unsupported capture.

2. **Compare synchronous versus asynchronous HBR2.** Start each arm from the same recovered state, with `dp_async_msa=0` versus `1`. Use normal scanout initially. For RGB8, expect MISC `21→20`, controller clock-mode bit `1→0`, unchanged M/N, and TU start delay `38→45`; TU boundaries remain unchanged. Repeat three times.  
   **Pass:** repeatable visible output at actual HBR2×2 RGB8. **Fail:** still dark with the expected programming verified. Training or video-ready alone is not a pass.

3. **Separate DPU and denominator effects.** Repeat the successful/failed arm with RGB8 TPG and **widebus off**, then normal scanout with widebus off/on. If asynchronous signalling fails, independently test a fixed `NVID=0x8000` nominal MVID calculation before attempting automatic generation.  
   **Pass:** visible TPG establishes usable downstream transport. A denominator-only improvement identifies an M/N compatibility issue; a widebus-only improvement identifies interface/clock coupling.

4. **Test transition and recovery independently.** Check the second-training and training-disable results, plus post-disable link status. Separately compare normal power handling against orderly idle/shutdown → checked D3 → ≥200 μs → checked D0 → 1–2 ms wake → restore `3050..3052` → train/enable. Attempt HBR recovery after an HBR2 failure without reboot or reconnect.  
   **Pass:** repeatable HBR2 picture or independently repeatable recovery. Report a recovery-only improvement separately.

5. **Expand to the captured wide timing.** First 3840×1080p60 RGB8 SDR, then RGB10/HDR only after actual encoding/depth and VSC capability are captured on the Deck. Track `3047` as an observation.  
   **Pass:** stable visible output through repeated HBR↔HBR2 modesets, with correct effective stream settings and successful recovery. If all arms fail, obtain powered source-register captures or wire-level MSA evidence; the current snapshots cannot distinguish remaining PCON clock-recovery, source-transition and hub-specific PHY hypotheses.
