# Brief: is kernel r110 fit to become the FALLBACK (safe-r9) kernel?

Phone: ASUS ROG Phone 5 (SM8350), mainline Linux 7.2.7 + patch series patches/linux-7.2.7/series.production (through 0147). Repo: /home/deck/.local/state/rog5-prod-boot-20260923 (HEAD). Built tree: /home/deck/.local/state/rog5-kernel-7.2.7-build-r110/source (build PASS).
Boot chain: signed slot-B wrapper -> loader picks the selector's primary (try-once) or the fallback bundle (initramfs/persistent-slotb-loader-init, tools/persistent_trial_state). The fallback is booted only when the primary failed (or its trial record is failed/pending), so it must be the most conservative, reliable kernel we have.
Current fallback safe-r8 = kernel build r69 (series up to ~0069/0070, weeks old; lacks speaker DSP 0121-0124, DP fixes, 0144/0146, 0116 SEA logging, etc.) + DTB usbbtm-r2 + memx. Proposed safe-r9 = kernel r110 Image + DTB r9 (compose feature list touch,bluetooth,cpuidle,gpubw,bwmon,ddrscale,periph,audio,slpi,usbotg,osi,aoss,qupicc,dp,l3,skin,acd,cpucap,usbbtm,mic,usbbtmtc,memx; sha 4a919c15...) + a fallback ramdisk (no trial descriptor; same init as the default, v2 restore).
Field record of r110 (and r108/r109 which differ only by 0145-0147): booted and committed healthy several times on 2026-09-30 (r204/r205/r206/r207/r208); Wi-Fi, speakers with protection DSP (0 amp errors), 4-lane DP incl. 5120x1440@60, bottom USB-C stage B, s2idle not yet re-tested on these builds; charge policy, memx; one boot-time ADSP DP race handled in userspace. Test logs: test-results/2026-09-30-*.md, docs/reviews/2026-09-30-*.md.

Please (read-only) assess r110 as a FALLBACK kernel:
1. Patches added since r69 (roughly 0070-0147, list them from series.production) that could make a boot fail or hang early, or brick recovery (SSH/Wi-Fi/UFS/persistent root), especially: 0144 (PDC SPI config writes for every PDC IRQ, probe fails if reg[1] present but unmappable), 0146 (TCPM), 0136-0139/0145/0147 (DP/PHY), 0121-0124 (cs35l45 DSP firmware at boot), 0125-0127 (q6asm), 0130-0135 (DPU), 0140-0143 (USB), 0116 (SEA), 0099 (DPU clock floor), and anything that depends on userspace/rootfs state that a fallback boot may not have.
2. Features in DTB r9 that are risky for a fallback (usbbtmtc enabling QUP wrapper 1 at boot, dp, audio, slpi) — should the fallback DTB drop any (e.g. compose without usbbtmtc/dp/audio) to maximise the chance of a working SSH/Wi-Fi recovery boot? Weigh: a fallback that lacks features vs one that fails the same way as the primary (common-mode failure: if a bug in r110 breaks the primary, a fallback with the same kernel breaks too). Recommend whether to (a) use r110 as fallback, (b) use r110 with a reduced DTB, or (c) keep r69/safe-r8 — with reasons.
