The main defects are in **session carry**. I found no concrete implementation defect in patch 0151, the SWIOTLB change, or the d13 composer. Their evidence has limits, especially firmware ownership across kexec and recovery paths that the tests never triggered.

This review used `stable-2026-10-01`, the supplied snapshots, and the patched k113 source. No files were changed. Live phone reads were blocked by the environment’s network restriction, so exact attribution of every shmem object remains unresolved.

**Task 1 — findings, ranked by severity**

1. **P1: session carry can substantially delay a security hand-back or shutdown.**

   `--timeout=8` bounds only the final polling loop. Collection happens first; each D-Bus call can take three seconds, subprocess calls generally ten seconds, and quit requests run serially before the deadline starts. Thus eight seconds is not the total stop budget. Both compositor services invoke this from `ExecStop`, and the desktop-mode hand-back waits synchronously for GNOME to stop. GNOME’s old desktop can therefore remain visible while carry waits for unresponsive apps. Shutdown also inherits this delay. [rog5-session-carry:108](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-session-carry:108), [rog5-session-carry:236](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-session-carry:236), [GNOME drop-in:5](/home/deck/.local/state/rog5-prod-boot-20260923/configs/systemd/rog5-gnome.service.d/60-rog5-session-carry.conf:5), [rog5-desktop-mode:122](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-desktop-mode:122).

   **Fix:** use one monotonic deadline covering collection, quit requests and waiting; give every operation only the remaining budget. Bound the stop helper explicitly in systemd. For lock/unplug hand-back, prioritize hiding the desktop: precollect while the session is running, then allow only a short bounded close phase. Only an explicit switch should arm restoration; ordinary shutdown and recovery stops should not.

   **Verify:** unresponsive D-Bus applications, many applications, unavailable user manager, shutdown/reboot, and Phosh crash with `Restart=always`. Measure compositor disappearance, not just helper completion.

2. **P2: apps are restored into locked Phosh without an unlock check.**

   Restoration is triggered by `graphical-session.target`, waits two seconds, then launches apps. It checks neither the destination session nor its lock state. Phosh deliberately starts locked, including after GNOME hand-back. A previously open browser, Steam or media app can consequently start network activity, playback or other work before authentication. This does **not establish a PIN bypass**, but it defeats the expectation that hand-back produces a locked, quiescent phone. [restore unit:4](/home/deck/.local/state/rog5-prod-boot-20260923/configs/systemd-user/rog5-session-restore.service:4), [rog5-session-carry:279](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-session-carry:279), [Phosh service:1](/home/deck/.local/state/rog5-prod-boot-20260923/configs/systemd/rog5-phosh.service:1).

   **Fix:** defer Phosh restoration until the new, active local session is confirmed unlocked. Bind the record to an explicit switch token and destination session; revalidate immediately before launching. Cancel pending restoration when that session stops. Preserve the existing explicit-stop behavior: `Restart=always` does not override a systemd stop request.

3. **P2: “apps with windows” includes background applications in scopes.**

   Every running `app-gnome-…scope` with a visible desktop file is collected without checking for a window. Only applications discovered solely through D-Bus receive the window test. A desktop file being visible says nothing about whether its application currently has a window. For example, Steam remaining in its scope after its window closes can still be terminated and reopened. [rog5-session-carry:216](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-session-carry:216).

   **Fix:** intersect scope/application identities with the compositor’s current toplevel inventory. If background application carry is intentional, make it an explicit option rather than describing this as window-only collection.

4. **P2: record validation and “once only” consumption are incomplete.**

   Valid JSON with an invalid shape escapes the exception handling: a list causes `AttributeError`; a nonnumeric `saved` value causes `ValueError`; invalid application elements cause type errors. I reproduced these with the actual functions and an in-memory record. A failed unlink is ignored, so a readable record can be launched again on a subsequent restore. Reading the record and deleting it are also separate operations. [rog5-session-carry:282](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-session-carry:282).

   **Fix:** impose a small size limit, validate the format, object shape, finite timestamp, application count and string IDs; reject symlinks and unexpected ownership. Atomically claim the record under a lock before launching, and refuse restoration if consumption fails. Create the directory/file privately and use a unique temporary file.

   **Security assessment:** execution remains under `phone`, and launch uses an argument vector rather than shell evaluation. I found no root escalation here. The practical issues are malformed-state failures, unintended launches and duplicate restoration.

   Separately, `save --close --timeout 0` can reference an uninitialized `left`; initialize it and validate timeout arguments. [rog5-session-carry:246](/home/deck/.local/state/rog5-prod-boot-20260923/scripts/device/rog5-session-carry:246).

5. **P2: the checkpoint overstates live validation.**

   “All installed and tested on the phone” and the unconditional description of clean app reopening exceed the evidence: current state explicitly says the first live switch with apps is pending. Likewise, the speaker quick-stop test recorded **zero reloads**: it validates prevention of the observed quick-stop wedge, but not forced recovery after another missed pause. The GPU report also leaves the live hang/recovery test outstanding. [checkpoint:3](/home/deck/.local/state/rog5-prod-boot-20260923/docs/history/2026-10-01-stable-checkpoint.md:3), [checkpoint:38](/home/deck/.local/state/rog5-prod-boot-20260923/docs/history/2026-10-01-stable-checkpoint.md:38), [current-state:30](/home/deck/.local/state/rog5-prod-boot-20260923/docs/current-state.md:30), [quick-stop result:4](/home/deck/.local/state/rog5-prod-boot-20260923/test-results/2026-10-01-k112-speaker-quickstop-and-fallback-k111.md:4), [GPU report:73](/home/deck/.local/state/rog5-prod-boot-20260923/test-results/2026-10-01-desktop-idle-gpu-gmu-hang.md:73).

   **Fix:** say “installed; validation status below,” label carry as offline-tested/live-switch-pending, and distinguish speaker wedge prevention from reload-path validation. The bundle identities, +650 MiB arithmetic, fallback rehearsal, graphics figures and final shell choice are consistent with the reports.

**Huge shmem is not demonstrated waste.** The platform loader deliberately sets `within_size`; it previously reduced quick-settings dropped frames from 37 to 8. Ordinary tmpfs defaults to `huge=never`; the production overlay upper layer is ext4, while the 2 GiB tmpfs upper applies only to volatile-root mode. Switching these dense allocations to 4 KiB pages should not recover their payload memory. Sparse memfd/shared mappings remain worth investigating.
