## Round 1 answer

**Blocking issues remain.** I read all five commit messages and the trial-debug analysis. The supplied patches match the five commits, and all 17 changed base files match k114. Locations below refer to the supplied patched iris directory.

1. **[P1] Runtime PM can still deadlock against the IRQ thread — [iris_probe.c:332](drivers/media/platform/qcom/iris/iris_probe.c:332), `iris_hfi_queue.c:177`.**  
   Moving `disable_irq()` outside `core->lock` fixes that mutex cycle, but leaves this one:
   - Runtime suspend enters `RPM_SUSPENDING` and waits in `disable_irq()`.
   - The IRQ thread waits for `inst->lock`.
   - A command holds `inst->lock` and calls `pm_runtime_resume_and_get()`, which waits for suspend to finish.

   There is also an IRQ-thread variant: sequence-change/EOS response handling itself calls the session-command wrapper and can wait for an overlapping suspend that is synchronizing that same IRQ. These waits are unbounded. Runtime-PM acquisition and IRQ synchronization need coordination beyond moving the core mutex.

2. **[P1] Close frees firmware-owned DMA before containment establishes quiescence — [iris_vidc.c:306](drivers/media/platform/qcom/iris/iris_vidc.c:306), `iris_core.c:225`.**  
   Containment wakes instances **before** PAS shutdown. A woken process can close immediately: vb2 releases client mappings, END is rejected because `core->fatal` is set, and close forcibly frees internal buffers (`:312–313`). At that point firmware can still run.

   The EOS allocation has the same problem at `:318`: `!fw_held` means shutdown has not failed yet, not that END or shutdown succeeded. It also frees EOS after an END timeout or submission failure. Even after a recorded PAS failure, internal buffers remain unconditionally freed; only EOS receives the retention check.

   Close needs a firmware-ownership barrier, with allocations retained until successful END or confirmed shutdown.

3. **[P1] An IRQ during the first failed boot can dereference NULL HFI operations — [iris_hfi_common.c:116](drivers/media/platform/qcom/iris/iris_hfi_common.c:116), `iris_core.c:335`.**  
   Power-on enables the IRQ before firmware boot, but `hfi_sys_ops` is initialized only after boot and hardware-mode switching succeed. An early firmware watchdog can leave the thread pending on `core->lock`. The 0154 error unwind drops that lock before synchronizing the IRQ, allowing the thread to call `core->hfi_sys_ops->sys_hfi_response_handler()` while the pointer is still NULL. Initialize the operations before enabling the IRQ.

4. **[P1] The init-error unwind bypasses failed-PAS containment — [iris_core.c:363](drivers/media/platform/qcom/iris/iris_core.c:363).**  
   `error_unload_fw` still ignores `iris_fw_unload()`’s return, powers off, frees queues/SFR, and declares DEINIT. Thus an authenticated firmware boot failure followed by failed PAS shutdown still loses its power and DMA mappings.

   It also lacks a `fw_held` check when reacquiring the mutex, so containment can establish retention during the unlocked window and this unwind can subsequently undo it. This retained 0154 path must use the same shutdown-result policy as `iris_core_teardown()`.

5. **[P1] Removal can leave newly scheduled containment work using freed core memory — [iris_probe.c:203](drivers/media/platform/qcom/iris/iris_probe.c:203).**  
   `cancel_delayed_work_sync()` runs while the IRQ can still execute. A fatal IRQ arriving after cancellation can schedule the work again before `iris_core_deinit()` synchronizes the thread. Removal never cancels that new work before destroying the mutex and releasing devm core memory.

   A non-watchdog PAS failure additionally leaves the IRQ enabled after containment’s final `enable_irq()`. Stop the IRQ producer and prevent further scheduling before the final cancellation.

6. **[P1, gen2] The closing guard does not protect gen2’s released context — [iris_hfi_gen2_response.c:933](drivers/media/platform/qcom/iris/iris_hfi_gen2_response.c:933).**  
   Gen2 gets the new kref but never checks `inst->closing`. While generic close releases the m2m context before CLOSE, gen2 buffer responses still traverse its lists, session errors call `iris_vb2_queue_error()`, and settings changes access its queues. The reference preserves `inst`, not `m2m_ctx`.

   Gen2 needs the same restricted closing-response dispatch as gen1. Its close command also never sets `end_sent`; after `iris_kill_session()` sends CLOSE and frees the command packet, final close returns `-EINVAL` instead of waiting for that pending acknowledgement.

7. **[P2] Commands after END can discard its legitimate acknowledgement — [iris_hfi_gen1_command.c:263](drivers/media/platform/qcom/iris/iris_hfi_gen1_command.c:263), `iris_vidc.c:238`.**  
   If the first decoder streamoff’s FLUSH fails, `iris_kill_session()` sends END and sets `end_sent`. The second streamoff can still enter STOP/RELEASE because LOAD_RESOURCES remains set. It replaces `expected_msg` and reinitializes the shared completion, so END_DONE is discarded as unexpected—or its already-recorded completion is erased.

   Final close sees `end_sent`, sends nothing, and waits on that reused completion until timeout. Prohibit further session transactions after END and retain its acknowledgement separately.

Other requested checks:

- The new session wrapper correctly balances runtime-PM references on failed resume. The old wrapper’s erroneous put remains reachable through gen2.
- I found no additional direct `core->lock`/`inst->lock` inversion in diagnostics or instance failure notification. Gen1 lookup references and closing guards protect the CPU-side instance/context lifetime.
- Normal IRQ depths balance: probe/off **1**, powered **0**, successful containment **1**. Watchdog handling retains depth **1**. Failed ordinary PAS shutdown leaves depth **0**, as noted above.
- The ACTIVE guard and removal of decoder STOP’s blanket completion do not introduce an additional buffer-return hole: the queue-specific stop callback drains its ready list.
- Gen1 expected response opcodes, including SESSION_INIT and RELEASE_BUFFERS, match stock. `init_attempt` is suitable for identifying firmware generations across runtime collapse.
- Debug property `0x1`, field order, mask `0x18`, and queue mode `1` match stock. Iris sends **24 bytes** versus stock’s **28-byte** declared size, which includes an unwritten trailing word; host sources alone do not establish that difference as a firmware rejection.
- EOS allocation through `core->dev` and `lower_32_bits()` fit this platform’s DMA mask. Its release timing is the blocker.

Read-only review completed; no files changed and no build or live test run.
## Round 2 answer

**Blocking findings remain.** Reviewed HEAD `cb91957`; its diff matches 0162. I found no separate confirmed regression introduced by 0162, but ownership and failure-path gaps remain.

1. **[P1] Close still releases client DMA after failed containment — [iris_vidc.c:350](drivers/media/platform/qcom/iris/iris_vidc.c:350).**  
   `flush_delayed_work()` waits for containment to finish; it does not establish that PAS shutdown succeeded. If shutdown fails and sets `fw_held`, close nevertheless calls `v4l2_m2m_ctx_release()` at line 353, releasing client mappings while firmware may still access them. The new retention gate protects only internal buffers and EOS.

   There is also a race: `fatal` can become true after the single check, including during streamoff inside context release. Close then releases client buffers without waiting for containment. Finding **#2 is only partially resolved**.

2. **[P1] An earlier authenticated-load failure still bypasses the checked PAS unwind — [iris_firmware.c:105](drivers/media/platform/qcom/iris/iris_firmware.c:105), [iris_core.c:327](drivers/media/platform/qcom/iris/iris_core.c:327).**  
   After successful authentication, a `qcom_scm_mem_protect_video_var()` failure calls PAS shutdown and ignores its result. `iris_fw_load()` returns an error, so core init takes `error_power_off` with `unload == false`, powers off and frees queues without recording `fw_held`. SM8250 has a protection configuration, so this path applies here.

   0162 fixes the previously reported **`error_unload_fw` branch**, but this earlier path retains the same shutdown-policy hole.

3. **[P2] Failed-PAS removal still permits IRQ handling after mutex destruction — [iris_probe.c:215](drivers/media/platform/qcom/iris/iris_probe.c:215).**  
   For a non-watchdog PAS failure, deinit’s final `enable_irq()` leaves depth **0** and the core powered. Removal then destroys `core->lock` before devm frees the IRQ. Another interrupt can use that destroyed mutex. This is observable with debug mutexes; the inspected k114 configuration disables them. The gen1 containment-work scheduling race itself is fixed.

Status of the original seven findings:

| Finding | Result |
|---|---|
| **#1 PM/IRQ deadlock** | **Resolved.** PM callbacks no longer synchronize the IRQ; power-off uses `disable_irq_nosync()`. |
| **#2 Close DMA ownership** | **Partial.** Internal/EOS retention fixed; client-buffer gap above remains. |
| **#3 NULL HFI operations** | **Resolved.** Operations initialized before IRQ enable, with a thread-side NULL guard. |
| **#4 Init-error PAS unwind** | **Reported branch resolved.** Failed unload retains power/memory; existing `fw_held` is respected. Earlier load-error gap remains above. |
| **#5 Removal work UAF** | **Resolved for gen1 scheduling.** Retained-state IRQ caveat above remains. Gen2 still schedules directly at `iris_hfi_gen2_response.c:290`, bypassing `removing`. |
| **#6 Gen2 closing-context UAF / pending CLOSE** | **Unchanged intentionally**, as the commit message states; not used on SM8350. |
| **#7 END acknowledgement overwritten** | **Resolved for gen1.** Commands are rejected after `end_sent`; expectation/completion bookkeeping is preserved. |

A pending ordinary IRQ temporarily contributes another disable, balanced by the thread’s final enable. I found **no remaining IRQ-thread synchronization inside a runtime-PM callback or while holding `core->lock`/`inst->lock`** in these gen1 paths.

Close’s new flush runs without `inst->lock`, avoiding a containment-lock deadlock. Its END return handling preserves a pending acknowledgement, distinguishes timeout/fatal wakeups, and intentionally accepts END error replies, consistent with the OEM close handler. The internal/EOS release predicate and init-unwind `fw_held` branch are otherwise sound. The debug packet is now 28 bytes.
