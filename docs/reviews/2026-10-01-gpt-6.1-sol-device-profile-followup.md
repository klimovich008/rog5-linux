# GPT-6.1-Sol review: device profile follow-up (2026-10-01)

Answer to [the brief](2026-10-01-device-profile-followup-brief.md) (codex exec, gpt-6.1-sol, reasoning high, read-only sandbox). Absolute links were shortened to repository paths.

## Answer

The fixes are **not complete**. I found two P1 issues in new-root construction/installation, but no new initramfs blocker for a RAM trial using the existing reference root.

1. **P1 — User-file installation still follows predictable temporary symlinks.**  
   [rog5-install-userspace:63](../../scripts/device/rog5-install-userspace) uses `$dst.rog5-new.$$`. The `user-file` branch calls this as root inside the phone user’s writable home. A precreated symlink makes `cp`, `chmod`, and `chown` affect an arbitrary target. The `mktemp` change correctly fixes the manifest temporary file, but leaves this second exposure.  
   **Fix:** perform home-directory installation as the target user, including parent creation and temporary-file operations. Use securely created temporary files for privileged destinations.

2. **P1 — Creating the persistent seal invalidates its own tree hash.**  
   [rog5-build-rootfs:340](../../scripts/host/rog5-build-rootfs) hashes the tree, creates `.rog5-persistent-seal`, then verifies it. Although the seal file is excluded, [persistent-root-tool.py:254](../../scripts/host/persistent-root-tool.py) hashes the root directory’s size, nanosecond mtime, and link count. Creating the file changes directory metadata, so verification can fail with `sealed tree changed: tree_sha256`.  
   **Fix:** create the excluded seal placeholder before computing the persistent hash, then overwrite it in place without changing the parent directory. Verify the resulting seal.

3. **P2 — Excluding `boot/rog5-linux` does not preserve the seal through bundle insertion.**  
   [rog5-build-rootfs:389](../../scripts/host/rog5-build-rootfs) deletes and recreates that directory. Its parent `/boot` remains hashed, including mtime, size, and link count. First insertion and subsequent replacement therefore still invalidate the recorded tree identity. Boot’s limited checks can hide this because they do not recompute the tree.  
   **Fix:** establish `/boot/rog5-linux` before sealing and replace only its contents, preserving the hashed parent metadata. Verify the seal after `boot` and before `image`.

4. **P3 — The state stager lacks the claimed post-format allocation proof.**  
   [stage-persistent-service-state.sh:299](../../scripts/device/stage-persistent-service-state.sh) correctly adds `nodiscard`, but proceeds directly to loop setup. Unlike the overlay stager, it has neither a second `fallocate` nor the allocated-bytes check. `nodiscard` addresses the original discard defect; the stated stronger fix remains incomplete.  
   **Fix:** add the same post-format allocation and `stat` proof used by the overlay stager.

For the brief’s three questions:

- **Reference regression:** all seven reference-profile renderings are byte-identical to their working-tree sources. Default and explicit reference-base selection retain every old verifier, kexec, and key hash pin. The configured reference archive matches those pins. The persistent UUID, lower-cache profiling, partition-fit check, FEX ownership change, and installer variable rename look correct.
- **Alternate-base trust:** acceptable **when the caller deliberately trusts the pinned archive as executable recovery code**. Its hash binds the verifier, kexec, and key bytes; deriving the signing check from that key avoids imposing the reference key. A 32-byte key check alone does not qualify the alternate verifier’s behavior or recovery capabilities. Host bundle verification cannot prove those target properties.
- **Reference RAM trial:** I found no new boot-path blocker against the existing reference root and accepted 182 GiB overlay. The sealing findings block or invalidate newly constructed roots; they do not change the existing reference lower filesystem.

Validation included 11 read-only profile tests, syntax checks under both pinned recovery and target BusyBox binaries, reference archive/member hashes, and in-memory reproductions of the directory-metadata hash changes. No files were modified and no device was contacted.
## Disposition

1. **Fixed.** `rog5-install-userspace` installs files in the user's home as
   the user (`runuser`) on a running system; in a staged root it refuses any
   symlink below the home and writes through a `mktemp` name. System files
   also go through `mktemp` names. New test: a planted link is refused and
   nothing is written behind it.
2. **Fixed.** The seal step creates an empty `.rog5-persistent-seal`
   placeholder before hashing and writes the seal into it in place, so the
   root directory's metadata is final when hashed; `verify` passes (test).
3. **Fixed.** The seal step creates `/boot/rog5-linux` before hashing; the
   boot step only replaces its contents and verifies the seal afterwards
   (tests: seal, boot, boot again).
4. **Fixed.** The state stager allocates again after formatting and refuses
   an image whose allocated bytes are below its size, like the overlay
   stager.

On question 2 (alternate recovery bases): accepted as stated. A non-reference
base is executable recovery code the owner chooses to trust; the packagers
bind the signing check to its key member, and the guide lists the recovery
base as a missing piece until a builder is published.
