Read-only review completed; I modified no files and ran nothing against the phone. **Verified** means source evidence; **inference** means the hardware or incident conclusion remains unproved.

References below use **K** = the named r98 kernel tree, **R** = the repository, **S** = stock msm-5.4, and **W** = the brief’s `work/` directory.

1. **Reset / p1a–p1b — agree with the mechanism; “confirmed cause” is too strong.**

   **Verified:** legacy glue treats a non-NULL `dwc->xhci` as host mode, then dereferences its driver data without checking it (`K/drivers/usb/dwc3/dwc3-qcom-legacy.c:303,329,451`). Completed unbind clears driver data (`K/drivers/base/dd.c:602`); the platform device survives. Thus the described pre-hook can reach a NULL `hcd`. Both guards are appropriate; the other glue has the same defect (`K/drivers/usb/dwc3/dwc3-qcom.c:241`).

   **Inference:** the journal ending at suspend entry plus panic settings makes this a strong explanation, not proof without an oops/pstore record. The repository’s current pre-hook only records devices; its unbind is in `post` (`R/scripts/device/rog5-usb-sleep:32,44`), so the incident used different bytes.

   **Better:** defensively check `root_hub` too. Concurrent removal remains a lifetime concern: xHCI removal frees the HCD (`K/drivers/usb/host/xhci-plat.c:453,461`), and `usb_hub_find_child()` returns an unreferenced child (`K/drivers/usb/core/hub.c:6505`). NULL checks alone do not solve arbitrary concurrent teardown; the normal suspend path relies on stable roles and PM ordering.

2. **Femto / p2 — agree.**

   **Verified:** `usb_add_hcd()` requests `PHY_MODE_USB_HOST_SS`; the primary HCD acquires the named USB2 PHY (`K/drivers/usb/core/hcd.c:2830`; `core/phy.c:92`). Femto accepts and stores that mode. Consequently, the existing exact-HOST suspend check misses it, and 0113 wrongly pulses POR for HOST→HOST_SS while missing HOST_SS→DEVICE (`K/drivers/phy/qualcomm/phy-qcom-snps-femto-v2.c:187,263,271`). p2 fixes both; the enum ranges are contiguous (`K/include/linux/phy/phy.h:26`).

   **Given the reported `power/control=on`:** ordinary runtime suspend is forbidden. Probe explicitly calls `pm_runtime_forbid()` (`femto-v2.c:655`), and its PM table contains only runtime callbacks (`:547`). Thus correcting AUTO_RESUME will not itself activate that path. I did not independently verify the phone’s current sysfs value.

3. **Delayed enumeration / p3 — agree with basic lifetime handling; better to revise before adoption.**

   **Verified:** the scheduled-work reference is balanced by completion, failed scheduling, or successful cancellation (`W/p3.diff:60,78,91`). `hub_quiesce()` marks quiescing before cancellation, and disconnect cancels before freeing ports (`K/drivers/usb/core/hub.c:1402,1816,1836`). The worker takes no device mutex, so cancellation while holding the hub lock introduces no evident lock deadlock.

   The synthetic `change_bits` route works even with `portchange=0`: `port_event()` recognizes the bit and reaches `hub_port_connect()` (`hub.c:5770,5883,5713`). `kick_hub_wq()` supplies its own hub/interface references, but checks **disconnected**, not **quiescing** (`:708`). A racing kick can queue an event that later exits without enumeration.

   **Wrong because:** `u8 enum_retries` wraps forever if the unsigned parameter exceeds 255 (`W/p3.diff:24,71,74`). Also, “VBUS is externally controlled” does not establish the no-PPC predicate: xHCI derives it from `HCC_PPC` (`K/drivers/usb/host/xhci-hub.c:265`). The experiment might never trigger.

   **Better:** default off or scope to this controller; bound/read the parameter consistently; retry selected transport failures; discard stale pending bits after success/disconnect; define resume handling for canceled retries. Three retries are bounded at the default, but each repeats the entire enumeration sequence. The in-loop single retry is simpler and keeps existing locking, at the cost of holding the hub lock during the delay; ensure another iteration actually remains (`W/p10-sol-hub-inloop-retry.diff:50`).

4. **Runtime-PM rule / p4 — agree. Interlock / p7 — incomplete.**

   **Verified:** DWC3 forbids runtime PM during probe (`K/drivers/usb/dwc3/core.c:2321`), so matching `bind` addresses rebind resets. Explicitly restoring `auto` after bind also makes sense.

   **Wrong because:** the pre-hook continues after its 45-second lock timeout (`W/p7-scripts.diff:52`), and `post` removes the marker **before** its xHCI recovery (`:60`). That allows the reconnect helper to tear down DWC3 during post-resume rebinding.

   **Better:** serialize the entire post recovery with the same lock and retain the marker until recovery finishes. A timeout cannot count as successful exclusion; coordinate suspend admission through a service that can actually prevent entry. Keep the lock held through each complete reconnect transaction.

5. **Storage / p5–p6 — agree with RAID denial and hiding; wrong premise about loop authorization.**

   **Verified:** a missing UDisks **Drive object** does not imply a missing polkit `"drive"` detail. UDisks 2.11.2 falls back to the block’s preferred device name. `"device"` is also that path; `"drive.removable"` is supplied as `"true"` only for removable drives. Therefore the original rule already denies ordinary block operations on these loops—and on user-created loops. The added loop helper does not implement the promised user-loop exception. See [`udisksdaemonutil.c:780,816,858`](https://github.com/storaged-project/udisks/blob/udisks-2.11.2/src/udisksdaemonutil.c#L780).

   Other relevant calls are:
   - **RAID creation:** authorization uses a NULL object, without member-device details; p5 correctly closes it. [`udiskslinuxmanager.c`, `handle_mdraid_create`](https://github.com/storaged-project/udisks/blob/udisks-2.11.2/src/udiskslinuxmanager.c).
   - **LoopSetup:** also has no block details, but requires a caller-supplied open FD; it does not grant access to an otherwise inaccessible UFS file.
   - **Job cancellation:** a Job object supplies no block/drive details. `cancel-job-other-user` can interrupt a root-started, cancellable UFS operation and is not denied by p5. [`udisksbasejob.c:378`](https://github.com/storaged-project/udisks/blob/udisks-2.11.2/src/udisksbasejob.c#L378).

   `polkit.spawn()` exists in [127’s Duktape backend](https://github.com/polkit-org/polkit/blob/127/src/polkitbackend/polkitbackendduktapeauthority.c#L999). The fixed argv and strict device regex avoid shell injection; sysfs exports `backing_file` mode 0444 (`K/drivers/block/loop.c:648`). However, p5 fails open on **every** helper error, not merely an unattached loop, and backing identity can change after checking. Spawn runs as polkitd and blocks authorization processing, with a ten-second limit. [Polkit manual](https://polkit.pages.freedesktop.org/polkit/polkit.8.html).

   **Better:** retain the conservative drive denial, remove the redundant spawn, and explicitly address manager/module actions and cross-user cancellation. Optional storage-module coverage remains unverified here. p6 is useful UI hiding, not authorization; use `ATTRS{loop/backing_file}` if loop partitions must also match.

6. **Bottom port — better: TCPM-controlled, source-only first.**

   Concrete initial stage-B sketch, retaining the existing host-only `usb_2`:

   ```dts
   #include <dt-bindings/interrupt-controller/irq.h>

   &qupv3_id_1 { status = "okay"; };
   &gpi_dma1 { status = "okay"; }; /* inherited i2c13 DMA references */

   &tlmm {
       rog5_btm_alert: rog5-btm-alert-state {
           pins = "gpio118";
           function = "gpio";
           drive-strength = <2>;
           bias-pull-up;
           input-enable;
       };
   };

   &i2c13 {
       status = "okay";
       clock-frequency = <400000>;
       pinctrl-names = "default";
       pinctrl-0 = <&qup_i2c13_default>;

       typec@4e {
           compatible = "richtek,rt1715";
           reg = <0x4e>;
           interrupt-parent = <&tlmm>;
           interrupts = <118 IRQ_TYPE_LEVEL_LOW>;
           pinctrl-names = "default";
           pinctrl-0 = <&rog5_btm_alert>;
           vbus-supply = <&rog5_btm_vbus>;
           wakeup-source;

           connector {
               compatible = "usb-c-connector";
               label = "bottom";
               power-role = "source";
               data-role = "host";
               pd-disable;
               typec-power-opmode = "default";
           };
       };
   };
   ```

   Remove the stage-A `rog5-btm-vbus-output` consumer so TCPM owns VBUS exclusively. No role switch is needed for this fixed-source/fixed-host version.

   **Verified:** wrapper 1/i2c13 and GPIO0/1 `qup13` pinctrl are in `K/arch/arm64/boot/dts/qcom/sm8350.dtsi:1261,1433,3402`; stock address/ALERT are in `S/arch/arm64/boot/dts/vendor/qcom/ZS673KS-EVB-overlay.dts:793`. RT1715’s regulator callback controls sourcing, not the ASUS charging path (`K/drivers/usb/typec/tcpm/tcpci_rt1711h.c:147`). `pd-disable` requires `typec-power-opmode` (`tcpm.c:7998`).

   **Charging needs more than DT:** dual power can use `power-role="dual"; try-power-role="sink"` with the same non-PD configuration. For PD, provide conservative 5-V source/sink PDOs and `op-sink-microwatt`. Host-only TCPM maps sink operation to `USB_ROLE_NONE` (`tcpm.c:1302`); provide controller gating if that must stop xHCI.

   **Verified stock protocol:** boost is OEM owner **32782**, opcode **0x2102**, followed by GPIO4 switching (`S/drivers/power/rt-charger.c:237`; `asus_battery_charger.c:865`). Charging coordination is separate: owner **32784**, type **0xF0**, capabilities/state/VID **0xF2**, ADSP-selected request **0xF4**, APSD **0xF5**, and custom-source notification **0xF3** (`rt-charger.c:87,418,489,758`). VBUS-source query **0x2003** reports bottom=1, side=2 (`asus_battery_charger.c:311,2897`). Port this coordination without allowing ADSP and TCPM to independently negotiate different contracts; 0089 alone does not prove safe sinking or current limits.

   **Wrong because:** always-on “automatic 5 V” is unsafe. Reset defaults are **Rd/Rd, DRP off** (`ROLE_CONTROL=0x0a`); firmware may subsequently change them. A charger/PC can therefore detect a sink and supply VBUS while the phone also drives it. Source contention/backfeed is the hardware inference. Proper minimal operation needs Rp, debounced Rd attachment, VBUS checks, and detach handling. [Richtek datasheet, p.24](https://www.richtek.com/assets/product_file/RT1715/DS1715-05.pdf).

   **p8 — agree with the placement; safety remains conditional.** Glue propagates `wakeup-source` to DWC3 (`legacy.c:817`), avoiding host `core_exit()` when full reinit is unnecessary (`core.c:2504`); 0090 provides retention. Apply p1 first. Retention does not prove remote-wake signaling, VBUS continuity, or suspend/resume reliability.

7. **Side SuperSpeed — agree with a small opt-in change; defer making it default.**

   ```dts
   #include <dt-bindings/phy/phy-qcom-qmp.h>

   &usb_1_dwc3 {
       maximum-speed = "super-speed";
       phys = <&usb_1_hsphy>,
              <&usb_1_qmpphy QMP_USB43DP_USB3_PHY>;
       phy-names = "usb2-phy", "usb3-phy";
   };
   ```

   Remove `qcom,select-utmi-as-pipe-clk` from the **composed** `usb_1` node. A `/delete-property/` in a separately compiled overlay does not delete an existing base property; remove its originating assignment or use composition-time deletion. The PHY/controller SS graph already exists (`K/sm8350.dtsi:2666,2683`; `R/displayport-side.dtso:77`).

   **Verified:** the current QMP node has orientation-switch only, so it remains USB3+DP/two lanes even when ADSP reports C/E. With **mode-switch added**, C/E selects DP-only and powers off USB3 despite an active USB consumer; D/F retains USB3+DP (`K/drivers/phy/qualcomm/phy-qcom-qmp-combo.c:4450,4484`). Switching is deferred while DP is already powered (`:4474`). There is no direct DWC3 maximum-speed change; loss of the SS link and USB2 fallback/re-enumeration are the expected consequence, not a guaranteed seamless transition.

   **Inference/recommendation:** worthwhile for fast disks or Ethernet, with extra PHY power and more complicated DP/reconnect ownership. It does not fix USB2 `-71`; enabling SS also makes helper rebinds affect a PHY now genuinely shared with DP. USB3 interference with 2.4-GHz radios is documented, but its magnitude on this phone is unmeasured. [USB-IF white paper](https://www.usb.org/sites/default/files/327216.pdf).
