# GPT-6.1-Sol review: device profile in the boot sources (2026-09-30)

Answer to [the brief](2026-09-30-device-profile-brief.md) (codex exec, gpt-6.1-sol, reasoning high, read-only sandbox). Absolute links in the answer were shortened to repository paths.

## Answer

I found blockers in the new installation path, though no additional reference-phone boot-check regression from moving literals into variables.

1. **P1 — Root installer uses a predictable temporary file.** [rog5-install-userspace:72](../../scripts/device/rog5-install-userspace) redirects into `/tmp/rog5-userspace.$$`. A local user can precreate a symlink there, causing a root invocation to overwrite another file. **Fix:** use `mktemp` with restrictive permissions and install the cleanup trap before writing.

2. **P1 — Formatting undoes the overlay’s allocation.** [stage-persistent-root-overlay.sh:228](../../scripts/device/stage-persistent-root-overlay.sh) runs `mkfs.ext4` after `fallocate` without disabling discard. E2fsprogs defaults to discard and implements regular-file discard by punching holes, leaving the image sparse again. Later loop writes can therefore exhaust userdata despite successful staging. [Upstream mke2fs](https://raw.githubusercontent.com/tytso/e2fsprogs/v1.47.4/misc/mke2fs.c), [regular-file discard implementation](https://raw.githubusercontent.com/tytso/e2fsprogs/v1.47.4/lib/ext2fs/unix_io.c). **Fix:** add `nodiscard`, reapply allocation after formatting, and verify backing allocation before publication.

3. **P1 — Rebuilding the root image invalidates existing bundles.** [rog5-build-rootfs:390](../../scripts/host/rog5-build-rootfs) generates a fresh UUID on every `image` step. The documented workflow builds a profile and bundles, then reruns `boot,image` to embed those bundles. The resulting filesystem has UUID B while their attestor expects UUID A; regenerating the profile alone cannot repair the embedded ramdisks. **Fix:** generate and persist the UUID once per work directory, reuse it on rebuilds, and require an explicit operation to change it. Supplying the same `--fs-uuid` is an immediate workaround.

4. **P2 — Wrapper packaging does not carry the profile or alternate trust key through.** [package-production-ram-trial.py:175](../../scripts/host/package-production-ram-trial.py) passes the repository’s reference `recovery-init`. The called [wrapper builder:12](../../scripts/device/build-persistent-slotb-recovery-initramfs.sh) also selects the reference loader, and still pins the reference base and raw key at lines 57–80. Thus another profile’s ramdisk can be packaged with reference wrapper geometry, while another signing key’s base is rejected outright. **Fix:** pass rendered init and loader sources through both wrapper packagers, explicitly pin the selected base/key, and verify the key and profile in the finished recovery archive.

5. **P2 — Service-state staging retains a reference filesystem-size pin.** [stage-persistent-service-state.sh:170](../../scripts/device/stage-persistent-service-state.sh) requires exactly `51124000` ext4 blocks. This rejects other storage variants—and even the reference-size filesystem produced by `plan`, which specifies `51124696` blocks. I reproduced both outcomes using the extracted function with stubbed inventory commands. **Fix:** profile the observed ext4 block count, independently of partition capacity, and validate that it fits p23.

6. **P2 — Production runtime guards still assume `sda`.** [production-wifi:82](../../initramfs/production-wifi), [production-trial-commit:72](../../initramfs/production-trial-commit), and [rog5-update:605](../../initramfs/rog5-update) reject writable UFS resolved under another disk letter, although the profiled init supports that resolution. Wi-Fi, trial acceptance, or update acceptance then fails. **Fix:** validate these guards against the exact disk/userdata relationship recorded by the init. Legacy native-Wi-Fi helpers also retain literal `117` counts if those paths remain supported.

7. **P2 — The new cap breaks compatibility without proving backing capacity.** [rog5-device-profile:140](../../scripts/host/rog5-device-profile) admits the current 182 GiB overlay, but rejects every previously accepted image above approximately 184.93 GiB, including 185 GiB, regardless of its actual backing allocation. Conversely, a sparse image below the cap can pass on a smaller userdata filesystem or alongside enough other files to exhaust backing space. **Fix:** treat this as a policy limit, document its compatibility change, and separately validate actual ext4 capacity and image allocation. Partition geometry alone cannot provide that guarantee.

For questions 1 and 3, I found no additional evaluation-time, `set -u`, subshell, or ash/bash issue. All seven reference renderings were byte-identical; shell syntax checks passed. Missing keys, unknown keys, and attempted shell injection were rejected; supplied derived values are recomputed.

For question 5, the relaxed partial rule did not reveal another concrete regression: it remains restricted to the unpublished staging path and refuses recognizable filesystems. The allocation issue above is the material problem.

For question 6, the existing base/key pins prevent a wrong-key wrapper from successfully packaging; the change currently fails closed for alternate bases. Those guards need explicit replacement before alternate-base support is complete.

I did not modify files or contact a device. I used in-memory checks and stubbed functions; I did not rerun suites that create temporary files.
## Disposition

1. **Fixed.** `rog5-install-userspace` uses `mktemp` (trap set before writing).
2. **Fixed and reproduced.** A 64 MiB `fallocate`d file formatted with default
   `mkfs.ext4` kept 696 of 131072 blocks; with `-E nodiscard` plus a second
   `fallocate` all 131072. Both stagers now pass `nodiscard`, allocate again
   after formatting, and the overlay stager refuses an image whose allocated
   bytes are below its size.
3. **Fixed.** `rog5-build-rootfs` keeps one UUID per work directory
   (`WORK/fs-uuid`); `--fs-uuid` replaces it.
4. **Fixed.** `package-production-ram-trial.py` and
   `package-slotb-boot-wrapper.py` take `--device-profile` and render
   `recovery-init` and the selector loader with it;
   `rog5-make-bundle.py` passes a `device_profile` entry of
   `bundle-inputs.json` to both the ramdisk and the packager. The recovery
   builder accepts another recovery base when its caller pins it
   (`ROG5_RECOVERY_BASE_SHA256`, set by the packagers from the hash they were
   given), checks the key member is a raw 32-byte key, and keeps the
   verifier/kexec/key pins for the reference base. Offline check: wrappers
   packaged from the reference inputs with no profile and with a 512 GB
   profile both PASS; the second carries `rog5_ufs_disk_sectors=1000204288`
   and `rog5_ufs_node_count=118` in both the recovery init and the selector
   loader.
5. **Fixed.** The state stager requires the userdata ext4 to fit its
   partition instead of exactly 51124000 blocks.
6. **Open, documented.** `production-wifi`, `production-trial-commit` and
   `rog5-update` still expect the UFS main LUN to be `sda`. On SM8350 LUN 0
   enumerates first, so this holds on every ROG Phone 5 we know of, but the
   init is more general. The legacy native-Wi-Fi, local-image and
   RAM-transaction paths keep literal 117 counts; they are not in the
   production bundle. Listed in the install guide's gap list.
7. **Accepted as a policy limit, documented.** The cap refuses images above
   184.9 GiB on the reference phone (previously 192 GiB); the reference
   overlay is 182 GiB. The stagers now create fully allocated images, which
   removes the sparse-overcommit case for new installs; the boot does not
   check allocation because the reference overlay (created sparse in
   September) is not fully allocated.
