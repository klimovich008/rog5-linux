## Round 1 answer

I would fix **two cleanup races in 0154 and the missing low-IOVA reservation before a firmware boot**. The remaining DT hardware values look correct. Nothing was modified.

Kernel references below use the supplied r113 source tree; `iris/` means `drivers/media/platform/qcom/iris/`.

1. **[P1] Timeout cleanup can deadlock against the IRQ thread.**

   The new call at [0154:70](patches/linux-7.2.7/0154-media-iris-power-the-core-off-when-the-firmware-does-not-come-up.patch:70) reaches `iris_core_deinit()`, which holds `core->lock` while calling `iris_vpu_power_off()`. That calls synchronous `disable_irq()`. The IRQ thread needs the same mutex, both to clear the interrupt and to read response queues.

   A late interrupt therefore permits: cleanup holds the mutex → waits for IRQ thread → IRQ thread waits for mutex. See [iris_core.c:19](/home/deck/.local/state/rog5-kernel-7.2.7-build-r113/source/drivers/media/platform/qcom/iris/iris_core.c:19), `iris/iris_vpu_common.c:232`, and [iris_hfi_common.c:107](/home/deck/.local/state/rog5-kernel-7.2.7-build-r113/source/drivers/media/platform/qcom/iris/iris_hfi_common.c:107).

   The underlying power-off locking problem predates 0154, but this patch exposes it to firmware-response timeouts. Quiesce and synchronize the IRQ **outside `core->lock`, before removing clocks and power**, with teardown serialized against reinitialization.

2. **[P1] An old waiter can tear down a replacement firmware attempt.**

   The wait correctly happens outside `core->lock`; otherwise the IRQ could not deliver its response. However, the new unconditional deinit does not establish that it still owns the failed attempt.

   Concrete sequence: opener A waits → firmware reports a system error → recovery work deinitializes and starts attempt B → A’s old wait times out → A deinitializes B. Recovery can also reset the shared completion while A still waits. See [iris_probe.c:213](/home/deck/.local/state/rog5-kernel-7.2.7-build-r113/source/drivers/media/platform/qcom/iris/iris_probe.c:213), `iris/iris_hfi_gen1_response.c:228`, and patch lines 54–70.

   There is also an existing concurrent-open problem: `iris_core_init()` returns success whenever state is already `IRIS_CORE_INIT`, although that state is set **before firmware initialization completes** (`iris/iris_core.c:57,65`). Another open can proceed while the first initialization is pending; 0154 can subsequently remove its core.

   Serialize initialization/recovery ownership and make timeout cleanup conditional on the same attempt still being current. Protect state checks with the mutex; merely resetting the completion cannot provide this ownership.

3. **[P1] The DT permits nonsecure allocations inside the protected video IOVA range.**

   [Overlay:75](dts/qcom/sm8350-asus-rog-phone5-video.dtso:75) specifies the SMMU and firmware carve-out, but no low-IOVA reservation. I confirmed the supplied `d14-test.dtb` also lacks one.

   Stock explicitly allocates `venus_ns` from `0x25800000` through `0xdfffffff`: [stock-fdt.dts:23369](/home/deck/.local/state/rog5-production-boot-20260923/trial-stockcap-c1-session/stock-fdt.dts:23369), and downstream `lahaina-vidc.dtsi:53–61`. The driver’s `dma_mask = 0xdfffffff` supplies only the upper limit.

   This is a documented SM8350 failure: an [upstream fix proposal](https://lists.openwall.net/linux-kernel/2026/08/07/614) reports SMMU faults and spontaneous reboots when video DMA enters the range below `0x25800000`.

   Reserve **`[0, 0x25800000)` in IOVA space**, using a reserved-memory node with `iommu-addresses` and no physical `reg`, then reference it as the **second** `memory-region`. Keep `pil_video_mem` first: `iris_firmware.c:33` loads firmware from index zero. Linux 7.2.7 already implements this reservation mechanism in `drivers/iommu/of_iommu.c:204–264`.

   The composition script must then check that reservation and account for the additional node when stripping the overlay.

For the other 0154 questions:

- **Single-open runtime PM counting is balanced:** open takes one reference; deinit temporarily takes another; deinit drops its reference; the failing open drops its original reference: **1 → 2 → 1 → 0**. Neither waiting nor explicitly powering off consumes the opener’s reference. See `iris_vidc.c:146–157` and `iris_core.c:17–32`.
- **Recovery needs its own PM protection.** `iris_sys_error_handler()` holds no PM reference across deinit + init. After deinit’s put, autosuspend can race the new initialization. This is inherited, but matters to the new cleanup: `pm_runtime_resume_and_get()` can invoke another power-on when state is INIT and PM considers the device suspended. Hold a PM reference across the whole recovery operation.
- **Sequential deinit calls avoid double unload/power-off** through the locked `IRIS_CORE_DEINIT` guard. That guard does not prevent an old waiter from shutting down a newer attempt.
- **Normal IRQ depth is balanced:** power-on enables; ordinary ISR disables and its thread reenables; power-off disables. On watchdog, the ISR leaves the IRQ disabled and power-off deliberately skips another disable. The synchronization race above is the problem, rather than an unconditional extra disable.
- **`reinit_completion()` is placed before new commands, which is appropriate**, but its comment overclaims protection. It clears an already completed response; it cannot exclude an old response handler that completes afterward, or distinguish old and new waiters.
- **Error responses usually still become `-ETIMEDOUT`.** Gen1 sets ERROR and returns without completing (`iris_hfi_gen1_response.c:282–291`); gen2 does likewise (`iris_hfi_gen2_response.c:295–303`). Wake waiters on both success and failure and inspect the recorded result afterward. The commit-message statement that error responses were previously not failures is inaccurate for this ordinary path: they eventually timed out.
- **Returning `-EINVAL` for invalid UC-region settings is correct.** It enters the existing firmware-unload/power-off unwind instead of reporting success. The firmware logging and preservation of the original load error are also useful.
- **Shutdown success remains unchecked.** `iris_core_deinit()` ignores the PAS shutdown result before freeing queues and declaring DEINIT. An unsuccessful shutdown therefore does not establish the “clean state” claimed by the commit message (`iris_core.c:21–27`, `iris_firmware.c:105–107`).

For the first firmware boot:

- **SID `0x2100` on a low context bank remains unproven.** The allocator’s high-bank exceptions cover DSP ranges, not `0x2100` (`arm-smmu-qcom.c:643–666`). Patch 0064 reserves firmware-owned banks; it does not prove that the hypervisor accepts every remaining low-bank route. `qcom_smmu_write_s2cr()` writes without checking readback (`:549–581`). Verify the effective SMR/S2CR route before interpreting an HFI timeout. A Linux IOMMU-group attachment alone is insufficient.
- **The SCM protection arguments match downstream behavior.** Downstream derives `cp_size` from the nonsecure pool’s start and nonpixel limits from the secure nonpixel pool: [hfi_common.c:3440](/home/deck/Projects/rog-phone-linux-migration/kernel-src/msm-5.4/techpack/video/msm/vidc/hfi_common.c:3440). Thus `cp_start=0` is not a request to reserve 600 MiB of physical RAM. Watch for `qcom_scm_mem_protect_video_var failed`; the new authenticated/started message occurs **before** that call.
- **`INT_MAX` is clamped**, not sent unchanged: video memory becomes 15,000,000 kB/s average, with configuration at 1,000 kB/s (`iris_platform_vpu2.c:49–52`, `iris_resources.c:19–45`). This is a substantial temporary vote; failure cleanup should remove it.
- **Check effective rail votes after cleanup.** `iris_opp_set_rate(dev, 0)` selects the lowest OPP through `devfreq_recommended_opp()`, rather than explicitly disabling the OPP table (`iris_resources.c:62–70`, `drivers/devfreq/devfreq.c:2089`). Useful dmesg distinctions are: firmware request/load failure → PAS authentication failure → authenticated/started followed by protection failure → UC-region rejection → HFI timeout/system error. Also look for `Unhandled context fault` with SID/context-bank evidence, `failed to suspend/resume`, clock/GDSC failures, `Unbalanced enable for IRQ`, and a task stuck in `disable_irq()`.

**No separate SM8350 platform-data implementation is justified by these sources.** The fallback selects four-pipe VPU2/HFI-gen1 data, MX/MMCX domains, and the expected clocks/resets (`iris_platform_vpu2.c:96–122`). Firmware must remain SM8350-specific. The IOVA correction belongs in DT; any proven low-bank restriction belongs in the SMMU quirk. The lifecycle fixes are generic Iris fixes.

## Round 2 answer

**I still find blocking lifecycle issues in 0154.** The IOVA reservation and new platform plumbing look sound. Nothing was modified.

1. **[P1] Completing a failed initialization can now produce success or skip cleanup.**  
   [0154:153](patches/linux-7.2.7/0154-media-iris-power-the-core-off-when-the-firmware-does-not-come-up.patch:153), [0154:130](patches/linux-7.2.7/0154-media-iris-power-the-core-off-when-the-firmware-does-not-come-up.patch:130).

   Concrete sequence: opener A waits; the failed SYS_INIT response sets `ERROR` and completes; before A resumes, opener B enters the existing `ERROR` branch at [iris_core.c:60](/home/deck/.local/state/rog5-kernel-7.2.7-build-r113/source/drivers/media/platform/qcom/iris/iris_core.c:60). That branch jumps to `error`, which sets `DEINIT` **without unloading firmware or powering off**.

   A then consumes the failed response’s completion, sees `DEINIT` rather than `ERROR`, and returns success. If A sampled `ERROR` earlier, its abandonment instead skips teardown because B has set `DEINIT`. Either interleaving can leave the failed core powered. The new completion-on-error behavior exposes the false-success case; the attempt number only protects teardown ownership.

   Preserve the result of the waited attempt, and make rejection of an already erroneous core leave its state and cleanup ownership intact.

2. **[P1] Recovery still has the original IRQ/mutex deadlock.**  
   [0154:96](patches/linux-7.2.7/0154-media-iris-power-the-core-off-when-the-firmware-does-not-come-up.patch:96), [iris_probe.c:218](/home/deck/.local/state/rog5-kernel-7.2.7-build-r113/source/drivers/media/platform/qcom/iris/iris_probe.c:218).

   `iris_sys_error_handler()` calls `iris_core_deinit()`, which still holds `core->lock` through teardown. For a non-watchdog error and pending normal IRQ thread, teardown reaches synchronous [disable_irq() at iris_vpu_common.c:240](/home/deck/.local/state/rog5-kernel-7.2.7-build-r113/source/drivers/media/platform/qcom/iris/iris_vpu_common.c:240), while that thread waits for the mutex at [iris_hfi_common.c:107](/home/deck/.local/state/rog5-kernel-7.2.7-build-r113/source/drivers/media/platform/qcom/iris/iris_hfi_common.c:107).

   This is an unresolved previous finding in the recovery caller. The new abandonment helper fixes synchronization for its own caller; `iris_core_deinit()` also needs IRQ quiescence outside the mutex.

3. **[P2] 0156 warns on expected firmware-owned routes during reset.**  
   [0156:85](patches/linux-7.2.7/0156-iommu-arm-smmu-qcom-ROG5-SM8350-report-stream-routes-the-hypervisor-did-not-take.patch:85).

   The filter checks the **quirk-adjusted hardware value**. Logical `BYPASS` becomes `TRANS` to the bypass context bank, so it passes this filter. During reset, every S2CR is written, including firmware-owned streams whose bypass writes are deliberately ignored—the condition patch 0064 uses to reserve their banks.

   Consequently, boot can emit one warning per protected stream despite successful Linux-device attachments; later resets repeat them. Filter on Linux-owned logical translating entries, such as original `s2cr->type == TRANS` with a nonzero ownership count. The SMR indexing and readback itself otherwise look correct.

The new abandonment helper’s **IRQ depth arithmetic is balanced**:

| Case | Depth sequence |
|---|---|
| IRQ enabled | `0 → 1 → 2 → 1` |
| Hard ISR ran; normal thread pending/running | `1 → 2 → 1 → 2 → 1` |
| Watchdog interrupt | `1 → 2 → 1` |
| Already torn down | `1 → 2 → 1` |
| Replacement attempt running; teardown skipped | `0 → 1 → 0` |

Its PM reference is also balanced: `1 → 2 → 1` for an opener, and `0 → 1 → 0` for recovery without another holder. Failed acquisition gets no put. Acquisition and release occur outside `core->lock`, so I found no new PM-resume lock inversion there. Recovery retains its acknowledged inherited lack of a reference across the entire deinit/init operation.

For DT, I verified the supplied composed DTB and the actual arm-smmu → `iommu_dma_get_resv_regions()` → `of_iommu_get_resv_regions()` → `reserve_iova()` path. The SoC DMA range translates the reservation identically, reserving `[0, 0x25800000)`. Early and late reserved-memory scans skip the node without `reg`/`size`; Iris uses index zero; the inspected OF and kexec paths introduce no issue.

I found no additional bugs in 0155, composition checks, service ordering/publication, module-list packaging, or the firmware installer. The deliberate `dt_sources` omission is not a finding.

Patch applicability and shell syntax checks passed. This was source and artifact inspection only; no compilation or hardware testing.
## Round 3 answer

**One remaining blocker in 0154:** the synchronous init-error unwind still calls `iris_vpu_power_off()` while holding `core->lock` ([iris_core.c:100](/home/deck/.local/state/rog5-kernel-7.2.7-build-r113/source/drivers/media/platform/qcom/iris/iris_core.c:100)).
