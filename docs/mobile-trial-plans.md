The [five trial plans](../configs/mobile/trial-plans.json) are offline plans,
**not armed sessions**. They bind the current test source hashes and common
identity, power, thermal, rescue, abort, cleanup and return checks. There is no
new candidate, admission or execution claim. Exact future candidate hashes remain
unassigned because candidate generation and all phone operations are excluded
from this repair.

The smallest next physical question is whether the corrected panel prepares,
shows a stable 60 Hz pattern and blanks cleanly on the exact production build.
It requires a separately authorized, fully prepared candidate and reviewed
recording/cleanup session. Existing signed 136f bytes lack the current panel and
boot-health fixes and cannot be represented as that candidate.

Buttons/default-off LED, touch controller/protocol, A660 rendering and
suspend/idle drain retain separate plans and proof. Do not make touch or display
wait for unrelated server milestones. Do not promote IOMMU attachment or generic
QEMU execution into rendering or hardware proof. The corrected byte order is
software-proven; it is not an optical brightness qualification.

Before asking for Ready, finish all builds, offline checks, staging, recording
setup and actual input/output discovery under a future explicit authorization.
Only short current-state checks and arming may follow Ready. Give one short
physical action at a time. If readiness or a prerequisite expires, release the
operator and resolve preparation independently. No countdown or Ready request
is active during this offline task.
