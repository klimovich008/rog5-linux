# Battery and charging: stock ASUS charger stack vs our qcom_battmgr

Phone not reachable (169.254.77.2 timed out; 10.77.0.2 refused the key), so everything below is from source plus the repo's own test records. Paths: S = `/home/deck/.local/state/rog5-kernel-compare-20260927/stock`, O = `.../ours`, R = `/home/deck/.local/state/rog5-prod-boot-20260923`, DTBO = `~/.local/state/rog5-stock-payload-20260927/dtbo/dtbo0.dts`, RC = `.../vendor/etc/init/hw/init.asus.rc`.

Topology first: on the ZS673KS the whole charger stack (SMB1399 pair, fuel gauge, JEITA, PD/QC negotiation, adapter ID, thermal charging policy) runs in the ADSP `charger_pd` service. The stock kernel is only a glink client: `qti_battery_charger_2.c` (owner 32778, the same BC protocol qcom_battmgr speaks) plus `asus_battery_charger.c` (owner 32782 "asus_BC", OEM opcodes). No SMB1398/qpnp-smb5 kernel driver is used (DTBO only has the SMB139x VADC channels, DTBO:221-255; `lahaina_GKI.config:73-74` builds only `QTI_PMIC_GLINK`/`QTI_BATTERY_CHARGER`). So we run the same firmware-side charger; the gaps are in what the kernel reports and which knobs it exposes.

## 2. Details for the top items

**#1 temperature.** The generic QTI driver (SAKE branch) divides by 10, so mainline copied that. ASUS's ZS673KS branch explicitly converts "0.1K to 0.1C" by subtracting 2731 (qti_battery_charger_2.c:1126, and for USB_TEMP at :929). With our conversion the displayed value is (T+273.15)/10 °C: real 24-27 °C shows as 29.7-30.0, which is exactly the spread in our records; 45 °C would show as 31.8. Nothing we run today keys off battery temperature, but anything that will (thermal policy, upower warnings) is blind. One-line fix inside the existing `asus,cell-voltage-readonly` branch (rename the flag to something like `asus,rog5-charger-quirks` if it grows).

**#2 charge units.** Stock prints "FCC:%dmAh, RM:%dmAh" from CHARGE_FULL/CHARGE_COUNTER and a second line "TFCC/TRM" from OEM opcode 0x3007 (u16 mAh each). Our calibrations show charge_counter moving at 2x the measured pack current and upower showing 47.6 Wh design (5.5 Ah × 8.65 V; upower has no `voltage_max_design` here so it uses `voltage_now`). Halving the three charge properties gives ~23-24 Wh and correct time-to-empty; `current_now`, `voltage_now`, `power_now` are already pack values (the 2026-09-24 bench used them fine). Reading 0x3007 through the existing OEM path is a 30-line probe if the lead wants gauge-side confirmation first.

**#3 health.** Mechanical enum diff; every value ≥5 from this firmware is off by one on kernels ≥6.x. Worth sending upstream since sm8550 phones have the same firmware numbering.

**#4 charge limit.** Firmware facts from the stock driver: owner 32782 (already used by 0018 for cell voltages, request/response pattern proven), opcodes 0x2117 (`mode`,`value` u32 pair; ack has the same length), 0x2105 (`enable`), 0x2108 (`enable`), 0x2103/0x2104 (limit enable/cap — ADSP-side limit whose behaviour the ASUS kernel stopped trusting: "Tranfer this feature back to kernel", :1126,1170, and reimplemented at :2807-2809). The kernel-side algorithm is: charging_pause = (limit_en && soc ≥ cap) || smartchg || bypass || feature_stop; on change send mode2(0x8, pause); separately usbin_suspend(1) above 60 % for the ultra-battery-life mode with a `demo_recharge_delta` hysteresis (:2829-2843). Mode bits: 0x1 slow-charge watts, 0x2/0x4 side/bottom thermal alert, 0x8 bypass, 0x20 18 W workaround, 0x100 audio LCM (charger low-current mode off while a mic is open), 0x200 launched-time trigger (:359-368). "Bypass" here is the ROG feature: the system is powered from the adapter and the cells rest, which is precisely what an always-plugged server wants. Mainline-shaped surface: `charge_behaviour` (auto/inhibit-charge/force-discharge) on qcom-battmgr-bat plus `charge_control_start_threshold`/`end_threshold` (kernel-side compare, with the 5 % delta convention the driver already uses for sm8550). upower/phosh need nothing new; a systemd unit or rog5-powerd writes the threshold. Unknowns to test live: whether charger_pd clears the mode on cable detach (stock re-sends within 60 s anyway) and whether 0x2104's cap is honoured by the firmware on its own (if yes, items 4 becomes S).

**#6/#7 USB side.** Stock exposes USB `TEMP` (prop 10, 0.1 K) and reads the adapter type from prop 7; QC2/3/3+ come back as 0x80-0x82 and are shown as DCP. Our sm8350 usb psy reads prop 6 for usb_type; if the firmware's prop 6 is the generic "type" and prop 7 the detected adapter, we may be showing the wrong thing, and any QC value makes the sysfs read fail. Check `cat /sys/class/power_supply/qcom-battmgr-usb/usb_type` with a PD and a QC adapter.

**Fast charge (30 W/65 W).** Negotiation, ASUS adapter-ID (0x0b05) detection and the 18 W workaround are entirely ADSP/PD-firmware side; the stock kernel only forwards "charger type level" notifications to an extcon for the UI (:2019-2057) and sends the adapter/side VID from the RT1715 path. Side-port fast charging should therefore already work with our kernel (our DT leaves PD to the ADSP: R/dts/qcom/sm8350-asus-rog-phone5-usb-otg-side.dtso); there is no charging-rate record in test-results to confirm it, so a plug-in measurement (`current_now`/`voltage_now` on the usb psy) is the next check. Bottom-port fast charge is item 8.

## 3. Works the same / not needed

- Charger/PD/JEITA/CC-CV/step charging: all on ADSP charger_pd in both ("JEITA is decided on ADSP", :2943); same firmware, same PDR service (`tms/servreg` + `msm/adsp/charger_pd`, O/drivers/soc/qcom/pmic_glink.c:396-397 = S/…/lahaina.dtsi:5571-5573).
- BC protocol: owner, opcodes 0x04/0x07/0x30-0x35, request/response structs and the 1 s ack timeout match (qti_battery_charger_2.c:24-45,147-172 vs qcom_battmgr.c:33-124). Status, charge_type, technology, usb_type enums (≤ CUSTOM / ≤ APPLE_BRICK_ID) are numerically compatible; only HEALTH is not (#3).
- Properties present in both: status, health, present, charge_type, capacity, ocv, voltage_now/max, current_now, temp, technology, charge_counter, cycle_count, charge_full(_design), model_name, TTF/TTE, resistance, SOH, power_now; usb online/voltage/current/max/ICL/type; wireless (ROG5 has none; the psy is harmless).
- Charge-units fix 0038 (unit = mAh) is right; the cell-voltage patch 0018 mirrors stock's OEM read 0x3005 with the same 2×u16 layout (:197-201).
- Notifications: both enable BC notifications at probe; the ~2.3 s PMIC_RTR_ADSP_APPS traffic seen in the cxsd work is firmware-side and identical on stock (not a kernel difference).
- upower/phosh needs: type=Battery, present, status, capacity, current_now, voltage_now, charge_full(_design), plus usb online — all present; after #2 the Wh figures become right. No `voltage_max_design` is needed (upower falls back to voltage_now).
- Not needed from stock: extcon UI switches (quick_charging, battery_id, invalid_dongle), ASUSEvtlog 3-minute status prints, PMI_MUX_EN/POGO_OTG_EN GPIOs (dock/fan accessory path), wireless FW update, moisture detection, fake_soc, demo-app 60 % modes, launched-time trigger, `charger_limit_mode 16,x` (inbox dongle) and `64,x` (in-call) hooks, the mic-open "LCM disable" vote (audio agent already listed it).
