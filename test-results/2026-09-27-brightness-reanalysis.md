## 1. What I retract, and what the new evidence says

- My FIFO-watermark diagnosis was wrong as a root cause: 0x33 and 0x110033 changed nothing (and stock pads/sizes the DMA buffer exactly like mainline: `dsi_ctrl_copy_and_pad_cmd`, `dsi_ctrl.c:1112-1157`: `roundup4(packet->size)`, 0xFF fill, same "MSM format" header bits). 0074 is harmless but not the fix; keep or drop.
- At every layer I could compare, mainline now equals stock: DMA buffer layout, `CMD_DMA_CTRL` bits (embedded mode, LP bit), `DMA_FIFO_CTRL`, TRIG_CTRL (TE pin, MDP trigger none, DMA sw), EOT (none), esc clock 19.2 MHz, non-continuous clock in both (stock `force_clk_lane_hs` unset), 7 nm PHY common registers (VREG 0x5c, LPTX_STR 0x55, HSTX_STR 0x88, PEMPH 0, LANE_CTRL0 0x1f, CTRL_2 0x40) and per-lane config (`00 00 0a 0a`, clk `8a`; `lahaina-sde-common.dtsi:378-384`), one-wire timing (56 µs / 227 µs), Iris GPIOs (flashed DTBO: wake 92, ready 84, px-reset 93 = ours; px-reset is already high). Register offset mapping is verified across 8 pairs (techpack = mainline + 4; `DSI_6G_REG_SHIFT 4`, `dsi_cfg.h:39`), so `DMA_FIFO_CTRL` 0x50 ↔ mainline 0x4c ↔ absolute **0xae94050**.
- The one assumption everything rested on is unproven: that the DDIC ever received a complete LP long write from us. CASET/PASET/PPS/TE/unlock effects are all masked by DDIC defaults, so "LP long writes lose their last byte" and "the DDIC ignores DBV[7:0]" are indistinguishable so far. The lab module's reads settle it (E0/E1 below).

## 2. How brightness works on stock (kernel + Android), exactly

- Android: the QTI composer writes `/sys/class/backlight/panel0-backlight/brightness` (perms in `vendor/etc/init/hw/init.qcom.rc:204-207`); no ASUS-specific node. The **flashed** DTBO (both `dtbo0` "ANAKIN2 PR" and `dtbo19` "SR1") carries `qcom,mdss-dsi-bl-max-level = <0x3ff>` and `qcom,mdss-brightness-max-level = <0xff>` — userspace range 0..255, kernel `dsi_display_set_backlight` scales ×1023/255 → DBV. (The kernel source overlay says 1023/1023; the flashed one says 255: stock effectively uses 255 steps of 4.)
- Kernel (`dsi_panel.c:654-712`): `dsi_anakin_backlightupdate()` (`dsi_anakin.c:1200-1222`: identity except DBV 1→2, 9→10; 224 floor only in DC/CSC mode), inverted-DBV swap, then — with the Iris present (`iris_is_mp_panel()`), which is the case on every ROG5 —
  - **PT mode (stock's default at boot, `iris_lp_init` → `IRIS_PT_MODE`, `dsi_iris6_lp.c:110`)**: `iris_update_backlight()` (`dsi_iris6_pq.c:2433-2480`) builds `{0x51, hh, ll}` as a DCS **long write**, `DSI_CMD_SET_STATE_HS`, and hands it to the **Iris** (`iris_pt_send_panel_cmd`); the Iris re-transmits it to the panel from its own DSI TX. The Iris HAL (`vendor.pixelworks.hardware.display.iris-service`, class `animation`, loads `/data/vendor/display/irissoft.fw`, params `/vendor/etc/inparm/irissoft/*`) lists "Brightness Smooth / DC Dimming" as Iris features.
  - **ABYP**: `mipi_dsi_dcs_set_display_brightness()` direct, HS. For bl=300: swap → 0x2C01 → 5.4 helper payload `{0x01, 0x2C}` → wire `39 WC=3: 51 01 2C` — identical bytes to our `_large` path.
  - Around a change: `dsi_anakin_set_dimming_smooth()` (`dsi_anakin.c:392-414`) re-sends `53 28` (dimming 20-frame) after FOD/DC events; post-on is `51 00 00 / 53 20 / 55 00 / 29` in LP (`asus-post-on-command-state = dsi_lp_mode`, dtsi line 1093). HBM: `53 E0` / `53 28`.
- Panel lightup with Iris: `iris_enable()` (`dsi_iris6_lightup.c:3105-3135`) sends the whole LP on-command set through **ABYP** first (`iris_abyp_send_panel_cmd`), then lights the Iris in PT. So stock does push LP long writes through the bypass — but the *brightness* on stock normally goes through the Iris TX in PT mode; I found no proof that the direct ABYP+HS brightness path is ever exercised on a running stock phone. Copying stock literally therefore means either (a) PT mode with the Iris firmware (needs `irissoft.fw` + the I3C control path, `dsi_iris6_i3c.c`, out of reach for now), or (b) making the direct path work, which is what the experiments below discriminate.

## 3. Ranked hypotheses

1. **DDIC accepts only P1 of a 0x51 written in LP; HS is what stock relies on, and our HS DMA fails for a host-side reason (likely clock-lane HS request for single DMA packets with a non-continuous clock).** Evidence: `51 FF` short = full; flat 256-blocks; HS long ignored in the 2026-09-23 trial; stock always sends 0x51 in HS; on-command in LP contains only writes whose completeness is unobservable. Mainline only sets `DSI_LANE_CTRL_CLKLN_HS_FORCE_REQUEST` for continuous clocks (`dsi_host.c:918-926`); stock same, but stock's ULPS exit path programs PHY `LANE_CTRL1` (`dsi_phy_hw_v4_0.c:615-631`: 0 then `BIT(5)|BIT(6)`) while mainline never touches LANE_CTRL1 outside `set_continuous_clock`. Test: E0-E2, then E6 patch if HS still fails.
2. **LP long-packet tail loss in our link (Iris ABYP LP path with the Iris MIPI block in the bootloader's leftover state).** Evidence: the Iris listens to LP packets in ABYP (stock can leave ABYP via a DSI "GRCP" packet, `dsi_iris6_lp.c:501-510`), and stock resets its MIPI block around mode changes (`IRIS_POWER_DOWN_MIPI`/`UP_MIPI`, `dsi_iris6_lp.c:946-951`). Test: E1 (reads), E5 (one-wire 9 then 8).
3. **Both LP and HS packets complete, DDIC applies DBV[7:0] only under a mode we do not set (e.g. `53 28` dimming, or a level-2/level-3 key state left half-unlocked because `F0 5A 5A` itself was truncated).** Test: E1 read of 0x52 after slider moves; E3.
4. Timing/race with the frame kickoff: unlikely — `BLOCK_DMA_WITHIN_FRAME` is set (`dsi_host.c:884-886`), no `INTERLEAVE_OP_CONTENTION` errors, and a race would not quantise to 256.
5. DBV format (11/12-bit, left-aligned): excluded — `51 03 FF` bright, `51 04 00` and `51 00 FF` dark fit only "P1[1:0] used, P2 unused" on a 10-bit big-endian DBV.

## 4. Experiments (lab tool + lab module; the lead loads `rog5_dsi_lab.ko` with `insmod`, no msm reload)

Exact wire bytes for every packet the module can emit: `bl hh ll [lp|hs]` → DSI long packet DI 0x39, WC 0x0003, payload `51 hh ll`, HW CRC; `bl hh [lp|hs]` → DSI short packet 0x15, `51 hh`. Reads: `read REG LEN [lp|hs]` → SET_MAX_RETURN_PACKET_SIZE + DCS read 0x06 `REG`, BTA. Nothing else can be sent.

- **E0 — validate reads (LP, screen on, slider idle):** `read 0a 1 lp` (expect `9c`), `read 0c 1 lp` (expect `77`), `read da 1 lp`, `read db 1 lp`, `read dc 1 lp` (ID bytes, any stable non-zero), then the same in `hs`. If LP reads return sane values and HS reads error/zero → HS path broken (H1). If all zero → the response path is broken and 0x52's "00 00" was meaningless.
- **E1 — what the DDIC holds:** `read 45 2 lp` → `09 80` means our LP `44 09 80` arrived complete (LP intact, H2 out; H1/H3 in); `09 00`/other → LP tail loss (H2). Then with the lab slider: set 768 → `read 52 2 lp` (expect `03 00`); set 800 → `read 52 2 lp`: `03 20` = the DDIC has the low byte and merely doesn't display it (H3); `03 00` = lost (H1/H2).
- **E2 — HS, one packet, observed:** slider at 512 (visible 2nd block), then `bl 03 20 hs`, look, `read 52 2 lp`. Then `bl 03 20 lp`, look, read. This directly separates H1 (HS never lands) from H2/H3.
- **E3 — short-write control:** `bl 03 lp` then `bl ff lp` (expect block 3 and full), `read 52 2 lp` after each.
- **E4 — register dump:** `cat regs` with the screen on (runtime PM held by the module). Check (stock offsets): `0x050` DMA_FIFO_CTRL (= current `dma_fifo_ctrl`), `0x03C` CMD_DMA_CTRL, `0x084` TRIG_CTRL, `0x0AC` LANE_CTRL (bit 28 CLKLN_HS_FORCE, bit 24 HS_REQ_SEL_PHY), `0x11C` CLK_CTRL (stock writes 0x23F), `0x0FC` EOT_PACKET_CTRL; PHY CMN `0x0A0`/`0x0A4` LANE_CTRL0/1. Also `devmem 0xae94050` if `/dev/mem` works. Record for the report; differences from the stock values above are the next patch.
- **E5 — Iris MIPI block (opt-in, user watching, recoverable):** `iris1w 9` (POWER_DOWN_MIPI), repeat E1/E2; if the panel goes dark or ready (gpio84) drops, `iris1w 8` (POWER_UP_MIPI) then `iris1w 2`/`6` (enter/force-enter ABYP), or a blank/unblank (prepare re-runs the handshake).
- **E6 — if E2 shows HS still not landing:** patch the panel driver to drop `MIPI_DSI_CLOCK_NON_CONTINUOUS` behind a module param (`continuous_clk=1`; the host then sets `CLKLN_HS_FORCE_REQUEST` and calls the 7 nm PHY `set_continuous_clock`, `dsi_host.c:918-926`, `dsi_phy_7nm.c:1195-1205`) — needs a panel-module reload, not msm. I'll write it on request once E0-E4 are in.

Lab-tool notes: log each `read` result next to the slider value; keep `bl_hs=N` for E1/E3 so the driver's own writes stay LP and only the module's packets change mode; don't slide while a `read` is in flight (the module serialises its own ops only).

## 5. Ambient light (for phosh auto-brightness)

Stock ASH: `lux = adc * 1000 / calvalue` (`ALSPSsensor_2nd.c:696-697`, `light_get_lux`), `calvalue` = per-unit factory value (`/vendor/factory` 50 ms calibration file), default `VCNL36866_LIGHT_CALIBRATION_DEFAULT = 4563` for the ROG5's `vcnl36866_2nd` (`vcnl36866_2nd.h:26`). Register config is identical between stock and `tools/vcnl36866/rog5-vcnl36866.c` (50 ms IT, high dynamic range, persistence 1), so counts match stock; only the constant differs (module `CAL_1000LUX 1658`, i.e. lux = 0.603·adc; stock default would be 0.219·adc — lower still). The user's 1.8-23 lux indoors means few ADC counts; the per-unit factory constant is not in the OTA. Proposal: make the scale a module parameter (or an IIO `in_illuminance_calibscale`), calibrate once against a reference (phone camera light-meter app in the same room), and let phosh's `auto-brightness-bucket.c` do the rest; nothing in gsd/phosh needs changing. Note the flashed stock DT's 255-level userspace range: once fine DBV works, phosh's 1023 levels are strictly better.
